Uber's 5,000 agent skills: trajectory evals, ablations and self-filed bug reports

The cost and ablation numbers are real but sparse; the most portable idea is an always-on skill that lets agents report the bugs they hit.

Uber tried its warehouse-query skill both ways. Without it, the agent made 13% more tool calls, hit six times as many tool errors and took 31% longer, and a blind judge preferred the with-skill answer 87% of the time. A skill here is a directory with a SKILL.md. Its name and description (~100 tokens) are always loaded, the body (under 500 lines) loads when the skill runs, and scripts load on demand. The marketplace is one Git repo. It grew from 1 skill in October 2025 to more than 5,000, with over 1M invocations a month across Claude Code, Codex, OpenCode and an internal agent. A CLI called aifx installs skills into every agent from one config.

The eval mix is about 5% golden cases with tool mocks, 80% real prompts graded on trajectory (whether the agent used the right skills and tools, in the right order) and 15% judged by the skill's author. Suites run on remote sandboxes, which caught skills that relied on paths and tools on the author's laptop. The authors argue that evals passing 70–90% of runs are more useful than ones passing 100%. Despite the title, the million monthly invocations are tracked by telemetry, not each evaluated. Beyond the warehouse case, ablation results come down to "a majority of cases", with no counts given.

The cost work is the most concrete part. Loading 100+ MCP tools (Model Context Protocol tool servers) put 50–70k tokens of tool definitions into context before the user typed anything. Uber moved those common flows into scripts called through a gateway and now blocks .mcp.json in skills. Running a tracing skill in a subagent on a cheaper model cut its cost per call 46%, while a deployment skill showed no drop in its first week. Finally, an always-on log-papercut skill lets agents file structured friction reports. Agents filed thousands in three months and hundreds have been fixed, including a deploy skill that passed seconds where the API expected milliseconds.

“In our experience, evals that pass 70%-90% of runs can be more useful than those that pass 100%.”

— Andrew Mager et al. on the post

Under the hood

  • Three tiers: Domain (one peer approval plus CI), Core (team-maintained, every change reviewed by the platform team), Always-on (~100 skills enabled for everyone).
  • aifx merges six config layers: company, team, repo, working directory, user, local override. Layers only add plugins, never remove them.
  • Cost per call = first session-cost snapshot after the call minus the last one before it, so other tool calls in that window are counted too.
  • Running a search skill's script at load time cut it from four turns to three and its mean cost by 32%. Notification turns were about a third of spend in the top 20 sessions.

Takeaway. Give agents an always-on skill for filing structured friction reports (what they tried, expected and got, and the fix); it surfaces silent failures such as unit mismatches and shared temp files.

Eight of twelve agent benchmarks fail correct work, Eugene Yan finds

The grader bugs run both ways: hidden tests reject valid solutions, and rubrics pass hallucinated ones. His fix is to measure reliability and reviewer attention instead of average pass rate and dollars.

Eugene Yan audited twelve public agent evals and found graders failing valid work in eight of them. Reviewers found 41 of 65 Terminal Bench 4.0 tasks graded on unstated requirements. Once those were made explicit, one model went from 63% to 89%. DeepSWE's hidden tests clash with tests the agent wrote itself, so the agents that check their own work get penalized. Errors run the other way too. On Harvey's legal benchmark, more than 60% of deliverables that passed every rubric item contained material hallucinations, because the judge never sees the source documents. One AutomationBench task passes any email that contains a "3" and a "4".

His prescriptions, some of which he admits are "vibes": report pass^k, where a task counts only if all k trials pass. Two agents that both average 70% can score 70% and 17% over five trials. He also wants cost counted in reviewer attention as well as tokens. GDPval found GPT-4o, at a tenth of GPT-5's cost per task, was slower than an expert working alone once review and redo time were added. And scores belong to a model-harness pair, not the model alone. On Terminal Bench 2.0, one model scored 57.8% on a neutral harness and 52.1% on its own provider's harness.

“Saving on token costs may be token-wise and attention-foolish”

— Eugene Yan on the post

Under the hood

  • AutomationBench: models falsely declared success in 72–91% of analyzed failures; a check treated "150,000" and "150000.0" as different values.
  • Terminal Bench Science: one run classified 99 of 100 stars correctly and scored zero under all-pass grading; 128 task-fix issues filed against 57 of the 70 tasks.
  • HealthBench Professional averages about two rubric criteria per task (original HealthBench: ~11); 47% of tasks have one positive criterion.
  • Laban et al.: models scored 39% lower in simulated multi-turn conversations than single-turn; few evals test multi-turn because simulating users adds noise.

Takeaway. Evaluate candidate models inside your own production harness over repeated trials, and audit transcripts that passed as closely as ones that failed.

Featured · arxiv.org · Nov 23 · HF Papers ▲17 · ★ 3 · 2 min

Most never-solved SWE-Gym tasks have tests that reject correct fixes

The common filter that drops never-solved tasks removes only the broken tasks that never produce a training signal. The broken tasks that do shape the policy stay in the set.

Yikai Zhang, Mai Xu, Yunbei Zhang, Qirui Jin, Kenan Li, Yuwen Jia, Jinwei Yao, Xiangyu Zhang et al. — AMD

In SWE-Gym, 74% of the tasks a 9B model never solves have a hidden test that rejects correct fixes (a false negative). Among tasks it sometimes solves, the figure is 20%. AMD and collaborators checked 2,265 tasks one assertion at a time with Claude and GPT judges. An error counted only when an executed "witness", a patch that follows the issue but differs from the reference fix, failed the test. The sharper finding is about GRPO, which learns from a task only when its samples get different rewards. Never-solved broken tasks get the same zero for every sample, so they supply just 0.9% of gradient-carrying groups and the usual drop-the-zeros filter removes errors that were doing little. Broken tasks that are sometimes solved still supply about a fifth of those groups. In one example, the rewarded samples were the ones that copied the upstream warning text word for word, text the issue never gave.

With Qwen3.5-9B trained on 512 tasks per set, matched for size and difficulty, the audited set beats the original set by 2.4 points on SWE-bench Verified and 2.7 on SWE-bench Pro, averaged over three seeds. The pass-rate-filtered set shows no gain on average. Treat this with care: on each benchmark taken alone, individual runs of the two sets overlap, there is only one model, training stops at 80 steps, and the LLM verdicts were spot-checked by humans on just 105 items. False positives (wrong patches that pass) were 26% of passing patches. New tests that catch a quarter of them had no detectable effect on held-out scores.

“A pass rate shows whether a task yields reward, not whether that reward is right, so the reward labels themselves must be checked.”

— Yikai Zhang et al. on the post

Under the hood

  • Repairs append a Requirements block to the issue without revealing the solution; this raised the base model's pass count by 2.1 of 8 on average. One sentence took moto-4846 from 0/8 to 7/8.
  • The never-solved vs sometimes-solved gap holds with only verdicts both model families confirm (68% vs 13%) and with PAIChecker's human labels (61% vs 21%).
  • The filtered set had the most gradient-carrying groups (70.8% vs 65.9% for the audited set), so more signal alone does not explain the audited set's gain.
  • Released: SWE-Gym-Verified (1,087 tasks, 184 repaired), every verdict with its executed evidence, the training sets and the audit pipeline, under Apache 2.0.

Takeaway. Audit the tests of partially solved RL tasks, where label errors actually steer gradients; zero-pass filters mostly discard tasks that were already contributing nothing.

Why PyTorch's KL divergence breaks when two distributions are close, and how to fix it

Clamping negative KL at zero, the usual advice, hides the symptom: most of the wrong values are still positive, and switching to FP64 doesn't fix them either.

For nearby distributions, KL (the Kullback–Leibler divergence) is tiny, roughly the square of their difference. PyTorch computes it by adding much larger terms that nearly cancel. Near FP32 rounding error (~6e-8), 86% of values are ≥1% wrong, and about 30% go negative at smaller divergences. Rerunning the same formulas in FP64 still leaves 7–51% wrong. Rewriting KL as sums of non-negative terms, computed from logits, fixes it at 2.4–5.9× GPU cost. HN's fluxem calls near-identical distributions contrived. Yet KL between cached decoding and a full forward pass, a gap that matters in RL fine-tuning, comes out more than 600% wrong.

Under the hood

  • Identical-start distillation: Adam scales a 5e-8 spurious gradient up to a full-size step, reaching 97.4% top-1 disagreement in FP16. The strict repair moved the student in none of 720 runs.
  • Ground truth from Arb interval arithmetic over 8.5M inputs, 18 closed forms plus F.kl_div; CPU and A100 error rates differ by at most 1.5 points.
  • Commenters say the paper reads as AI-written; the authors disclose using ChatGPT and Claude. A related report, PyTorch issue #80488, dates from 2022.

Takeaway. Compute KL penalties and distillation losses straight from logits, not from rounded log_softmax outputs. Fixing F.kl_div alone left student weights bit-identical to the official runs.

Catastrophic cancellation: why a tiny KL divergence comes out wrong, and how to compute it stably

KL penalties and distillation losses are often tiny, because the policy has barely moved from the reference model. That is exactly when the textbook formula KL(p||q) = Σ p_i (log p_i − log q_i) breaks. Write q_i = p_i(1+ε_i). Each term is then about −p_i·ε_i, which is first order in ε. Because both distributions sum to 1, these first-order terms cancel, and what remains is second order: KL ≈ ½ Σ p_i ε_i². You are subtracting large numbers to get a much smaller one. Each FP32 log-prob carries a rounding error of roughly 1e-7 times its size, and those errors do not cancel. When the true KL is close to that error level, the computed value can be off by 100% or come out negative.

A small example: p = (0.5, 0.5), q = (0.5001, 0.4999). The two terms are about −1.0e-4 and +1.0e-4, and the true KL is only about 2e-8. log 0.5 ≈ −0.693, and FP32 resolves numbers that size to only about 6e-8, so the rounding noise is as large as the answer. Clamping at zero hides the negative values but leaves the positive ones wrong. The fix is to change the algebra. Since Σq = Σp = 1, you can rewrite KL = Σ p_i (r_i − 1 − log r_i), where r_i = q_i/p_i. Every term is now ≥ 0, so nothing cancels. Compute d_i = log q_i − log p_i once, straight from the logits (logit difference minus log-sum-exp difference), and evaluate each term as expm1(d_i) − d_i, which is about d_i²/2 when d_i is small.

Costs: one extra exp per vocabulary entry, and you need both sets of logits instead of saved, rounded log_softmax outputs. In exchange the result can never be negative, and it stays accurate when the distributions are close. Moving to FP64 only pushes the problem further out, and the story found that FP64 still leaves 7–51% of values wrong. Use the non-negative form for RL KL penalties, on-policy distillation, and any monitoring of small drifts. Its single-sample version is the familiar low-variance 'k3' KL estimator.

Further reading: David Goldberg, "What Every Computer Scientist Should Know About Floating-Point Arithmetic" (ACM Computing Surveys, 1991); John Schulman, "Approximating KL Divergence" (2020 note)

Armin Ronacher makes the case for removing Rust's mutex poisoning

The feature is meant to stop code from reading half-updated state after a panic, but his examples show the usual lock().unwrap() turning one panic into a process that stays up and fails on every request.

In Rust, if a thread panics while holding a std::sync::Mutex, the lock is marked "poisoned" and every later lock() returns a PoisonError. The idea is to stop other code from seeing state that was halfway through an update. Ronacher's main point is that nobody handles it properly. Josh Triplett has said std has "never once" received a report of someone trying to recover. The common lock().unwrap() turns one panic into a slow outage. Thread pools, request handlers and tokio tasks survive the first panic, so the process stays up and every later lock call panics too. Neon had a staging safekeeper fail every timeline lookup this way. Mozilla's application-services saw PoisonError reach #5 in crash stats and switched to parking_lot, a third-party lock crate without poisoning.

The design has other problems. PoisonError holds the guard, so m.lock()? keeps the mutex locked for as long as the error exists, which has caused deadlocks. Recovering with into_inner() leaves the poison flag set, and there was no way to clear it until 1.77. Std's own internal locks ignore poisoning, and tokio strips it out. RefCell has the same broken-invariant risk and never poisons. He wants nonpoison locks as the default, with an opt-in Poison<T> wrapper for anyone who wants the old behaviour.

“In the entire history of the standard library, we have never once seen a single report of anyone attempting to recover from poison.”

— Josh Triplett on the post

Under the hood

  • The libs team is discussing making non-poisoning locks the default in the next edition (rust-lang/rust#149359).
  • One test that poisons a shared static makes every later test fail; this has hit cargo, deno, polars and rustc.
  • Inconsistent std behaviour: LazyLock poisons permanently, OnceLock never poisons, Mutex poisons but can be recovered.
  • He opposes the counter-proposal of a lock() that panics on poison: it fixes the held guard but leaves the slow outage as the only option.

Takeaway. Under unwinding, a bare lock().unwrap() takes down every later caller of that lock, so pick deliberately: panic = "abort" or a non-poisoning lock.

An offline "sleep" phase refines a model's context cache between uses

The claim is fewer in-context examples for the same adaptation, with no extra decode cost between refinements, but the evidence behind it isn't public yet.

Sangyun Lee, Zhang Enyan, Michael Xu, Hao Tang, Zinan Lin, Weijia Xu, Chris Quirk, Jianfeng Gao et al. — Carnegie Mellon University, Yale University, Microsoft Research

Agents that learn from what's in their context pay the full cost of that context on every call. A new paper from Carnegie Mellon, Yale and Microsoft Research (Jianfeng Gao and Chris Quirk among the authors) tries a different approach. It adds a sleep phase: an offline step that refines the model's context cache (the stored state built from the examples it has seen) between uses. The reported result is that the model adapts from fewer in-context examples, and token generation between refinements is no slower. That fits, since the extra compute happens offline and not during decoding.

That's all the paper's abstract-level framing gives. It doesn't say how big the gains are, which tasks were tested, what the baselines were, or how much the sleep step costs in compute. Without those numbers there's no way yet to judge it against plain long-context prompting or test-time fine-tuning. The idea is still worth watching for a memory engine: it treats consolidation as a scheduled background job on cached state, separate from the request path. Early interest is modest, with 19 votes and about 720 visits on alphaXiv in its first week.

Anthropic's repo posts a Lean-formalized claim that VP ≠ VNP over every field

This would separate the algebraic analogues of P and NP. The paper itself says it has not checked how the proof relates to relativization and algebrization, two known barriers to proofs like this.

Per-prompt teacher–verifier correlation turns sparse RLVR reward into dense distillation

The gain over fixed extrapolation is about one point, and roughly 65% of prompt groups never use the verifier signal at all.

Juntong Shi, Stefano Ermon, Jure Leskovec, Minkai Xu — Stanford University, Google DeepMind

For each prompt, VOPD (Stanford and Google DeepMind) computes one number: the correlation between verifier pass/fail and the teacher's summed implicit reward log(pT/pref) across the student's rollouts. That number scales an extra term over the whole vocabulary, added to the usual on-policy distillation loss. This is the same as distilling toward pT^(1+λc)·pref^(−λc), which extrapolates past the teacher where teacher and verifier agree and pulls back where they disagree. On Qwen3-4B same-size distillation, the average over eight math benchmarks rises from 64.71 (OPD) to 66.38, above ExOPD's 65.25 and the teacher's 64.16. The caveat: with 4 rollouts per prompt, about 65% of groups have zero reward variance and fall back to fixed ExOPD-style extrapolation.

Under the hood

  • Strong-to-weak (4B teacher → Qwen3-1.7B): VOPD averages 53.32, best on 6 of 8 benchmarks; still below the teacher.
  • Naive OPD+GRPO co-optimization gives only marginal gains over plain OPD; λ=0.25 was best, and larger values degrade AIME scores.
  • Needs teacher logits plus a frozen reference model (one extra forward pass per batch). Trained on DAPO-Math-17k with top-16 distillation, on 8×A100 per run.

arxiv.org · Nov 25 · 1 min

NVIDIA treats FSDP, DP, TP, SP and CP as one scheme, then schedules all-gathers per GEMM

The idea is simple: start each weight all-gather right before the matrix multiply that reads it, not once per Transformer block. The 2T-parameter showcase model is internal, and every baseline is NVIDIA's own.

Shiqing Fan, Deepak Narayanan, Jimmy Zhang, Jiangfei Duan, Prajwal Singhania, Haoran Zhang, Wanying Wang, Philip Monk et al.

An internal 2T-parameter mixture-of-experts model ran at 13.0 model EFLOP/s on 12,288 GB300 GPUs, with 98% weak-scaling efficiency from 4,096 GPUs. The paper's framing: for linear layers, DP, TP, SP, CP and FSDP are all one scheme. Weights and tokens are split across GPUs, and either input to a matrix multiply (GEMM) can be all-gathered just before use. FSDP-style hooks fetch a whole block's weights at once. Fetching per GEMM means each GEMM waits only for its own weights. The result is 1.05–1.55× Megatron-FSDP and 1.27–1.31× a tuned pipeline-parallel recipe on a DeepSeek-V4-Pro proxy. The code is in Megatron-LM.

Under the hood

  • Expert-weight all-gathers are issued one MoE block ahead because they cross NVLink domains. Ablations on 256 GPUs: 4.6–13.9%, 2.8–18.7% and 3.5–9.0% gains from the three scheduling policies.
  • Weight sharding costs 1.5× the communication volume of data parallelism. Shards are stored as MXFP8 or NVFP4, padded to 32 or 16 rows, so all-gathers move quantized weights without re-quantizing.
  • Ran the full 2T model on 1M-token sequences on 512 GPUs: each sequence spans two 64-GPU NVLink domains, so weight all-gathers stay on NVLink.
