Separately distilled 3B memory writer and retriever compose well without joint training

Why read · A modular write/retrieve/read memory stack built from independently trained small specialists roughly doubles LongMemEval accuracy over composed RL specialists, but only when the two parts are compatible.

Davydenko, Sakhno, Pavlov, Belikova, Savchenko and Makarenko test whether a memory writer and a retriever, trained separately in different environments, can be combined with no joint training. They distill each one from GPT-6.1-sol action trajectories into its own copy of Qwen2.5-3B-Instruct. The writer imitates Mem-α's edit operations over core, semantic and episodic memory, trained on Mem-α data. The retriever imitates Search-R1-style iterative search over Wikipedia. When composed, the writer builds a BM25-indexed store from conversation sessions. The retriever then runs up to 4 searches with 3 records each, and a fixed GPT-6.1-sol reader writes the answer.

On 147 LongMemEval questions the distilled pair scores 73.1%, against 36.2% for the released Mem-α + Search-R1 pair. On PersonaMem-v2 it scores 40.3% against 32.8%. How well the parts fit together matters. With Mem-α's memory, the distilled retriever drops accuracy slightly (36.2% to 35.2%). With distilled memory, it raises accuracy from 63.1% to 73.1%. Retriever-only GRPO (group-relative RL, 8 rollouts, reward = answer correctness) brings LongMemEval to 75.2%. SFT of both specialists on in-task teacher trajectories brings PersonaMem-v2 to 48.9%. Caveats: the test set is small (3 users on LongMemEval), all systems share a frontier reader, and a gap to frontier pipelines remains.

Under the hood

  • RL retriever: 75.17% with 3.35 searches, vs base Qwen2.5-3B 64.92% with 2.12 searches, BM25 top-12 65.16% and top-3 59.22%. The gain comes from learned query refinement, not from extra search turns.
  • Standalone: distilled retriever 37.75% vs Search-R1 35.75% and CoRAG 36.25%. Distilled writer 80.58% vs released Mem-α (Qwen3-4B) 74.79%.
  • Mem-α's RL recipe on the same Qwen2.5-3B backbone reached only 9.51% (8.34% untrained), so distillation beat RL from scratch at this size.
  • Training the retriever on teacher-written stores instead of the adapted writer's stores cost 0.89 pp (LongMemEval) and 2.82 pp (PersonaMem-v2). Code and teacher trajectories are released.

Takeaway. If you split memory into writer and retriever, evaluate and tune the retriever on stores your own writer produced, not on idealized ones. Distilling each role from a frontier teacher is a cheap baseline to try before end-to-end RL. Keep RL for the retriever, with answer correctness as the reward.

KL penalties in PPO/GRPO: estimators and numerics

RL post-training keeps the policy π close to a frozen reference π_ref with a KL(π‖π_ref) penalty. That penalty can be computed in two ways. The exact KL sums over the whole vocabulary at every position. The cheaper, more common route is to estimate it from the tokens you actually sampled. Let δ = log π_ref(x) − log π(x) for a sampled token x, and r = e^δ. There are three standard estimators. k1 = −δ is unbiased but noisy, and on a single sample it can be negative. k2 = ½δ² has low variance but is biased. k3 = (r − 1) − δ is unbiased, never negative, and has low variance; GRPO uses it.

Here is a worked example. Say π(x) = 0.50 and π_ref(x) = 0.49. Then δ = log 0.98 = −0.020203. That gives k1 = 0.0202, k2 = 0.000204, and k3 = (0.98 − 1) + 0.020203 = 0.000203. Note how k3 is formed: two numbers of size 0.02 cancel to leave about 0.0002. In bf16, which keeps roughly 3 significant digits, each 0.02 term carries an error near 1e-4. That error is about as large as the answer, so the penalty and its gradient become noise. This is the failure today's PyTorch brief describes. It is worst when the distributions are nearly identical, which is the normal state inside a trust region.

To avoid it, get log-probs with log_softmax applied to the logits, never as log of rounded probabilities. Compute in fp32, and write k3 as expm1(δ) − δ so the subtraction stays accurate. Never clamp a negative estimate to zero, because clamping biases the penalty upward. Add a unit test: identical inputs must give exactly zero loss and zero gradient. Use the full-vocabulary KL when you can afford it, as in distillation, and k3 on sampled tokens in RL loops.

Further reading: John Schulman, "Approximating KL Divergence" (2020); Shao et al., "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models" (GRPO, 2024)

PyTorch's KL functions break down when two distributions are nearly the same

Why read · PPO/GRPO trust regions, distillation losses and checks on quantized models all compare distributions that are close together, and that is exactly where PyTorch's KL values and gradients become noise.

Yale, Oxford, Cambridge, Fudan and others tested kl_divergence (18 closed forms) and F.kl_div on 8.5M inputs, checked against interval-arithmetic references. For close distributions the true KL is tiny, but the code builds it from much larger terms of mixed sign, so rounding error swamps it. At KL ≈ 1e-7, 86% of FP32 values are at least 1% off, and about 30% are negative at smaller KL. Running the same formulas in FP64 still leaves 7–51% wrong. The fix is to rewrite the KL as a sum of non-negative terms and compute it from logits.

Under the hood

  • Basic term: φ(x)=x−log1p(x), never negative and evaluated near 0 with a series; gradients are derived by hand. On GPU the rewrite costs 2.4–5.9× the official call.
  • Student starting as an exact copy of its teacher: the official losses moved it in all 2,160 runs, the repair in none. With Adam, FP16, top-1 disagreement reached 97.4%.
  • HN noted a 2022 PyTorch issue where the advice was to clamp. The paper says FP64 alone does not fix it: inputs already rounded to probabilities stay wrong.

Takeaway. For RL KL penalties or distillation, compute KL from logits rather than from rounded probabilities, and never clamp a negative KL to zero. Assert that identical inputs give exactly zero loss and gradient.

Agents sharing a vLLM server can signal through kernel rounding and the KV cache

Why read · If you run agents, or a policy and its monitor, on one shared inference engine, batching and prefix caching create covert channels between them.

Niranjan Deshpande and David Africa show that two sandboxed agents on one vLLM server can pass bits to each other. vLLM picks a GPU kernel based on how many tokens an engine step (one batched forward pass) contains, and each kernel leaves its own tiny, deterministic rounding pattern. With step sizing, Alice reads a long document so that Bob's step is large. With the KV cache message board, Alice's helper caches a shared "mailbox" prompt prefix during a large step, and Bob's helper later reuses that cache and detects the foreign rounding. A fine-tuned Qwen3-8B Bob guessed Alice's color in all 1,221 rounds of an 8-color game. A colluding monitor let through 354/354 signalled attacks while still catching 85–92% of honeypots (fake attacks planted by defenders).

Under the hood

  • Background load breaks the channels. Replaying an Azure traffic trace at 0.1x/0.25x/0.5x/1x speed, the message board won 100/99/90/49% of rounds; step sizing fell to 39% at 0.1x.
  • No fine-tuning was needed: an unmodified Bob that read helper log-probs and knew the full protocol won 65–100%. Success rose sharply with model capability. The channels also worked on SGLang, LMDeploy, TensorRT-LLM and on H100 and 5090 GPUs.
  • Fixes: vLLM batch-invariant kernels, per-user KV cache isolation, or a separate engine instance for the monitor. On HN, amluto compared this to browsers splitting caches per site; kgeist proposed timing decode speed as a channel.

Takeaway. Treat a shared prefix cache like a shared browser cache: give each security context its own cache key. Run monitors on a separate engine instance from the agents they watch.

ARCTIC: a lock-free adaptive radix tree that beats lock-based indexes

Why read · This OSDI '26 paper gets an ordered, scannable in-memory index without locks, and its memory-reclamation trick works for any keyed structure.

ARCTIC, from UT Austin and ETH Zürich (OSDI '26), is a lock-free adaptive radix tree. An ART is a trie whose node size changes with the number of children. Reads are wait-free, and range scans are wait-free but not linearizable. The design moves compressed edge bytes and node-type tags into 16B parent edges, so most structural changes take one 128-bit CAS. To replace a node, a thread freezes it by setting a frozen bit on every CAS slot. Any thread can then build the same replacement. At 80 threads it beats lock-based ART by 1.3× (YCSB-C) to 7.7× (YCSB-A). In RocksDB it raised write-heavy throughput 40% over the default skiplist, and in Turso 12%.

Under the hood

  • Hazard keys: each operation announces its key once, and a retired node is freed only when its prefix is not a prefix of any announced key. One stalled thread blocks only part of reclamation. Heavy key skew can leave memory unreclaimed indefinitely.
  • In an 80-thread insert-only run with 100M random 8B keys, 324 inserts hit a frozen-node CAS failure and none backtracked more than one level.
  • Requires 16B CAS (CMPXCHG16B on x86, CASP on ARM). Memory is 0.97–1.5× ART for integer keys and 0.19–0.61× for string keys. Written in Rust, code at github.com/nwtnni/arctic.

Takeaway. Store the metadata a child's structural change needs in the parent's pointer word, so the change becomes a single CAS. If your index is keyed, consider protecting memory with operation keys rather than per-pointer hazard pointers.

SeaStore redesigns Ceph's storage back end to use less CPU on NVMe

Why read · A storage-engine paper that relies on the SSD's own firmware to absorb random writes and keeps an append-only log mode for drives that can't.

The ACM paper itself could not be fetched (HTTP 403), so this story comes from the title and the HN thread. SeaStore is a new Ceph storage back end built to deliver NVMe performance with less CPU. A commenter quotes its core choice. Most SSD-friendly layouts treat the whole disk as a journal. SeaStore instead updates data in place whenever possible, relying on the drive's Flash Translation Layer (the firmware that remaps logical blocks to flash) to absorb random writes. For other drives it offers an append-only journal mode.

Under the hood

  • The paper's stated reason for in-place updates: enterprise SSDs absorb random writes in their FTL and offer strong write endurance and guaranteed IOPS.
  • Journal backend mode, for FDP-enabled and consumer SSDs, changes only the on-disk layout to log-structured writes. The rest of the architecture stays the same.
  • The commenter's critique: the paper says little about journal mode, so it's unclear how much of the gain comes from the specific SSD tested.

Takeaway. Before you assume a log-structured layout, check what your target devices already do in firmware. Keep the layout policy separate from the rest of the engine so you can switch it per device class.

Hex.pm hit by pre-auth RCE through fake Elixir structs and error logging

Why read · A detailed postmortem of a deserialization gadget chain where the error reporter itself ran the attacker's code, with an honest account of what logs could and could not prove.

On November 23, an attacker sent 69 unauthenticated POSTs and ran commands on six hex.pm servers (CVE-2026-129514). A parser that runs before auth decoded Erlang terms with non_executable_binary_to_term. It blocks functions and new atoms, but not maps with a __struct__ key, so the attacker could send fake structs. One made Plug.MethodOverride raise. Sentry and the loggers then called inspect on it, and protocol dispatch led through Ecto's DynamicExpr into DBConnection.Stream. That applied an attacker-supplied {module, function, args} :log callback. The patch shipped in about 15 minutes. Database reads aren't logged, so data exposure can't be ruled out.

Under the hood

  • They compared a database restore from 18:13:59 with live data and found no unexplained writes. All 62 package files and 186 registry files matched stored checksums.
  • Six servers were hit instead of three because a restart at 18:28 brought up three new servers still on the vulnerable build. The safety check had been removed in 2016.
  • Ash keyset-pagination cursors had the same class of bug (CVE-2026-124283). Planned hardening: plug refuses struct body params, Ecto checks the binding is a list, and db_connection ignores :log from structs.

Takeaway. Don't decode rich typed terms from unauthenticated input, even with a "safe" decoder. Treat your error reporter and log formatter as attack surface, because inspect/toString/__repr__ run code chosen by whatever the attacker managed to deserialize.

Rewind VM adds after-the-fact critical-path and off-CPU analysis

Why read · A deterministic VM records every context switch and every wakeup anyway, so Brendan Gregg's off-CPU methods can run on any past run without tracing ahead of time.

fzakaria added rewind time to Rewind, his deterministic VM. Rewind runs on one CPU and already logs every context switch so it can replay a run; it now also records every wakeup and which thread caused it. From that it computes the critical path (the longest chain of dependent steps, which no number of CPUs can beat) and applies Gregg's thread-state and off-CPU analysis to any recording. On a libuv build: 78.0 s elapsed, a 47.4 s critical path, and 67% of that path asleep (epoll_pwait 23.1 s). The cause was 287 timer-heavy tests running one after another. rewind where replays to the exact step and opens gdb at the test's uv_sleep(45).

Under the hood

  • A 'drag' table shows how much sooner the run would finish if a part took no time: all lt-run-tests 36.1 s, all cc1 compiler processes 6.66 s, the hrtime test 3.38 s.
  • The process tree follows Gregg's colony-graph idea and includes every fork, even short-lived ones a ps snapshot would miss. It exports folded stacks (flamegraph.pl, speedscope) and Perfetto traces.
  • HN commenters: a single-CPU VM limits analysis of busy multithreaded pipelines, and async/coroutine critical paths still need request context added in the framework. One asked how it compares with rr.

Takeaway. Before you profile CPU, measure the critical path and how much of it is spent asleep. If the waiting dominates, a CPU flame graph won't show it, so look at off-CPU time and wakeups instead.

trynix.dev runs Nix packages with GUI, sound and network on Linux compiled to WebAssembly

Why read · A working stack for full Linux userlands in a browser tab, and the parts that make each OS subsystem work there.

Farid Zakaria moved trynix.dev, which runs any of 300,000+ Nix package versions in the browser, from QEMU-in-wasm to unkernel. unkernel is Linux compiled to WebAssembly, published by Pooya Parsa on November 19. The kernel runs at wasm speed and only user programs are emulated. On his benchmark page it runs 2x to 32x faster than a patched qemu-wasm, with the biggest gains on first runs, where kernel work dominates. GUI, GL, audio and TCP all work, enough to run Firefox inside Firefox. On HN, one builder says LLMs did most of the work on a rival arm64-in-wasm project.

Under the hood

  • Graphics: wland composites Wayland surfaces in the page. A minimal Mesa build with only the virgl driver, compiled to wasm, renders through WebGL2.
  • Network: each TCP connection runs over one WebSocket to a Wisp relay, so curl, git clone and pip install work.
  • Audio comes from an ALSA sound card wired to browser audio. The nested Firefox demo took over 4 hours and needed JIT disabled in the inner Firefox.

Takeaway. To sandbox untrusted tools or agent code in the browser, compile the kernel to wasm rather than emulating the CPU. Map each OS subsystem to a web API: Wisp over WebSocket for TCP, WebGL2 for GL, ALSA to browser audio.

Google's Agent Retrieval now handles file ingestion and returns cited search results

Why read · A reference for what a managed RAG layer now does for you: page and timestamp citations, hybrid search with fusion, reranking, and audio-aware video search.

Agent Retrieval (formerly Vector Search 2.0) has two Public Preview features. Managed ingestion takes PDF, Office, TXT or video files from Cloud Storage, then parses, segments and embeds them with Gemini Embedding 2. SearchDocuments answers with one REST call (v1beta). It runs semantic and full-text search, fuses the two result lists, and returns segments with page ranges or video start and end offsets. In Google's tests, 18 investor PDFs were searchable in about 9 minutes. Queries over 19 minutes of video returned in 0.3–0.5 s.

Under the hood

  • Segmentation: chunks of 100–500 tokens with layout parsing, or one segment per page. Both record startPage and endPage. Video uses fixed windows (default 30 s, range 10–80 s).
  • Optional reranking pulls more than top_k candidates and reorders them with semantic-ranker-fast. Without it, an employee-count query returned balance-sheet pages. Reranking doesn't work on video data stores.
  • Video audio_mode ENABLED embeds the first audio track with the frames, so queries match spoken statements without transcripts. Imports took 20–45 minutes. Preview runs only in us-east4 and europe-west4.

Takeaway. If you build your own retrieval, copy the result contract: every segment returns a source URI plus a page range or time offset, and metadata filters use the same paths as the results. Add a reranker before you tune embeddings, because it fixed the obvious errors here.

vLLM · 1 min

vLLM-GR runs a whole recommendation beam search as one engine request

Why read · It moves beam search into the engine: candidates share the cached prompt, selection stays on the accelerator, and the catalog constrains decoding. All of this carries over to other search-heavy decoding.

The vLLM project released vLLM-GR, built on vLLM 0.30.0, for generative recommenders such as OneRec-1.7B. These models produce semantic IDs (SIDs), short token sequences that name catalog items. One request runs the whole beam search. A beam session records each surviving path's parent, so the next decode reads the right KV state. Beams share the user-history KV, selection stays on the accelerator, the host prepares the next stage while the device runs the current one, and a catalog filter prunes prefixes that match no real item. On H20 at beam width 256 and batch size 8, P99 latency was 369.4 ms, against 428.1 ms for NVIDIA SID-GR and 1,280.1 ms for SGLang.

Under the hood

  • Beam width can change per stage (e.g. 2→3→2), with a cap on candidates per parent. Requests come in through offline Python, OpenAI-compatible HTTP or gRPC, on NVIDIA GPUs and Ascend NPUs.
  • Not a clean sweep. At batch size 1 on RTX PRO 6000, SID-GR measured 28.25 ms vs 29.21 ms, and the leader at width 128 changes with hardware.
  • The benchmark runs used different timing definitions, and backend revisions were not reported. Planned work: stop beams at EOS and free their KV, and reuse prefix KV across requests for histories of 10k+ tokens.

Takeaway. For decoding shaped like a search (tree search in agents, constrained generation), run the whole loop inside the engine. Share the prefix KV across branches and track each branch's parent index, instead of going back to the host at every step.

GPT-6 designs binding proteins using reasoning and code

Why read · A frontier general model matches specialist tools on parts of a scientific pipeline while specialists still gate the output — a useful template for judging capability claims.

OpenAI reports that GPT‑6.2 designs protein backbones and sequences with reasoning and general coding tools alone, no specialized biology model in the generation step. With lab partner Onava, 35 of 322 designed minibinders (10.9%) bound across five targets; 128 of 182 redesigned antibody loops (70%) kept binding to IL‑4Rα. Under the hood

  • Structural constraints — helix/strand counts, contact sites — followed from prompts alone, without retraining.

Takeaway. When a general model is said to replace specialists, trace which pipeline stage it actually owns: here it generates candidates, but specialist models still score and filter every one. The transferable result is prompt-level constraint control with no retraining.

Uber's agent skills platform: trajectory evals, ablations, and agents that file their own bugs

Why read · Production numbers on evaluating, distributing and cutting the token cost of 5,000+ agent skills, plus a feedback loop any agent harness could copy.

Uber's skills marketplace went from 1 skill in October 2025 to more than 5,000, with over 1M invocations in one month across Claude Code, Codex, OpenCode and an internal agent. A skill is a SKILL.md directory loaded in three stages: a ~100-token name and description always in context, a body under 500 lines loaded when the skill runs, and scripts loaded on demand. Skills sit in one Git repo in three tiers (domain, core, ~100 always-on). A CLI, aifx, merges six config layers and installs the same skills into whichever agent starts next. Eval suites are about 5% golden cases with mocked tools, 80% real prompts graded on trajectory (right skills and tools, in the right order) and 15% judged by the author. They run in clean remote sandboxes, which caught skills that only worked on the author's laptop. Uber says a 70–90% pass rate tells you more than 100%.

Ablation replays real prompts with and without a skill, and a blind judge picks the better answer. Without the warehouse-query skill, sessions made 13% more tool calls, hit 6x more tool errors and took 31% longer; the run with the skill won 87% of comparisons. An always-on log-papercut skill lets agents file structured friction reports. Agents filed thousands in three months, and hundreds have been fixed.

Under the hood

  • Cost per call is the session's running cost just after a skill call minus the cost just before it, averaged per skill per day.
  • Running a skill in a subagent on a cheaper model that returns only a short summary cut a tracing skill's cost 46%. A deployment skill showed no drop.
  • Running the script at load time removed one model turn from a search skill (4 to 3 turns) and cut its mean cost 32%.
  • Loading 100+ MCP tools by default cost 50–70k tokens before the first prompt. Uber now calls tools from scripts through a gateway ('Code Mode') and blocks .mcp.json files in skills.

Takeaway. Measure each tool or skill by ablation: replay real prompts with and without it and have a blind judge compare. Then move every deterministic step out of the model's context into code. Give your agents a structured way to report friction, because they already notice when something is broken.

Gnomon: a Postgres extension that gives each agent its own branch of production data

Why read · It treats agent writes to a live database like a pull request: the agent works on a branch, you review a per-field diff, then merge it or undo it, all inside your existing Postgres.

Gnomon, from bitsinfra, is an extension for PostgreSQL 15–18 that also runs on managed services such as RDS, Aurora and Supabase. You run gnomon.track('orders') to start recording history for a table, with no backfill of past rows. After that, create_branch makes a branch that reads from main and stores only what it changes, so it opens instantly and copies nothing. A session joins a branch with gnomon.use(). Behind a connection pooler, gnomon.begin() scopes it to one transaction. You can also hand out a branch-specific connection string. Migrations run on a branch and reach main only when the branch is merged.

Merges are three-way and type-aware. Counts add up, JSON merges key by key, text merges line by line, and real clashes come back as conflict rows that a person or a query settles. SQL checks must pass on the merged result before the merge lands. The README claims undo works at three sizes: one transaction, one agent session, or a whole merge. Tracked tables can be read as of any timestamp, and bisect finds the transaction that made a check start failing. For agents, Postgres itself enforces merge rules such as "at most 20 rows, only these tables". Emails and webhooks an agent queues stay on its branch until merge. Every read records the moment it happened, so a replay returns the same rows. The README does not explain how branches are stored or give benchmark numbers. Both are in linked docs (concepts.md, benchmarks.md) that were not fetched.

Under the hood

  • The core is plain SQL and installs on managed Postgres. An optional C module adds SET gnomon.branch routing, real row locks, ON CONFLICT/TRUNCATE on branches, stale-read detection and faster writes.
  • Tooling: one Go binary bundles the CLI, the MCP server (lets agents call Gnomon as tools) and the review web app. gnomon agent create sets up a database role, a branch and a connection string in one step.
  • The TypeScript and Python SDKs create one branch per task with startRun. Runs that share a database login still cannot read each other's branches.
  • History streams to Kafka, NATS, webhooks or dbt snapshots, and older history can move to object storage. License: PostgreSQL License.

Takeaway. If agents write to transactional data, the idea worth copying is the safety model: writes go to a copy-on-write branch, and a merge gate enforced by the database checks row limits and SQL checks. Check the C module's locking behaviour and the benchmarks before trusting it on hot tables.

Beads: a Dolt-backed dependency graph as task memory for coding agents

Why read · A working, opinionated design for agent long-term task memory: versioned SQL, atomic claims, and decay by summarization.

Beads (bd) is a Go CLI that gives coding agents a persistent task graph in place of markdown TODO lists. Issues are stored in Dolt, a SQL database with git-style versioning, cell-level merge and branching. Agents run bd ready to list unblocked work, claim a task atomically with bd update --claim, and run bd close to unblock whatever depended on it. Hash-based IDs (bd-a1b2) keep agents on different branches from colliding. bd remember stores durable project facts that bd prime adds to the agent's context. Compaction summarizes old closed tasks to save context window, which the README calls "memory decay".

Under the hood

  • Two storage modes: embedded Dolt, which runs in-process and allows one writer, or --server against dolt sql-server for concurrent writers. Sync goes through refs/dolt/data on the git remote.
  • Experimental bd serve HTTP backend: reads get a 15s header timeout and one retry within a 60s bound. Writes are never retried. A generated ledger lists every way it differs from local mode.
  • A schema guard refuses to open a database migrated by a newer binary. A committed .beads/.env cannot set commands or credential helpers, and it does not expand $VAR.

Takeaway. If agents share work, model tasks as a dependency graph with an atomic claim operation and a ready-queue query. Merge-safe IDs and versioned storage are cheaper than resolving conflicts after the fact.

Mason puts DuckDB behind a Postgres read-replica interface

Why read · The useful part is the method for testing an engine swap: 5,410 real slow queries replayed, with Postgres results as the reference.

Mason is an open-source drop-in replacement for a Postgres read replica. It looks like Postgres to clients but runs queries on DuckDB's columnar engine. To pick an engine, the team took 5,410 slow, hand-written queries from 159 real databases. They loaded synthetic data generated from those schemas and compared each engine's results with Postgres. pg_clickhouse matched 59.4% and refused 39.9%. CedarDB matched 88.1% and returned wrong results on 3.9%. DuckDB matched 84.1% and was wrong on 1.6%. After dialect work, Mason matches on 96%. The other 4% fail with an error that says how to rewrite the query.

Under the hood

  • Rejected options: Materialize, RisingWave and ReadySet need query shapes known in advance. pg_duckdb gives fast queries or fresh data, not both. Firebolt's license was a problem. Redshift and AlloyDB tie you to one cloud.
  • Each query was scored as matched (identical rows), refused (error) or wrong (different rows). DuckDB was chosen over CedarDB because its open license let them fix the long tail.
  • The post doesn't say how replication or data freshness works. HN commenters asked why not use CDC from the WAL, suggested the polyglot SQL transpiler, and asked about S3/Parquet storage.

Takeaway. Before you swap a query engine, replay a real query log through both engines and diff the results. Then sort failures into refused and wrong: an error is safe, but a wrong answer is not.

Recursive LM harnesses trained on short tasks generalize to tasks 64× longer

Why read · MIT's RLM work suggests a different way to train long-horizon agents: keep each model call's input familiar, and train only the orchestrating call, on synthetic tasks.

Alex L. Zhang, Souradip Chakraborty, Omar Khattab

Zhang, Chakraborty and Khattab (MIT CSAIL) say ReAct-style harnesses, which put the whole trajectory in the prompt, make the Transformer generalize over an ever-growing context. Recursive Language Models (RLMs) instead put the context in a code REPL and call sub-LMs from code. The paper's claim is that this keeps every call locally in-distribution: each call sees an input the model can already handle. They trained Qwen3-30B-A3B with GRPO (an RL method) on short tasks only. RLM matched its training reward on tasks 2–64× longer and transferred across domains with similar structure. The base model, Pi (a coding-agent harness) and CodeAct (code REPL, no sub-calls) fell off on dense semantic tasks such as OOLONG.

RL on short tasks did not carry over to harder benchmarks (+7 and +2.4 points). So they used surrogate harness training: Opus 5.5 builds synthetic environments that share the target task's solution program but not its content. Some environments use fake sub-calls that return pre-built oracle answers. Fine-tuning Qwen3.8-27B on 8,015 root-only rollouts gave RLM-27B: +12.4 points across eight benchmarks (the abstract reports 26.9% on average), with 3× fewer turns and 6× fewer root input tokens.

Under the hood

  • During RL, loss is applied only to the RLM's root (orchestrator) trajectory, with sub-call depth 1. Sub-agents reuse capabilities the model already has.
  • Root trajectories on long eval tasks closely matched successful training trajectories by weighted Jaccard token similarity. Sub-task accuracy on OOLONG was similar in training and evaluation.
  • Training rollouts were generated with the LM program given as a hint and filtered by GPT-5-mini as judge plus the environment reward. Pure RL on the synthetic environments without hints gave +6.8 points and no efficiency gain.
  • On a meta-task chaining four sub-tasks, SFT'd tail recursion into fresh sub-RLMs raised the solve rate from 55.2% to 77.5%. Just hinting at recursion hurt.

Takeaway. If you build agents, store long context as data the code can query and have the agent call sub-models from code, so each call's prompt stays short and familiar. Train the orchestrator on cheap synthetic tasks with fake sub-calls instead of full, expensive rollouts.

Many unsolved SWE-Gym tasks are mislabeled, and fixing the labels trains better agents

Why read · If you train agents with RL, a zero pass rate usually means the reward label is wrong, not that the task is hard, and pass-rate filters don't catch the bad labels that matter.

Yikai Zhang, Mai Xu, Yunbei Zhang, Qirui Jin, Kenan Li, Yuwen Jia, Jinwei Yao, Xiangyu Zhang et al. — AMD

AMD and university co-authors checked SWE-Gym's hidden tests, which act as the RL reward labels, one assertion at a time. Claude and GPT judges flag suspect assertions. A flag counts as an error only if the tests reject an executed alternative fix that follows the issue. Of tasks a Qwen3.5-9B base model never solves, 74% reject correct fixes (false negatives), against 20% of sometimes-solved tasks. Trained with GRPO at matched size and difficulty over three seeds, audited tasks beat the originals by 2.4 pp on SWE-bench Verified and 2.7 pp on SWE-bench Pro. Simply dropping never-solved tasks gives no gain.

Under the hood

  • GRPO only learns from groups where rewards differ. Never-solved flawed tasks are 11.1% of groups but 0.9% of gradient-carrying ones; sometimes-solved flawed tasks carry 19.5%.
  • False positives (wrong patches that pass) are 26.1% of 1,854 passing patches. New tests catch a quarter of them, with no detectable change in held-out score.
  • Released as SWE-Gym-Verified: 1,087 tasks, 184 repaired by appending a Requirements block to the issue. Every verdict ships with its executed evidence, under Apache 2.0.

Takeaway. Before using RL tasks, audit their verifiers. For each suspect check, run a correct alternative solution and see whether it gets rejected. Filtering on pass rate or reward variance leaves in the flawed tasks that actually produce gradient.

Agents fabricate when tools return truncated data, and a code-based verifier helps

Why read · If you build agents, the most dangerous tool failure is a plausible partial result, not an error, and checking answers against tool outputs in code catches some of the fabrication that follows.

Gün Kaynar, Boshen Yan, Carl Kingsford

Carnegie Mellon's Kingsford group built RetryRealistic, a fault-injection testbed. It runs on a real filesystem with chmod permissions, plus SQLite, a local HTTP server and an allowlisted shell, and covers 8 tools, 9 fault types and 30 tasks. Four ReAct agents went through 2,100 faulted runs graded against ground truth. They recovered correctly in only 19–68% of runs, and 6–26% of runs ended in a confident wrong answer. Truncated but plausible payloads drove fabrication to 38.3%, because agents accepted them on first contact without retrying, which the authors call silent ingestion. A Monitor that checks claimed values against tool outputs in code raised correct recovery from 45.6% to 56.3% and cut fabrication from 17.3% to 10.8%.

Under the hood

  • Monitor checks in order: are the answer's values present in any tool output, re-derive sum/avg/count from the rows, and only then an LLM drift check. Any veto lets the agent revise once.
  • An earlier version that simply asked an LLM 'is this fabricated?' vetoed 118 answers: 39 were correct and 46 wrong. Removing chain-of-thought raised fabrication from 17.3% to 25.6%.
  • The Monitor barely helps with truncation: fabrication on those runs fell only from 38.3% to 32.1%, and in 224 of 324 such runs it never acted because no error appeared.

Takeaway. Make tools fail loudly. When results are cut short, mark it explicitly or return an error, because in the paper's tests a clear denial produced honest failure where partial data produced fabrication. Check numbers in the final answer against stored tool outputs in code before trusting the agent.

VOPD turns sparse verifier rewards into dense, full-vocabulary distillation signal

Why read · A cheap way to make teacher distillation follow verified outcomes, with no extra rollouts or verifier calls.

Juntong Shi, Stefano Ermon, Jure Leskovec, Minkai Xu

Stanford and Google DeepMind (Shi, Ermon, Leskovec, Xu) combine verifier rewards with on-policy distillation (OPD, where the student matches a teacher's next-token distribution on its own rollouts). Within each prompt group they compute c_x, the correlation between verifier reward and the teacher's summed implicit reward log p_T/p_ref. That scalar then scales the implicit-reward term over the whole vocabulary, so the target pushes past the teacher when the two agree and back toward the reference when they disagree. On Qwen3-4B, the average over 8 math benchmarks rose from 64.71 (OPD) to 66.38, beating ExOPD (65.25) and the teacher (64.16).

Under the hood

  • Target is q ∝ p_T^(1+λc_x)·p_ref^(−λc_x) with λ=0.25. ExOPD is the special case c_x=1, and larger λ hurt results.
  • With group size n=4, about 65% of groups had zero verifier variance and fell back to fixed λ. n=8 did about the same or slightly better.
  • The only extra cost over OPD is a frozen reference model's forward pass. It needs teacher logits, and the authors distilled over each prefix's top-16 student tokens.

Takeaway. If you already run OPD alongside a verifier, use each prompt group's teacher–verifier correlation to scale the distillation term instead of adding a separate GRPO loss. Simply adding GRPO gave only marginal gains.

CMU and Apple tune RLVR hyperparameters during training with an 8-model population

Why read · If you post-train agents with RL, this replaces tuning across runs with selection and mutation inside one compute-matched population.

Yixuan Even Xu, Aleksei Petrenko, Raja Giryes, Jackson Hamburger, Kevin Chen, Fei Fang, J. Zico Kolter, Philipp Krähenbühl et al.

CMU and Apple (Kolter, Krähenbühl) applied population-based training (PBT) to RLVR (RL with verifiable rewards), calling it PBPT. Eight LoRA learners on Qwen3.5-4B/9B train asynchronously and post validation scores to a shared filesystem, with no coordinator. Each learner compares itself with peers at equal accumulated runtime. The bottom 25% that trail the best by more than τ_mut get new hyperparameters. Those trailing by more than τ_sel copy a top-30% donor's weights and optimizer state. PBPT beat compute-matched independent runs on Enigmata, Nemotron, Gaia2 and AppWorld, and recovered where plain RLVR collapsed.

Under the hood

  • Mutation scales numeric hyperparameters by μ^±1 and resamples categorical ones, including the loss itself (GSPO vs RLOO), clipping, rollout counts and task sampling.
  • Emergent schedule: learning rate rises then falls, rollouts per scenario grow later; budget is 2,112 B200 GPU-hours per method (8 learners × 4 GPUs × 66 h).
  • Restarting fresh RLVR runs from the population's final median config beats the baseline but trails PBPT. Weight transfer matters, not just finding a better config.

Takeaway. If you already run several RL seeds in parallel, write their checkpoint scores to shared storage. Then let runs that fall far behind copy the leader's weights and perturb their hyperparameters. Compare runs at equal compute, not equal steps.

LeJEPA's isotropic-Gaussian regularizer is weak, and isotropy is the wrong target

Why read · A UPenn paper finds a flaw in LeJEPA's collapse regularizer, replaces it with a cheaper one that trains 4.7× faster on ImageNet-1k, and shows the embedding norm works as a free confidence score.

Richeek Das, Pratik Chaudhari

Das and Chaudhari (GRASP Lab, UPenn) find a flaw in LeJEPA's SIGReg, a normality test on random 1D projections meant to push embeddings toward an isotropic Gaussian, so they cannot collapse. It accepts 90% of batches that span only 32 of 64 dimensions. More projections don't help; only bigger batches do. Isotropy is also the wrong goal: the term that pulls views together gives ambiguous images smaller norms, so norm depends on direction. PolarReg matches only the norm distribution (χ_d) and the pairwise cosine distribution, by comparing sorted values to the target's quantiles. On ImageNet-1k it matches VISReg, a LeJEPA variant, in 4.7× fewer epochs and finishes 1.8 points higher.

Under the hood

  • Cost: about 0.52 ms per call on an RTX 4090, 35–164× faster than SIGReg with 4096 projections; 0.14 GB of memory at batch 2048, against 34 GB for SIGReg.
  • Built as an MSE toward stop-gradient targets with fixed step sizes (η_dir=2, η_norm=3) in every experiment; ViT-B at 100 epochs ≈ VISReg at 400.
  • The embedding norm is a label-free signal: it detects out-of-domain images (galaxies, X-rays) at AUROC 0.80–0.95. Linear-probe accuracy rises from 76.7% to 91.8% on the 10% of images with the largest norms.

Takeaway. Don't assume an anti-collapse regularizer works. Measure effective rank (the participation ratio) on real batches. If you train embeddings with an alignment loss, try the embedding norm as a free confidence or out-of-domain score before adding a separate model.

Tool-call smuggling: when an agent's guard and executor parse the same JSON differently

Why read · If you build agents, your approval layer protects you only as far as its JSON parser agrees with the executor's.

Igor Santos-Grueiro, Daniel Romero-Ruiz

Two researchers at Universidad Internacional de La Rioja describe a class of bug. The guard and the executor each parse the same tool-call bytes, and they read them differently. The guard approves one call, the executor runs another, and the audit log records only the approved one. They list six ways this happens: repeated, case-varied or NUL-suffixed keys, type conversion, escapes, truncated streams, schema interpretation, and call-ID binding. Of 55 parser pairs, 43 disagree on some inputs. Their fix is to parse once, keep only the approved schema's fields, and send that object to the executor sealed with its call ID. It blocked all 7,412 crafted inputs.

Under the hood

  • τ-bench attack: Go's encoding/json matches keys case-insensitively and keeps the last match, while an official MCP SDK reads only the exact name. A guard using Go approves reservation I3EHXC, and the SDK cancels another customer's U86B6B.
  • Ten models never wrote repeated or disguised keys into the call itself. They did copy them verbatim into JSON text inside a string argument, where a case-varied key split a Python guard from a Go executor in 82 of 84 replays.
  • A malicious server copied a tool's public schema and added one field. Models put the user's workstation name in it in 29 of 30 trials, and the guard never saw it. 558 of 4,693 deployed MCP schemas gave different arguments or verdicts across components.

Takeaway. Don't let the guard and the executor parse calls separately. Parse once, including any JSON text inside string arguments, drop fields outside the approved schema, and hand the executor that parsed object instead of the raw bytes. Run data-loss checks on decoded values, not raw text, because a filter for "credentials" misses credentials.txt.

TriVS: route to clusters in DRAM, filter with RaBitQ, read only the finalists

Why read · On SSD, the cost of vector search is mostly disk I/O. This CUHK and Microsoft Research design cuts I/O by about two thirds without using more memory.

Yizou Chen, Baotong Lu, Peiqi Yin, Zhisheng Hu, Qi Chen, Ming-Chang Yang

CUHK and Microsoft Research show that disk-based vector search waits on the SSD: at 96 threads, I/O wait is 87–93% of latency in SPANN, DiskANN and PipeANN. Cluster search reads whole clusters (426 pages per query for SPANN). Graph search pays for a chain of reads while walking the graph. TriVS picks clusters with an in-memory index, filters their vectors in DRAM with 1-bit then 2-bit RaBitQ codes (compressed vectors with error bounds), then batch-reads only the shortlist. At Recall@10=0.9 on five datasets up to 1B vectors, it gets 3.42× PipeANN's throughput with 51.2% lower latency, 63.7% less I/O and less memory.

Under the hood

  • Clusters hold about 128 vectors. The cluster count is 0.7–0.8% of the vector count, versus 10–12% in SPANN. With no boundary copies, storage is 46% below the graph baselines and 82% below SPANN.
  • Only 0.8–4.9% of vectors get the 2-bit refinement, and exact reads cover 0.8–4.0% of what survives. The scan stops after about 0.3P clusters (P = clusters probed) in a row add nothing to the shortlist.
  • PipeANN given the same 2-bit RaBitQ was slower than plain PipeANN. The gain comes from quantizing each vector against its own cluster's centroid. At 1 thread, TriVS is 5% slower than PipeANN.

Takeaway. If your retrieval tier runs from SSD, settle the candidate set in memory before the first disk read, then issue all reads as one batch. Quantize each vector against its own cluster's centroid so the in-memory estimates are tight enough to prune.

Tencent OmniEVIE-4B: multi-vector retrieval, 1M records in 54 ms on one CPU thread

Why read · An open (Apache-2.0) retriever for text, images, document pages, video and agent memory that fits each record in under 10 KB and shows where in the page or clip each hit matched.

tencent

Tencent IMA Product Center and Youtu Lab released OmniEVIE-4B, a 4.54B-parameter retriever built on Qwen3.5 with bidirectional attention. It is multi-vector: each document is stored as several vectors, not one. Ward clustering over space and time cuts every record to at most 128×64D int8 vectors (≤9,472 bytes, 8.82 GiB per 1M records). A three-stage search returns 1M-record results in 54.2 ms on one CPU thread. It scores 60.68 on MMEB-V3 (190 tasks), ahead of WeMM-Embedding-9B (59.33), but trails that model on MMEB-V2.

Under the hood

  • Search funnel at 1M records: 14.6 ms coarse, then 19.7 ms Hamming, then 19.9 ms int8. Exact int8 MaxSim (best-match token scoring) takes 12,781 ms, 236× slower. At 5M records the funnel takes 120.2 ms.
  • One Prefix-MRL head gives embedding sizes from 64 to 2048 at query time. A learned gate weights query tokens. Each hit returns a page bounding box or a video timestamp span.
  • On MMEB-V3 Memory it scores 37.6, below WeMM-4B's 39.19. Compressed, it scores 62.96 on ViDoRe V3, below Nemotron-ColEmbed-V2-8B's 63.76. On QVHighlights, 94.3% of returned video spans overlap the correct span.

Takeaway. Cluster each document's vectors into a fixed int8 budget, then search with a coarse → Hamming → exact funnel. That keeps late-interaction retrieval affordable on CPU. Test it on your own memory data before switching, because it trails a smaller rival on the Memory subtask.

Tencent's Loop-PP brings pipeline parallelism to looped Transformers

Why read · Looped Transformers reuse one shared layer stack several times, and standard 1F1B pipeline schedules cannot handle that. This compiler-based schedule keeps one copy of the weights and still overlaps communication with compute.

Yunjia Xi, Jiarui Qin, Di Yin, Xing Sun — Tencent

Tencent Youtu Lab's Loop-PP trains looped Transformers, which run one shared layer stack T times, across pipeline stages. Interleaved 1F1B (Megatron's standard schedule) assumes each micro-batch visits each stage once, so feedback from the last stage to the first stalls it or runs it out of order. Loop-PP unrolls every visit into an acyclic graph, keeps 1F1B's per-stage order, and compiles a fixed per-rank stream that splits each transfer into POST (start) and WAIT (finish). On 8B–60B MoE models it cuts peak memory by up to 32.8% and raises best throughput 12.7% at equal budget. Losses match single-stage training bit-for-bit.

Under the hood

  • A priority-guided Kahn topological sort picks the next ready operation by (native 1F1B slot, forward before backward, node id). Each stage keeps its 1F1B order and no recurrence dependency is skipped.
  • Baselines: an unrolled copy with independent weights (about 30% more memory), tied replicas, and a conservative Lockstep schedule. Lockstep runs out of memory at 60B PP2, and Loop-PP is over 6x faster than it at PP8.
  • At PP8 Loop-PP is slower than Unrolled because thin chunks expose the cross-stage waits: 99.98% of receive-wait time is spent on dependencies. Doubling chunk thickness raised throughput from 64.7k to 71.3k tok/s.

Takeaway. If you train looped models, use coarse pipeline partitions with thick chunks per stage. The broader pattern is useful elsewhere: compile a cyclic workload into a fixed, deadlock-free schedule that splits each send into post and wait.
