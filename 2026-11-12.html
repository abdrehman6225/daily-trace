WikiTrace links each agent memory lesson back to the run it came from

KAIST shows that distilled lessons often break tasks an agent already solves, and that keeping the raw trajectory next to each lesson cuts those regressions.

Yukyeong Lee, Yumin Choi, Jinheon Baek, Sung Ju Hwang — KAIST AI

KAIST AI (Sung Ju Hwang's group) separates memory's effect into Gain (failures that memory turns into successes) and Regression (successes it turns into failures). Average accuracy hides the second number. The authors took tasks the agent solved in all three runs without memory but failed with memory. An LLM judge traced 52% of those failures to a memory item the agent followed, most often a lesson that was simply wrong (20%). Lessons go wrong because each is inferred from a single success/failure label. WikiTrace stores three linked layers per past run: up to three insights, a compilation explaining why the run succeeded or failed, and the raw trajectory. All three are mounted as read-only files. The agent sees every insight up front. The prompt tells it to dig into the source run with read/bash when an insight lacks detail, comes from a failed run, conflicts with another insight, or when an action fails.

The authors tested on eight suites from ALFWorld, ScienceWorld, PlanCraft, AppWorld and τ³-bench, using deepseek-v4-flash. WikiTrace averages 90.2, against 79.5 with no memory, and beats an Insights Only ablation (same insights, no source runs) by 3.2 points. Regression falls from 6.5% to 4.5%. Simply rerunning the agent with no memory flips 9.7% of successes, which sets the noise floor. Each task costs 1.17x as much as Insights Only. One limit: every insight sits in the prompt, so retrieval at larger memory sizes is left open.

Under the hood

  • Layout: /work/corpus/{raw,compilation,insight}, each with a code-generated _index.md. Insights are never updated or deleted, so the agent resolves conflicts at test time.
  • The agent opened source runs in 22% of Easy-task runs and 44% of Hard ones. The opened run changed its plan 43% of the time, usually by revising an insight (24%).
  • Insights from failed runs alone gave Insights Only its worst Regression: 9.3% on PlanCraft, 9.4% on ScienceWorld. WikiTrace cut these to 7.1% and 8.9%.
  • AWM, ExpeL and ReasoningBank each fall below no memory on some suite, even with 3–9x construction budget. WikiTrace holds up on GLM-5.3-flash (92.7 average).

Takeaway. Store raw provenance with every distilled memory item and let the agent read it on demand, especially for lessons drawn from failures. Track Regression against a no-memory rerun baseline, not just average accuracy.

A REINFORCE step with a binary reward is rejection-sampling fine-tuning

A short derivation that explains why reasoning chains get longer during RL, why forcing longer thinking stops helping, and where reward hacking comes from.

Alex Wang (Stanford PhD, formerly at Cartesia) treats reasoning as pathfinding in token space. The success probability p_x is the total probability of every chain of thought whose answer lands in S_x, the set of answers the verifier accepts. Best-of-k sampling raises it to 1−(1−p_x)^k. That scaling comes from the number of samples, not from longer chains. He shows that a REINFORCE step with a 0/1 reward is the same as fine-tuning on the model's own successful samples, scaled by the success rate M/N. Chains grow longer only when longer paths happened to succeed. Nothing in the reward checks whether the reasoning is faithful to the answer.

Under the hood

  • Gradient of p_x = (M/N) × average ∇log π over the successful paths. Failed paths have r=0 and drop out of the gradient entirely.
  • Muennighoff et al. 2025 forced models to keep thinking by appending "Wait": accuracy rose, then flattened. Gema et al. 2025 found tasks where longer reasoning made accuracy worse.
  • Reward hacking: if the verifier accepts wrong answers that are easy to reach, scaling RL probes the verifier more widely, finds those shortcuts and then trains the model toward them.
  • HN (gertlabs): turning reasoning off on some RL rollouts, for problems the model already solves without it, improved latent reasoning and cut the tokens needed per solve.

Takeaway. RL with a verifier only raises the success rate across many sampled paths. It does not make any single chain converge on the right answer, so put compute into more samples plus verification, and treat the verifier as the real specification you are optimizing against.

Apple trains small networks that route vector-search queries faster

If your retrieval layer serves a stable query distribution over a fixed corpus, you can learn to route queries more accurately than IVF centroids do.

Apple researchers (ICML 2026) build on a fact about maximum inner product search (MIPS, finding the key with the highest dot product against a query). The best score as a function of the query is the support function of the key set: it is convex, and its gradient is the best-matching key. They sample queries, label each one by exhaustive search, and fit small networks to the labels. SupportNet, an input-convex network, predicts each cluster's best score and replaces IVF centroid routing. KeyNet rewrites the query into a predicted key before a normal FAISS IVF lookup. On Natural Questions (~2.6M passages), KeyNet reaches 99% recall in 0.23 ms vs 1.8 ms for the raw query.

Under the hood

  • SupportNet (128 clusters): the small model reaches 95% routing recall in 1.74 ms vs 3.36 ms for centroids, and the large one reaches 97% in 1.74 ms. These times include the network's own cost.
  • Model sizes run from 1% to 20% of the database size. KeyNet uses a consistency loss from Euler's homogeneous-function theorem instead of enforcing convexity.
  • HN commenters say BM25 or grep tools beat learned retrieval below a few million items, and that the gains matter mainly at hyperscale.

Takeaway. The query-rewriter idea (KeyNet) needs no change to an existing ANN index: put it in front and query with the predicted key. It is only worth trying when the corpus is fixed, the query distribution is known and stable, and you can retrain whenever the keys change.

AWS releases an official local emulator, apparently built with AI agents

An official local stand-in for AWS APIs helps agent-driven development and CI, but its own docs say not to use it to test IAM or other security controls.

AWS has published aws/aws-emulator on GitHub, a local emulator for AWS services. Very little text could be fetched. The HN post links to an All Things Distributed post and an Amazon article about autonomous AI agents, which suggests agents built much of the emulator, but neither article's text was available. One commenter says it appears to be generated from AWS's Smithy models (Smithy is the interface-definition language that all AWS SDK clients are generated from) and checked by integration tests against the real APIs. If so, it would cover every endpoint variant and optional field, while Floci and MiniStack only implement the commonly used calls. That is a commenter's reading, not something AWS has confirmed.

The HN thread (765 points) focused on fidelity. A comment quotes the emulator's security page: the emulator never denies a request signed with its own key, ignores S3 bucket and KMS key policies, has no cross-account or cross-Region calls, and evaluates IAM differently from AWS. Others asked whether AWS will maintain it long term, pointed to Floci with Testcontainers (which also covers GCP and Azure), and asked whether a full cdk deploy behaves realistically, including ordering quirks during setup and teardown.

Under the hood

  • The security page explicitly excludes IAM policies, permissions boundaries, resource-based policies, KMS key policies and cross-account or cross-Region access from testing.
  • Requests signed with the emulator's own key are never denied, so permission bugs will not show up locally.
  • A commenter thinks it was built from Smithy specs (github.com/aws/api-models-aws), which would give much wider API coverage than LocalStack, Floci or MiniStack.
  • An Amazon engineer in the thread says agents need closed systems with mocked dependencies, and infrastructure emulators fill that gap.

An LP solver matches GPT-6 Astra's 8-hour weight edit in about a minute

An agent's slow trial-and-error weight edit turns out to be a sparse linear program, and a plain steering vector does almost the same job.

In MIT CSAIL's Sparks of Weight-Space Programming, the agent GPT-6 Astra edited Qwen3.5-0.8B's weights to stop its thinking loops, raising MATH-500 from 7.9% to 48.1%. Nathan Barry shows the edit is a rank-1 change ΔW = u vᵀ to down_proj (the MLP output matrix) in layers 15 and 19. Choosing v took Astra about 8 hours of trial and error. Barry recasts it as an L1-minimizing linear program and solves it in about a minute. His edit changes 16,291 weights against Astra's 130,188 and scores 51.7 against 50.9 on MATH-500.

Under the hood

  • The constraints are linear: push looping tokens at least δ against the loop direction u, push productive tokens at most ε. Minimizing L1 keeps v sparse, so the LP also picks the columns.
  • HiGHS took over 20 minutes per solve. A custom GPU PDHG solver (the algorithm behind PDLP) got within 0.2% of the optimum in about a minute.
  • The edit acts as a near-constant push. A steering vector of the same average size scores 50.8 on MATH-500; at half or double strength it fails.

Takeaway. If a behavior lives along one residual-stream direction, write the fix as an LP with "change these tokens, keep those" constraints instead of searching by trial and error. Try a constant steering vector first.

Ex-Meta engineer: agent-written code is shallow-tested and hard to debug

An argument from experience, with no data, about how agent-written code fails over time. The HN thread is more useful for its fix: enforce maintainability with automated checks instead of relying on human review.

Evan Merz left Meta, where generating at least 90% of your code with AI was the minimum for a decent rating. He now generates 100% of his code with AI at another large company. His case rests on what he has seen, not on data: agents handle problems that fit in their context window and miss long-term design. He names four causes: shallow tests, too many small helper functions, a team that understands its own code less and less, and PRs that arrive faster than anyone can review them properly. HN commenters replied that codebases rotted long before AI and that automated quality checks are the fix.

Under the hood

  • The shallow tests: get/set tests and end-to-end tests that cover only paths the codebase already handles. Line-coverage numbers stay high, so the gaps are invisible.
  • His example: a top engineer tried to merge mouseover effects done with JS event handlers instead of the CSS :hover selector.
  • The symptoms he predicts are rising incidents, slower recovery and errors only users see. He gives these as a story, with no incident counts or before/after numbers.
  • HN (632 points): one commenter cited Oracle's 25M-line database codebase as pre-AI rot. Another wants maintainability checks (cyclomatic complexity, naming, DRY) enforced automatically and by adversarial review.

Takeaway. If agents write most of your code, don't rely on people skimming PRs to catch quality problems. Use tests that cover user scenarios, not just lines, plus complexity linters and review agents with explicit rubrics, and compare incident counts and recovery time before and after adopting agents.

NVIDIA's Agent Substrate snapshots idle agents and runs many sessions on a few warm Pods

It solves a choice every agent runtime faces: keep one warm sandbox per session, or pay a cold start on every step. Substrate snapshots idle sessions instead, and Dynamo's inference signals tell it when.

NVIDIA has given Agent Substrate to the CNCF Sandbox. It drops the one-Pod-per-agent model. A separate control plane runs many actors (an agent plus its environment) on a small pool of warm Kubernetes worker Pods. When an actor goes idle, it is snapshotted out of its gVisor or microVM sandbox with its memory and filesystem. When called again, it is restored onto any free worker without going back through the API server, scheduler or kubelet. NVIDIA says this gives 10x the density of standard containers but publishes no benchmark. Dynamo, NVIDIA's inference framework, reports projected time to first token and GPU-pool saturation, so Substrate can suspend actors during long model waits. The APIs are still changing.

Under the hood

  • Request parking (#221): when every worker is busy, the router holds the turn with a bounded wait and a cap on queued requests. A follow-up (#1229) keeps requests to already-running actors out of that queue.
  • GPU snapshot design: vendors list the device properties a checkpoint depends on. Restores go to a matching GPU through Kubernetes DRA (Dynamic Resource Allocation), or fall back to a cold start.
  • Dynamo's router uses session identity, tool-call boundaries and KV cache location to keep agent turns on GPUs that already hold the context. It drops cache from finished subagents first.

Takeaway. If your agent sandboxes sit idle between turns, snapshot and restore them onto a shared warm pool instead of keeping one per session. Use inference signals such as projected time to first token to decide when to suspend a session and when to wake it.

Google's Gemini Decisions API scores closed-set choices in one forward pass

A cheap, calibrated classifier endpoint for agent routing, tool selection and policy checks, so you don't need a full generative call.

Google DeepMind's new gemini-decision-1 model takes one multimodal input of up to 256K tokens (text, image, audio, video or PDF) plus up to 1,000 questions. It scores the candidate answers in a single forward pass and generates no text, so each answer comes back as probabilities with a 0–1 confidence. Latency is 150–250 ms end-to-end and stays nearly flat from 1 to 100 questions. Price is $0.10 per 1M input tokens, the shared input is billed once per request, and output tokens are free. Google says this is about 5x cheaper than Gemini 3.5 Flash-Lite on its own benchmark suite, but it publishes no numbers for the calibration claims.

Under the hood

  • There are three question types: noul (yes/no probability), choice (2–255 options with normalized probabilities) and score (an ordered rubric that returns a weighted continuous score).
  • Model compute is 50–100 ms at the median for contexts up to 16K tokens. Each extra question adds only its own instruction and criteria tokens.
  • Gemini Notebook uses it to route queries between model tiers and reports up to 40% lower latency on everyday queries.
  • HN commenters say it costs more than rival decision models but stands out for taking audio and video, and they point to known problems with asking LLMs to state their own confidence.

Takeaway. For an agent's router, tool picker or guardrail, try scoring a fixed set of options with a decision model instead of parsing generated JSON. Send uncertain cases to a fallback or a human based on the confidence score, and test the calibration on your own data before relying on it.

Cloudflare picks leaderless-leaning QuePaxa over Raft for its global consensus service

This is a clear look at why Raft-style leader election breaks down over wide-area networks, and at a randomized protocol that keeps working without fault detection.

Cloudflare's Meerkat is an experimental consensus service for its internal global control plane. It is a replicated log that backs a key-value store, similar to etcd or ZooKeeper, except its replicas sit on different continents. It runs QuePaxa (Tennage & Băsescu et al., 2023), not Raft or Multi-Paxos. In leader-based protocols, everything stalls whenever the leader is slow or cut off. Recovery then depends on fault detection, but over a wide-area network a dead node and a slow link look identical. Raft election timeouts are usually 5–10x the round-trip time, which comes to about a second at global distances. Candidates can also split votes again and again, a metastable failure: a two-second blip can trigger elections that go on much longer. In 2020, a partially failed switch left a consensus-backed system unable to accept writes and made the Cloudflare dashboard 80x slower for six hours.

QuePaxa has proposers and recorders. Every proposal gets a random priority, and the optional leader always gets the top priority. When a proposer sees a higher-priority proposal, it adopts that proposal and broadcasts it instead of its own. Concurrent proposers therefore converge on one value rather than blocking each other. Each round has four phases, and each phase waits for a majority of recorders: Propose/Adopt, Spread, Check/Decide, Carry Forward. Safety comes from majority intersection: any two majorities share at least one recorder. The random priorities are how the protocol gets around the FLP impossibility result.

There is no failure detector. Clients send each request to every replica and wait a short hedge timeout so the leader can decide first. A 5 ms hedge on a 100 ms network does not freeze anything. It just adds more active proposers, at the cost of extra bandwidth and sometimes extra rounds. In Cloudflare's tests, more than 95% of decisions came from the leader's one-round-trip fast path. When that path missed, throughput dropped to no less than a third of normal, and the system never fully stalled.

Under the hood

  • Leader fast path: if the leader's proposal reaches a majority of recorders before any other, it decides in phase 0. Intersection makes every other proposer adopt it.
  • Cloudflare departs from the paper: clients wait out the hedge timeout instead of replicas, which cuts network messages without changing the result.
  • The paper predicts a ≥50% chance of deciding in each round after the first. Cloudflare says it sees much higher in practice because proposers converge.
  • They can change which replica is leader while the cluster runs, because a poor leader choice slows the system but does not stall it.
  • Open risks: the original crash-stop design is being extended to crash-recovery. They are formally verifying the Rust implementation and running fault-injection tests. Benchmarks will come in later posts.

Takeaway. If your system's availability depends on a timeout guessing correctly that a node is dead, assume wide-area networks will make it guess wrong. Hedging (sending work to several replicas and letting duplicate work converge) can replace failure detection when extra bandwidth costs less than downtime.

Baseten and Genspark split deep research into RL for search and SFT for writing

A detailed agent post-training recipe: diagnose each phase separately, use the right training method for each, and add countable terms to an LLM-judge reward.

Baseten Applied Research post-trained Qwen3.5-397B for Genspark's Deep Research agent, running inside Genspark's own harness. On Genspark's LLM grader it scored 0.759, up from 0.612 for the base model. Sonnet 5.5 scored 0.742, Opus 5.5 0.738, Kimi K3 0.724, DeepSeek V4 Pro 0.675 and GPT-5.6 Sol 0.637. The key test came before any training. The team kept each trajectory's research the same and had a stronger model write the report. On a small panel the score rose from 0.58 to 0.73, which showed that synthesis was the main bottleneck, not research. An RL-only attempt at writing stalled because nearly every report got the same score, leaving almost no signal to learn from.

The recipe has three stages. Search RL uses a frozen writer, so the reward measures research quality only. Writing SFT pairs the model's own trajectories with strong reports written from the same evidence, with the research turns held fixed. End-to-end RL then trains both together. The reward adds a breadth score S with per-question targets to the judge score G. The judge reads the full trace, so padding a trace with irrelevant searches lowers G. A run with this reward at 50 steps beat runs without it at 200 steps.

Under the hood

  • S = 0.4·min(q/Q_i,1) + 0.6·min(d/D_i,1); Q_i, D_i = most distinct queries/sites any reference model used on that question.
  • R = (G + 0.5·S)/1.5. If no reference model searched on a question, that part gets full credit, so the agent isn't pushed to search there.
  • Base model vs trained: sites crawled 4.5→21.7, tool calls 7.9→28.5, report length 12.1K→15.9K chars.
  • Serving: expert weights in NVFP4, attention at full precision, 2×B200 per replica (down from 4 at FP8), about 160 tok/s decode, cache-aware routing per research session.

Takeaway. Before running RL on a multi-phase agent, swap out one phase at a time to find the real bottleneck. When an LLM-judge reward barely separates outputs, use SFT on the model's own trajectories to teach the behavior, and add capped, per-task countable terms to the reward.

Featured · uber.com · Uber Engineering · Nov 12 · 2 min

Uber moves 90% of eligible Presto traffic onto Velox's C++ engine

A production migration from the JVM to a vectorized native engine, with a routing model that changed partway through, honest shadow-test benchmarks and the operational work it took.

When Uber profiled its Presto fleet (dozens of clusters, thousands of hosts), it found that more than 90% of CPU went to one stage: scanning data, filtering it and selecting columns. In that stage the JVM pays for boxed objects and garbage collection, and its bytecode does not reliably compile to SIMD instructions. Uber moved query execution to Velox, Meta's vectorized C++ engine that processes data in columnar batches. Presto running on Velox is called Prestissimo. A proof of concept in December 2023 showed up to 7x CPU savings on scan-heavy queries. Most of the work that followed was operational: C++ build and CI tooling, vendoring native libraries, Prometheus metrics exported by a sidecar subprocess and scraped by M3, and tuning Velox's shared-mode memory arbitrator with the mmap allocator. The team also fixed Parquet reader bugs where nulls inside structs, arrays and maps produced silently wrong results.

Rollout came in two phases. Phase 1 (0 to 30%) ran every query on both engines and allowlisted only the query fingerprints whose results matched. Phase 2 switched to a blocklist of fingerprints known to crash Velox, which took coverage to about 90% of eligible traffic, around 100 PB a day. A four-day shadow test of live production traffic, on identically sized clusters, gave Velox 2.4x faster queries and 3.06x less CPU. Its success rate was 99.12% against Java's 92.43%.

Under the hood

  • Early benchmark on 40,000+ queries (1,000+ shapes): 3.73x less CPU time and 2.5x faster at equal capacity; with 30% less capacity, still 3.55x CPU and 1.47x elapsed.
  • Shadow test: the Modulator tool replayed queries at their original submission times. Java CPU sat at ~95%, Velox at 35-70%; time-limit failures were 663 on Java versus 7 on Velox.
  • Velox's Parquet writer still has gaps: no end-to-end schema evolution, partial TIME/TIMESTAMP support, worse compression on numeric and MAP columns, some files unreadable by Spark.
  • The fork is synced with upstream about weekly. Reader tests reuse Presto's Java unit tests to generate Parquet files, and geometry functions take ~15% of Presto CPU.

Takeaway. For an engine migration, start with an allowlist: shadow-run each query fingerprint on both engines and switch over only the ones that match. Once coverage is high, flip to a blocklist of known failures, and benchmark by replaying production traffic at its real arrival timing rather than with synthetic tests.

Baseten speeds up DeepSeek V4.1 Flash with agent-tuned kernels, PDL and CUDA graphs

On MoE models with few active parameters, kernel launch overhead and the Python scheduler become the bottleneck, and Baseten shows three ways to remove that overhead.

Baseten built a Fast variant of DeepSeek V4.1 Flash 1017, a 552B MoE with 8B parameters active in prefill and 16B in decode. An internal agent harness tuned 80+ kernels, and Artificial Analysis lists the result at 991 output tokens/s. Under the hood

Takeaway. For small-active-parameter models on fast GPUs, look for idle gaps between kernels and launch overhead from the CPU before tuning kernel math. Turn on PDL first for kernels that read a lot of weights.

Why RL post-training stalls, and why resetting the KL reference fixes it

A theory paper from Foster, Krishnamurthy, Kakade and coauthors explains why PPO and GRPO stall during post-training, and shows that resetting the KL reference to the current policy fixes it.

Audrey Huang, Nan Jiang, Sham M. Kakade, Sadhika Malladi, Akshay Krishnamurthy, Dylan J. Foster

Huang, Jiang, Kakade, Malladi, Krishnamurthy and Foster (Harvard Kempner, UIUC, Microsoft Research) prove that REINFORCE, the base of PPO and GRPO, can suffer coverage collapse. Reward rises while the probability of producing an optimal response falls toward zero, so the gradient signal disappears. Their example uses a base model that needs at most 6 samples per correct answer. Even with exact gradients and a KL penalty to that base model, training still takes a number of steps exponential in 1/√ε. The fix is reference resets: every so often, move the KL anchor to the current policy. They frame this as APMD (Approximate Policy Mirror Descent): solve a strongly regularized RL subproblem, reset the anchor, and repeat.

Under the hood

  • If each subproblem is solved closely enough (a KL tolerance), APMD converges at log(2·C_base)/(ηT), and every iterate keeps at least half the base model's chance of an optimal answer on most prompts.
  • PPO-NoClip with η=1/B needs Õ(C_base·B³/ε³) gradient steps; on the same example, fixed-reference REINFORCE needs exp(Ω(1/√ε)). In their analysis, clipping mainly reduces importance-weight variance.
  • The same guarantee holds for Kimi-style squared-loss methods (KimiPO, KimiPO-Norm) and on-policy Rebel. All proofs assume softmax-linear policies over frozen pretrained features.

Takeaway. If RL fine-tuning plateaus under a KL penalty to a fixed base model, try resetting the reference to the current policy every so often and using a stronger KL penalty within each phase. Track how often the policy produces correct answers (pass@k), not just mean reward.

DeepMind's excursion policies offer a new bias-variance knob for off-policy TD learning

Ex-trace is a one-line change to V-trace or Retrace that trades bias against stability on replay-heavy, highly off-policy data, and it comes with convergence proofs.

Jiamin He, Mark Rowland, Zhaohan Daniel Guo, Hado van Hasselt, Diana Borsa

Google DeepMind (van Hasselt, Rowland, Borsa et al., NeurIPS 2026) add a new way to learn a target policy π from data collected by another policy μ. Mixture policies re-pick π or μ at every step. An excursion policy instead follows π for a random-length stretch (continues with probability β), then switches back to μ. Their estimator, Ex-trace, moves smoothly from uncorrected TD (β=0) to V-trace (β=1), and the paper proves it converges. On the hardest dm_control dog and humanoid tasks with MPO, middle values of β learned better than unstable Retrace and slow uncorrected TD. Overall it matched mixture policies (α-Retrace), not beat them.

Under the hood

  • Trace weight: C_t = (1−β) + β·min(ρ̄, ρ_t)·C_{t+1}. Setting β=1 gives back V-trace's clipped importance-ratio product.
  • At equal α=β, excursions stay closer to μ. You need β = α / (1−(1−α)γλ) to match the mixture policy's discounted time spent on π.
  • On random MDPs, Ex-Retrace was more often Pareto-efficient on contraction versus bias. Policy-improvement guarantees are proven only for one-time excursions (λ=1).

Takeaway. If Retrace or V-trace becomes unstable at high replay ratios, scaling the trace by β (try 0.8–0.95) is a cheap fix to sweep. It sits next to the α-mixture option, and its behaviour suits coherent, option-like action sequences.

Learn · today's concept

Truncated importance traces: how Retrace and V-trace learn safely from stale data

The problem: replay buffers, distributed actors and logged agent runs all produce data from a behaviour policy μ that is older than, or different from, the policy π you are learning. Multi-step returns spread reward back through a trajectory quickly, but they include actions π might never take. The textbook fix is to weight each step by the importance ratio π(a|x)/μ(a|x), but those ratios multiply along the trajectory and the variance grows exponentially. One-step TD avoids the variance but spreads credit slowly. Trace methods sit between the two.

How it works: at each step t, compute the ratio ρ_t and turn it into a trace coefficient c_t = λ·min(1, ρ_t). The correction to the value at the start state is the sum of the TD errors δ_t = r_t + γV(x_{t+1}) − V(x_t), each weighted by γ^t and by the product c_1…c_t. Because every c is at most 1, the product can only shrink. When π disagrees with what μ did, the trace is cut and the update falls back on bootstrapped values. Retrace (for Q-values) converges for any μ. V-trace also clips the ratio on the TD term itself, at ρ̄. This makes it stable, but it then converges to the value of a policy somewhere between μ and π.

Example: suppose the ratios over three steps are 2.0, 3.0 and 0.5. Plain importance sampling gives cumulative weights of 2, 6 and 3, which is unstable. Truncation gives 1, 1 and 0.5, and with λ = 0.9 the weights become 0.9, 0.81 and 0.36. The trade-off is that very off-policy data cuts traces to almost one step, which is safe but slow. Ex-trace's β scaling shrinks traces further to buy stability at high replay ratios. Use these methods whenever your actors, logs or memory replay lag behind the learner.

A short burst can leave prefix-cached agent serving degraded indefinitely

If you serve multi-turn agents on vLLM or SGLang, a burst or a restart can cut throughput in half and it will not recover by itself. Suspending sessions that are already admitted gets it back.

Wen Huang, Jack Liu

Wen Huang (Microsoft) and Jack Liu show that prefix-cached agent serving is metastable: once something pushes it into a degraded state, it stays there after the trigger is gone. On vLLM with Qwen3-8B at about 70% of capacity, a 5-minute burst left 9 of 12 runs at about a 10% cache hit ratio and under half throughput, while their no-burst twins stayed healthy. Slower service keeps more closed-loop sessions in the system, their contexts outgrow the KV pool, and LRU evicts each prefix before its next turn. Throttling new admissions rarely fixes it. Parking admitted sessions does.

Under the hood

  • The fix is a gateway budgeter on resident KV demand D, the sum of each active session's context plus output budget. It admits while D≤0.75C and parks at turn boundaries above 0.95C, where C is the KV-pool size.
  • The budgeter recovered 17 of 17 collapsed runs, mostly in under 5 minutes. On the 8B matched seeds, an admission-only cap recovered 1 of 7 and latency-driven AIMD (additive-increase, multiplicative-decrease concurrency control) 5 of 7, after 14–25 minutes.
  • Recovery needs λ<1/S, where S is the cost of a session that misses on every turn: about 78 s, giving 0.013 sessions/s. Measured break-even was 0.010–0.014. SGLang needs larger triggers; CPU offload only delays the collapse.

Takeaway. Alert on prefix hit ratio and on active sessions' token demand relative to the KV pool, not on GPU utilization. Limit concurrency by tokens, not session counts, and be able to suspend sessions mid-task at turn boundaries.

If your agent routes each step to a cheap or a strong model, every switch throws away the prefix cache. This Microsoft paper recovers most of that loss using idle GPU capacity.

Microsoft Azure Research found a cost in per-step model routing: KV caches belong to one model. When an agent switches models, the prefix-cache hit rate drops from 80–89% to 44–65%, and the call takes 1.5–3.2× longer. ShadowPrefill prefills the session on the model the router didn't choose. It uses spare time in each decode iteration (69–79% of the per-token latency budget is unused, even at peak), a capped shadow-KV class that is evicted first, and spill to host memory. Under the hood

  • Slack controller: a request may next wait σ = (1−m)·T·(k+1) − (t−f). The batch budget is the smallest σ, capped at 0.5× the per-token SLO. Iterations carrying routed calls get only a credit of δ = 0.025.

  • Results are mostly from simulation (Vidur). The vLLM prototype is about 840 lines of Python with no engine changes and cut switch TTFT by 61.9% on 16 H100s. Gains shrink to about 3% for targets above 50B, where decode dominates.

Takeaway. If you route agent steps across models, measure cache hit rate on switch calls separately; the lost cached-input discount can cancel much of the routing savings. A simple first version is to send each finished call's prompt and response to the other model as a low-priority request.

Shanghai AI Lab trained Intern-S2-Preview-35B with GRPO (group-relative policy optimization) on 5,183 proof exercises from 158 math textbooks, with the solutions removed. The model reads each book through a three-tool BookNavigator (get_toc, search_index, read_section). The reward adds two things to proof correctness. First, a bonus for correct trajectories that used a tool, annealed on a cosine schedule from 1 to 0.25. Second, per-round credit: a frozen copy of the initial model labels each call useful, neutral or harmful. Proof accuracy rose from 51.5% to 79.5%, beating an RL-trained top-k retrieval baseline (73.1%). BrowseComp-Plus improved 1.7 points and CL-bench 2.3.

Under the hood

  • Correctness-only RL reached 74.9%, but the share of trajectories that used tools fell from 36.9% to 6.7%. The bonus raised it to 79.9% and added 2.0–2.9 points on held-out books and subjects.
  • Credit is spread across rounds as Ã_t = A + α|A|(c_t − c̄), centred so the token-weighted mean stays at A. Harmful calls score 0.5, others 1, with α=1. The judge never sees the answer or the verdict.
  • GLM-5.2 grades the proofs with 8-shot pessimistic verification: a proof counts as correct only if all 8 reviews pass. Removing the source section and its neighbours costs 5.2 points against removing random sections. Procedural CL-bench tasks got worse.

Takeaway. When you train a tool-using agent on outcome reward alone, watch how often it calls its tools, not just accuracy. A bonus for tool use that only applies to correct answers, plus centred per-call credit from a frozen judge, keeps retrieval alive without changing the trajectory-level signal.
