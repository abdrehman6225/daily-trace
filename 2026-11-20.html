Balestriero and LeCun: world models can answer "what if" by reusing the observed residual

A proof that factual training alone can never give an individual counterfactual, and a fix that needs no retraining. It applies directly to credit assignment and hindsight replanning in agents.

Randall Balestriero, Yann LeCun, Kerda Varaku

Randall Balestriero (Brown, AMI Labs), Yann LeCun (NYU, AMI Labs) and Kerda Varaku look at an individual counterfactual. A hidden disturbance, such as a current pushing a boat, changed an outcome. What would a different action have produced under that same disturbance? They prove that a model trained only on factual transitions cannot answer this, however much data or capacity it has. Factual data pin down each action's outcome distribution but not how outcomes are paired across actions. Two mechanisms with identical factual laws can give different counterfactuals. A perfect generative model does not escape this either: you can relabel its latent noise separately for each action (a "gauge" freedom) and every likelihood stays the same while the counterfactual changes.

The fix rests on the idea that nature makes no leaps. If action and disturbance act as separate forces, their interaction is second-order in the step h. To first order, then, ẑ(a') = z_{t+1} + μ(z_t,a') − μ(z_t,a_t): the observed outcome plus the model's predicted difference between the two actions. This needs no counterfactual data, no new parameters and no retraining. In additive worlds the rule is exact, and it is the only rule that is. Its error relative to the disturbance variance is O(h²), and a matching minimax lower bound shows unpaired factual data cannot do better.

The tests run from pixels, using JEPA predictors on frozen DINOv2 and MAE encoders. On four rendered simulators, counterfactual R² rises from 38–46% to 86–96%. On image features directly, with no state labels, it reaches 73–94%. A BlueROV2 underwater vehicle reaches 90–94%, but needs 16x more factual data. In hindsight planning, the method finds the action that would have reached the goal in 35–69% of events. An oracle planner that knows the simulator but not the outcome manages 14–23%. Failures appear where the theory predicts: contacts, folded coordinates, and disturbances that scale the command.

Under the hood

  • Exact error identity: E‖T_R − Y(a')‖² = tr Var(Δ), the variance of the action effect across disturbances. Learned-predictor errors enter only through the action contrast; errors shared by both predictions cancel.
  • ρ_z = residual-reuse error divided by the error of an exact factual predictor. Below 1 the method helps, and ρ_z ≤ (K‖a'−a‖/κ)². Computing ρ_z needs paired outcomes; factual data give only a lower bound.
  • The 86–96% figures apply the correction after a readout fitted on labelled factual frames, where interaction can be smaller. Correcting the embeddings directly works with any pretrained encoder.
  • DINOv3, SigLIP 2, CLIP and EVA-02 encoders give 81–95% on the same four simulators. A worn actuator whose effect grows with the command breaks the rule even though its dynamics are smooth.
  • Prior art: disturbance observers, offset-free MPC and additive-noise structural causal models. The paper adds the justification for learned latent world models. Code: github.com/galilai-group/counterfactual-WM.

Takeaway. To replay "what would another action have done" with a learned dynamics model, add the model's predicted action difference to what actually happened, rather than resampling the model. First check whether the disturbance multiplies the action or only adds to it, because the trick fails when it multiplies.

Zerodha's Blobasaur: a Redis-protocol blob store built on sharded SQLite files

A small, production-tested storage design: one writer per SQLite shard, group commit and compression, with p99 around 2 ms on three small nodes.

Zerodha stores layouts and workspaces for Kite users as JSON blobs from a few KB to several MB, and writes are half the traffic. Their old store, SSDB, was unmaintained and ran on a single node. They replaced it with Blobasaur, a Rust server that speaks the Redis and Redis Cluster protocols and uses SQLite as the storage engine. SQLite in WAL mode allows only one writer per file, so each node spreads keys over many SQLite files using multi-probe consistent hashing. Each shard has one writer task. It drains a bounded queue and commits the whole batch in a single BEGIN IMMEDIATE ... COMMIT (group commit). Separate read-only connection pools serve reads. zstd compression shrinks the average payload from 63.6 KiB to 5.5 KiB. That keeps 99% of stored values under ~100 KiB, the size above which raw files beat SQLite.

On 64 KiB blobs, going from 1 to 16 shards raised HSET from 7,740 to 25,324 ops/s. Reads stayed near 70k ops/s. In production, a three-node cluster (4 vCPU, 8 GB each) holds p99 around 2 ms. One lesson: TTL cleanup ran one large DELETE on its own connection and fought the writer for the lock, causing 30–50 ms spikes. Sending cleanup through the shard writer in 1,000-row chunks removed the spikes. HN commenters said that files not shrinking after deletes is normal RDBMS behaviour, and that SQLite commits are uncompetitive without batching.

Under the hood

  • Two-level routing: CRC16(key) % 16384 picks the node (gossip, MOVED redirects), and consistent hashing picks the SQLite shard. Slots are static, with no failover or live rebalancing yet.
  • Durability: WAL with synchronous=NORMAL. Optional async_write acknowledges a write once it is queued; a pending map with tombstones keeps read-your-writes for GET, HGET, EXISTS and TTL.
  • Schema: one blobs_<namespace> table per hash. A partial index covers expires_at, and expired rows are filtered at read time. Incremental auto_vacuum plus wal_checkpoint(TRUNCATE) reclaims disk.
  • Migration: one month of dual writes, with reads falling back to SSDB, showed zero discrepancies. Clients only switched to a Redis Cluster client. Written in Rust rather than Go to avoid CGo; licensed AGPLv3.

Takeaway. When one SQLite file can't keep up with writes, split the data across many files, give each one a single writer with group commit, and run background work like TTL deletes through that same writer in bounded chunks.

PostgreSQL 19 ships online REPACK, plan pinning and read-your-writes on standbys

Several long-standing operational problems get first-party fixes: table bloat, plans that regress after data changes, and reading stale data from replicas.

PostgreSQL 19 is out. REPACK (CONCURRENTLY) replaces VACUUM FULL and CLUSTER, reclaiming bloat without blocking reads or writes. pg_plan_advice pins planner choices, and pg_stash_advice applies that advice by query ID with no app changes. Standbys gain read-your-writes: WAIT FOR LSN holds a query until the standby has replayed the WAL past a given log position. INSERT ... ON CONFLICT DO SELECT returns the existing row, which removes the second query in get-or-create. HN commenters singled this out. Faster foreign-key checks made bulk inserts nearly 2x faster in testing. JIT is now off by default.

Under the hood

  • Logical replication no longer needs a restart. Creating the first slot raises the effective WAL level to logical, and sequences can now be published too.
  • Autovacuum vacuums indexes with parallel workers (autovacuum_max_parallel_workers) and picks tables by a score, shown in pg_stat_autovacuum_scores.
  • Async I/O workers now scale automatically between io_min_workers and io_max_workers, and lz4 is the default TOAST compression. RADIUS auth is removed, and md5 logins now trigger warnings.

Takeaway. If you do get-or-create or route reads to replicas, replace the DO NOTHING + SELECT pattern with ON CONFLICT DO SELECT, and replace sleep-and-retry reads with WAIT FOR LSN. Before upgrading, benchmark analytical queries now that JIT is off by default.

SuperEMeans combines dimension pruning with e-means to build IVF indexes 3× faster

Building IVF indexes is mostly clustering time, and this post measures the clustering speed against the search cost it adds later.

The SuperKMeans team combined their dimension pruning, which avoids scanning every vector dimension during clustering, with e-means. e-means is a mini-batch algorithm that claims Lloyd's-quality clusters in 2 epochs instead of the usual 10. The test used 5M OpenAI 1536-d vectors, about 20k centroids and a 16-core Zen 5 machine. SuperEMeans took 128 s, against 203 s for e-means and 985 s for Lloyd's. At 5 epochs it was 3.2× faster than e-means. Recall@100 was the same, but e-means clusters are less balanced, so each search scans 10–20% more vectors.

Under the hood

  • Cohere MS MARCO set (10M × 1024-d, ~40k centroids): Lloyd's took 2504 s, SuperKMeans 623 s, e-means 526 s, SuperEMeans 295 s. Recall was 0.919 vs 0.923.
  • The imbalance comes from mini-batch updates. Raising e-means' revival threshold from 0.1 to 0.3 cut the scan overhead vs k-means from 1.20× to 1.06×.
  • Hierarchical k-means did not work well combined with e-means; the author suspects the revival step. The code is in cwida/SuperKMeans, which FAISS, Zilliz and ParadeDB already use.

Takeaway. When you tune IVF clustering, compare methods by vectors scanned at a fixed recall, not by WCSS (the k-means error score). A lower error can still produce unbalanced clusters that make every query slower.

15M listening web servers on 1 core and 10GB using smoltcp

A worked example of where per-connection memory goes in the Linux kernel, and how a userspace TCP stack plus a custom scheduler cuts it to bytes per connection.

The post gets 15M (actually 16M) web servers onto one VM with 10GB of RAM and 1 core. Ports cap out at 65k, so each server listens on its own address from an AnyIP route. As processes they would need about 20TB, so they run as LFI-sandboxed guests in one runtime, with 16 bytes of saved state each. The kernel still spends ~3.4KB per socket(), idle or not, and runs out of memory around 2.5M servers. Swapping in smoltcp, a userspace TCP/IP stack, cuts that to 620B idle and ~1KB active. DPDK was fastest, with AF_XDP close behind.

Under the hood

  • Each kernel socket costs 3384B: tcp_sock 2240B, socket_alloc 768B, file 184B, dentry 192B.
  • Each guest only has to save its PC and two fds, ~220MB for 15M guests. smoltcp gets I/O through a 3-method Device trait, with xsk-rs for AF_XDP and rust-dpdk-net for DPDK.
  • AF_XDP keeps the NIC owned by the kernel and uses eBPF to pick which packets go to userspace, so SSH keeps working. DPDK detaches the NIC from the OS. The text gives no RPS numbers, only a chart.

Takeaway. At millions of mostly idle connections, kernel per-socket structs set the RAM floor. A userspace stack like smoltcp over AF_XDP lets you control that cost while keeping the NIC usable by the OS.

Tunix recipe: multi-turn GRPO takes Gemma 4 E2B from 9.4% to 95% wins

A small, complete agentic RL setup (environment, in-turn tool calls, async vLLM rollouts, GRPO) whose mechanics carry over to any tool-using agent you might train.

Google's Tunix (a JAX post-training library) trains Gemma 4 E2B in thinking mode to play Plane Strike on one Cloud TPU v6e-8. The board is a 6x6 grid with one hidden 8-cell plane, the game allows up to 23 strikes, and each move is a strike(cell=...) tool call. Out of the box the model wins 9.4% of held-out boards and averages 22.44 strikes. After 100 GRPO steps (8 boards x 8 games each) it wins ~95% in ~16 strikes. GRPO (Group Relative Policy Optimization) scores each rollout against the others in its group. A seeded environment makes all 8 rollouts in a group play the same board.

Three mechanics are worth copying. First, <|tool_response> is a stop token: generation pauses mid-turn, the board comes back as a tool message, and the model carries on in the same assistant turn. Second, vLLM-TPU runs in server mode for asynchronous rollouts of uneven length, with prefix caching for the growing chat history. Third, exact_token_continuity keeps the exact token IDs across turns, so re-tokenizing the text never changes them. The limit is that every strike shares one episode-level reward. Repeated strikes only fell from 0.55 to 0.15, and the author points to per-turn credit assignment as the next step.

Under the hood

  • Four components: PlaneStrikeEnv(BaseTaskEnv), StrikeTool plus a subclassed Gemma4ChatTemplateParser, PlaneStrikeAgent(ConversationAgentBase), and GRPOLearner driven by RLEngine.
  • The agent ignores the <|channel>thought...<channel|> reasoning block; an action counts only if the final answer has exactly one valid strike call, otherwise it returns INVALID_ACTION.
  • GRPOConfig: loss_algo="gspo-token", advantage_estimator="rloo" (leave-one-out baseline); LR 2e-6 decaying to 2e-7; actor, reference and rollout workers share the 8 chips.
  • Tool-call rate reached ~100% and invalid moves ~0 before win rate rose; the training win rate began at ~0.20. Code: github.com/windmaple/planestrike-gemma4-rl.

Takeaway. In multi-turn RL, keep the token IDs the sampler produced instead of re-tokenizing the transcript, and make the tool-response marker a stop token so tool output lands inside the model's turn. Also give every rollout in a group the same seed, so advantages compare policies, not luck.

Learn · today's concept

GRPO: group-relative advantages without a critic

PPO-style RL for language models needs an advantage for each sample, which says how much better this output was than expected. Classic PPO gets that 'expected' value from a learned critic, usually a second network as large as the policy. That costs memory and is hard to train when the only reward arrives at the end of a long answer or a long tool-using episode. GRPO (Group Relative Policy Optimization) drops the critic. It uses the other attempts at the same prompt as the baseline.

Step by step: for each prompt, sample a group of G completions from the current policy and score each one (r_1..r_G). Compute A_i = (r_i − mean(r)) / std(r) and give that same advantage to every token the model generated in completion i. Then optimize PPO's clipped ratio objective, usually with a KL penalty that keeps the policy close to a reference model. In multi-turn agents, tool output tokens are masked out of the loss, because the model did not generate them. Example: with G=4 and binary rewards 1,0,0,1, the mean is 0.5 and the std is 0.5, so the advantages are +1, −1, −1, +1. If all four attempts fail, every advantage is 0 and that prompt teaches nothing.

Trade-offs: GRPO saves the critic's memory and its instability. In exchange it needs several rollouts per prompt, it wastes compute on groups where every attempt gets the same reward, and it spreads credit evenly across all tokens. Dividing by the std also gives very easy and very hard prompts more weight, and some variants drop that step. Use GRPO when rewards are verifiable and come at the end of an episode, and pick tasks the policy sometimes solves. Fix the environment seed within a group so that differences in reward come from the policy, not luck.

Further reading: DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models (Shao et al., 2024), the paper that introduced GRPO; Proximal Policy Optimization Algorithms (Schulman et al., 2017)

DeepMind's Genie 4 world model ships, with Gemini acting as its in-loop planner

A frontier world model now has an API, and its design puts a language model in charge of planning and checking the pixel generator.

Google DeepMind's Genie 4 is a real-time interactive world model. It is rolling out to Google AI Ultra subscribers in Project Genie. As of Nov 19, developers can also use it through the Gemini API (the Interactions API) and AI Studio. It generates 720p, 24fps worlds from text, an image or both, and creates the audio itself, including character dialogue. The most interesting part is the control loop. Under the hood

  • Planner loop: Gemini watches the scene, breaks goals into steps, checks progress against new frames and replans when the user steps in.
  • Robotics experiment: Gemini 4 Argon splits a task into steps, which are fed to Genie 4 as text captions while it renders.

  • HN: commenters complained that eligibility is unclear (Workspace and UK accounts still show Genie 3) and there is no public demo. One test proposed: spin 360 degrees and see if details stay the same.

MaxText adds Streaming DiLoCo for training LLMs across slow cross-datacenter links

It shows how to replace one large periodic sync with a steady per-step stream of fragments, cutting cross-slice traffic 65x with no loss in model quality.

MaxText, Google's JAX-based training framework, now includes Streaming DiLoCo. Each learner, such as a TPU slice, runs H local AdamW steps. The learners then average their weight deltas and apply them with an outer optimizer, SGD with Nesterov momentum. The streaming version splits the model into P = layers + 1 fragments and syncs one fragment per step, picked in interleaved depth order. That turns a 65.5 GB spike into about 1 GB per step. In the test, Qwen3-32B trained on 2× v5p-32 slices over a 10 Gbit/s link. Step time was 5.76 s, against 55.11 s for data parallel and 7.55 s for vanilla DiLoCo, with matching loss.

Under the hood

  • Fragment deltas go to sharded syncer workers on the host CPUs. These run the all-reduce and the outer Nesterov update in the background while the TPUs keep training.
  • Each learner's local AdamW moment buffers are left alone at sync time, so it keeps its optimizer momentum. Large embedding and output-head matrices are spread across the layer fragments to avoid a traffic spike.
  • On MoE models (Qwen3-30B-A3B and Gemma4-26B-A4B, 4,000 steps), it tracks data-parallel loss after about 800 steps and ends slightly better. Settings: outer LR 0.3–0.7, momentum 0.9. Ships in MaxText v0.2.5.

Takeaway. When state has to be synced in bulk every so often over a thin link, split it into fragments and sync one each step, so bandwidth use stays flat. Run the sync off the critical path, and keep each worker's local state warm between syncs.

Stripe's coding-agent evals: 78% on average, 29% when every required check must pass

An eval design worth copying: an LLM plays a developer with hidden needs, each criterion gets its own judge, and a strict pass rate shows how often agents fall short on the final details.

Stripe ran 69 integration scenarios (one-time payments, subscriptions, Connect) on 14 model/harness pairs (Claude Code, Codex, OpenCode), each with and without its agent plugin (MCP tools plus skills). A second LLM plays the developer. It holds a fixed, hidden list of 2–6 needs and asks about one unresolved need per turn. Separate judges score each criterion against MUST/SHOULD rubrics, using the transcript and the final workspace. The plugin raised every pair by 3–8 points and cut web searches 96%. Requiring all MUST criteria drops the average from 78.1% to 29.4%. The harness is open source as Forge.

Under the hood

  • GPT-6.1 Sol served as both roleplayer and judge. A probe with Opus as judge showed it was uniformly more lenient, with no bias toward OpenAI models. Each judgement weighs five candidate readings of the criterion (verbalized sampling).
  • With the plugin, outdated API parameters fell from 7% to 1.3%; e.g. removed payment_method_types became automatic_payment_methods: { enabled: true }.
  • Final-step failure: Opus 5.5 shipped orders after checking only PaymentIntent.status === 'succeeded', so refunded or disputed orders could still ship. Best strict pass rate: GPT-6 Astra, 52.9% with the plugin.
  • Limits: no runtime check, so code that looks right but does not work can score full marks. Runs that hit the 45-minute timeout are left out of the score.

Takeaway. When you eval an agent, report a strict all-required-checks pass rate next to the average criteria score. Give each criterion its own judge call, and keep the simulated user's needs hidden from both the agent and the judges.

Baseten brings deferred tool loading to open models and reports 51–62% lower agent cost

Loading tool schemas only when needed shrank a Claude Code prompt from ~141k to ~1.3k tokens. That changes what an agent costs to run.

Baseten added server-side deferred tool loading for DeepSeek, Kimi and GLM on its Model APIs, in both Chat Completions and Messages formats. Claude Code and Codex turn the feature off when pointed at third-party open-model providers. With it, the client sends only tool names plus a tool_search tool. When the model searches, the server adds the matching schemas at the end of the transcript, so the KV cache (stored attention state) for the prefix stays valid. With three MCP servers, the per-request prompt fell from ~141k to ~1.3k tokens.

Under the hood

  • Test setup: 55 tasks from 8 benchmarks, run headless in Claude Code with GLM 5.3, with and without deferred loading.
  • Coding tasks (Terminal-Bench, SWE-bench Verified/Pro v2, DeepSWE) with Slack, Notion and Baseten MCPs: 62.5% cheaper, 26.2% faster on average.
  • Agentic tasks (MCP-Atlas, AutomationBench, ComplexMCP, Toolathlon-GYM): 51.1% cheaper, 14.9% faster, even with repeated tool searches.
  • Caching the prefix does not remove the cost: each decoded token still attends to all ~141k cached schema tokens in eager mode.

nginx2root: five nginx memory bugs, worst one a broken HTTP/2 window invariant

If you run nginx with HTTP/2 enabled, you need to patch now, and the root cause is a clear example of a broken invariant that a cheap assertion would have caught.

On November 18, F5 and nginx.org disclosed nginx2root, five memory-corruption bugs found by Xint. If an attacker bypasses ASLR (address randomization), each one gives unauthenticated code execution as the nginx worker. The worst is CVE-2026-123007, which affects every release since 1.9.5 and needs only HTTP/2 turned on. When a stream is cancelled, nginx refunds window credit for DATA frames that were queued but never sent, and that refund skips the 2^31−1 cap. Once the window is over the cap, the unsigned subtraction in the cap check wraps, so every later WINDOW_UPDATE is accepted. A frame length above 2^63 then reaches memcpy(). The other four bugs are use-after-frees in event-handler paths. Cloudflare says origins reachable only through its proxy are safe from the HTTP/2 and HTTP/3 bugs. You should still patch to 1.30.7 or 1.31.9.

Under the hood

  • Known exploits send about 2^33 WINDOW_UPDATE frames (~112 GB). Censys reached the corrupted window state with a 5.69 MB capture, so asserting the window cap after every frame would have caught it.
  • CVE-2026-123633: a connection with a partial HEADERS frame stayed marked reusable. When worker_connections ran low, the drain could close the same connection whose request was asking for an upstream slot. The fix is 2 lines.
  • Xint also found a Linux kernel SCTP use-after-free, present since 4.15, that gives root from inside Docker. There is no kernel fix yet. Block the module with install sctp /bin/false in modprobe.d, and restart nginx after patching because a reload keeps the old binary.

Takeaway. Write invariants such as "window ≤ protocol max" and "a connection with a live request is never reusable" as assertions in tests and fuzzers, so a bad state is caught when it happens instead of only when memory is corrupted.
