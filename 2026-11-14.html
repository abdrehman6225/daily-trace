Evolved memory programs beat Mem0 and Zep by keeping raw turns

Why read · An evolutionary search over whole memory programs found two design rules that you can test directly in a production memory engine.

Xinheng Ding, Seyyed Saeid Cheshmi, Ziyang Zhang, Tairan Chen, Wenya Xie, Yu Hou, Rui Zhang, Zirui Liu et al.

MAPE, from a University of Minnesota group, evolves complete agent-memory programs starting from trivial seeds: no memory at all, or the full context. Each candidate implements a Python interface with build, retrieve and an optional compose stage, while the answering model stays fixed. An LLM proposer writes each change together with a stated hypothesis. A separate diagnosis agent reads the execution traces, and every candidate is kept in an archive. Search runs on accuracy alone or on an accuracy–cost Pareto frontier (the set of candidates that no other candidate beats on both accuracy and cost). On LoCoMo with GPT-4.1 mini, the best accuracy-only program scores 87.94% and the best cost-aware one 85.18%, at about 28% of the cost. On LongMemEval with Qwen3-30B-A3B the best program reaches 77.00%, against 66.00% for plain RAG, the strongest baseline.

Two patterns kept recurring. The first is keeping raw conversation turns as retrievable evidence. Removing them costs 12.17 points on LoCoMo. The second is query-routed scaffolding (RQS): it classifies the question's intent and pairs LLM extraction with deterministic code, such as date arithmetic or counting. Added to Mem0, A-Mem, LightMem, SimpleMem and Zep, RQS gained 2.75–9.25 points on LongMemEval. Adding cost to the objective moved computation from build time to query time. Limits: only two conversational QA benchmarks, and one to three runs per setting.

Under the hood

  • After a backbone swap to Qwen, temporal accuracy for the accuracy-only program fell from 79.84% to 43.80%, while the cost-aware program, which resolves dates to absolute values, kept 70.93%.
  • The cost-aware LongMemEval program uses BM25 over raw text with zero build-time LLM calls and needs 90% fewer serving calls than the accuracy-only version.
  • In the accuracy-only LongMemEval program, per-session note extraction at build time was about 92% of serving cost.
  • Mem0 gained least from RQS (+2.75) because most of its errors come from missing retrieved evidence, which RQS cannot fix.

Takeaway. Index the raw turns alongside the extracted facts and return both at query time. Do date and count arithmetic in code, chosen by query intent, not in the answering model.

The importance ratio and clipping in PPO/GRPO, and why one update per batch disables them

Policy-gradient RL for LLMs samples rollouts from the current policy, scores them, then updates the policy. To reuse one batch for several gradient steps, PPO has to account for the policy drifting since the batch was sampled. It weights each token's loss by the importance ratio r = π_θ(token) / π_old(token). Large ratios make updates unstable, so PPO clips them. The objective is min(r·A, clip(r, 1−ε, 1+ε)·A), where A is the advantage (how much better this sample was than expected). Once the policy has moved more than ε in the direction the advantage favours, that token stops contributing gradient. This is PPO's trust region.

GRPO removes PPO's value network (the critic). For each prompt it samples a group of answers, scores them, and uses each reward's z-score within the group as the advantage. Example: four rollouts score 1, 0, 0, 1. The mean is 0.5 and the standard deviation is 0.5, so the advantages are +1, −1, −1, +1. Take ε = 0.2. Suppose an earlier step on the same batch raised a token's probability from 0.40 to 0.50. Then r = 1.25. With A = +1 the term is capped at 1.2, so that token stops pushing the policy further. Computing π_old means storing log-probs for every rollout or running an extra forward pass.

The catch: on the first step for a batch, θ equals θ_old, so r = 1 exactly and the clip never activates. With one gradient step per batch, the PPO/GRPO loss reduces to plain REINFORCE with group-normalised advantages, and there is no trust region at all. Several epochs per batch give better sample efficiency and a working clip, but cost compute and train on increasingly stale data. One step per batch is cheaper and fully on-policy, but you need some other brake: a KL penalty to a reference model, or a gate like LGPO's stop-gradient on high-likelihood sequences. If you reuse rollouts, clipping is your trust region. If you don't, add another one on purpose.

Further reading: Schulman et al., "Proximal Policy Optimization Algorithms" (2017); Shao et al., "DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models" (2024), which introduced GRPO

600 Push-T runs show LeWM's limits come from planning, not prediction

Why read · On LeCun's LeWM, planning changes with no retraining moved long-horizon success from 22% to 85%. Swapping in perfect physics barely mattered.

Haddy Alchaer ran 600 experiments on LeWM, the JEPA world model LeCun co-authored, on Push-T. LeWM encodes frames to embeddings, predicts the next embedding from an action, and searches action sequences for the plan that ends closest to the goal embedding. Replacing the predictor with exact simulator physics changed almost nothing: 78% vs 77% on 75-step tasks given expert subgoals. Without retraining, chaining 25-step subgoals (LeWM's reliable horizon, 89.7%) beat perfect physics on unsplit plans three to one. A graph over ~460k embedded demo states, with a cost on every cross-demonstration jump, produced its own subgoals and reached 85%, matching expert subgoals.

He also shows the standard test is easy: 84% of goals have near-duplicates in memory, and LeWM scores 68% on the official 50 episodes but 44% on 250 fresh ones. On his harder cross-demo test, shifted, rotated or mirrored demo segments lift the graph planner from 45% to 56%. Goal images also fix the pusher's position. Scoring against 16 pusher variants doubled LeWM's success, 11%→23%. HN commenters call this MPC (model predictive control) with a latent model, note that subgoal hierarchies are well known, and question evaluating on goals taken from demonstrations.

Under the hood

  • Exact physics added ~20 points on 75-step tasks. 25-step segmentation added ~60. Four planner restarts cost 4x compute for under 1 point.
  • Embedding distance ranks a reachable subgoal (within 25 steps) closer than an unreachable one 87% of the time, so latent distance roughly tracks reachability.
  • Without a jump cost, 318 of 1,015 plans used six or more cross-demo jumps. With the cost, success rose from 62% to 85%.
  • Exact-physics planner with the pusher left out of the cost: 30 of 50 tasks went from failure to success, none the other way.

Takeaway. Before retraining an agent's model, check whether the planner, the memory coverage or the goal cost is the real bottleneck. Define goals as sets of acceptable end states, and penalize shortcuts in any retrieval graph.

Gemini 4 Hydrogen ships with Orchestrator, a mid-task model switcher for Antigravity

Why read · Google's new fast tier claims Argon-level scores at $1.50/$7.50 per million tokens, and its Orchestrator shows a planner/executor handoff design you can copy in your own agent harness.

Google DeepMind released Gemini 4 Hydrogen, the fast execution tier below its frontier models Carbon and Argon. It replaces 3.8 Flash in the API, AI Studio, Search and the Gemini app. The model card says only that it is "adapted from Gemini 4 Carbon". It gives no parameter count, architecture or training recipe beyond SFT plus RL post-training. Specs: a 1M-token window shared by input and output, 64K synchronous output tokens (up to 1M via "background long decode"), four thinking levels (low, medium, high default, new xhigh), and a knowledge cutoff of March 2026. Pricing is flat across the whole window: $1.50 per million input tokens, $7.50 per million output. On the Artificial Analysis Intelligence Index it scores 51 at high (Argon scores 50) and 54 at xhigh.

The part that matters for agent work is Orchestrator in Antigravity, Google's agentic coding app. Static model routers guess difficulty from the first prompt and send the whole task to one model. Orchestrator instead switches between models in both directions inside a single trajectory. Carbon explores read-only and writes a plan with explicit re-planning triggers. Hydrogen then edits code and runs tests, and hands back to Carbon when it hits friction. On Terminal-Bench (4.0 in the main post, 4.1 in the Antigravity post) Orchestrator came close to Carbon's success rate while using 24% less quota and finishing 19% faster. Against 3.8 Flash, Hydrogen scores 57% vs 18.2% on Terminal-Bench 4.1, finishes tasks 2.5x faster, and makes more than 5x fewer fabricated claims. It also batches file reads and searches in parallel natively.

Caveats: every number is vendor-reported, and some benchmarks are Google's own and new (MKA). The model card shows unjustified refusals up 5.57pp from 3.8 Flash. On HN, commenters criticised the naming. One worried that pricing matches undiscounted 3.8 Flash, which would hollow out the cheap tier once the discount ends at year end. Another reported repeated automated suspensions of the agy command-line tool with no human support. One tester rated its image-to-HTML output between Sonnet 5.5 and Opus.

Under the hood

  • Partners report 2x–2.8x faster runs and 12–23% fewer tokens than 3.8 Flash on graph, SQL and data-heavy workflows, credited to parallel tool-call batching.
  • Parallel mode: Carbon acts as coordinator while Hydrogen runs worker and verifier agents in isolated workspaces; the Antigravity SDK lets you assign roles to models explicitly.
  • Other claimed scores: HLE-Diamond 58.8%, Vals Tax Agent Bench 52.3% (#1), MKA 53.4%, Agents' Last Exam v1.1 71.6%, #5 on Agent Arena.
  • Agent safety claims: up to 81% less overreach, 12x fewer misaligned actions, 94% on an internal honesty eval, 2.3x more resilient to prompt injection on the Gray Swan IPI benchmark.
  • Frontier Safety: below the CBRN-bio and cyber CCLs (critical capability levels) but past their alert thresholds; the full safety report is "coming soon".

Takeaway. Don't route a whole agent task once at the start. Let a strong model plan read-only with explicit re-plan triggers, let a cheap model execute, and hand control back when the executor fails. Treat the benchmark numbers as vendor claims until independent evals appear.

smolmaxxing: an 80B MoE model on a phone by paging experts from flash

Why read · The repo treats RAM as a cache for mixture-of-experts weights, which lets 16B models run on 1 GB devices, and every speed was measured on the device itself.

smolmaxxing is a set of llama.cpp patches for running large models on small, old devices. The main trick is an expert pager for mixture-of-experts (MoE) models, which use only a few experts per token. Popular experts stay in RAM, the rest are read from flash when needed, and the next layer's experts are prefetched. With about 1 GB usable, a Xiaomi TV box runs the 16B Ling-mini-2.0 at 5.1 tok/s and a 2013 iPad Air runs it at 2.6–4.5 tok/s. A OnePlus phone with about 3 GB free runs Qwen3-Next-80B-A3B at 2.6–3.1 tok/s.

Under the hood

  • Custom kernels: a 1-bit lookup-table kernel that needs only basic NEON, repacked 2-bit and ternary formats for Cortex-A55, and versions for the A7, which has no dot-product instructions.
  • Rarely used vocabulary output rows are dropped to save RAM. Dense models stream poorly: an 8B dense model runs at 0.08 tok/s on the iPad, against 3.5 tok/s for an 8B MoE.
  • EXPERIMENT.md logs all 165 experiments, failures included. On HN, one commenter argued that frontier agents can now write engines like this from one prompt, and another asked what such small models are useful for.

Takeaway. Sparse access patterns turn a memory limit into a caching problem: keep the hot set resident, page the rest from slower storage, and prefetch what you can predict. The same design works for agent memory tiers.

Brave Search API lets agents pay per request over HTTP 402

Why read · This is a working example of an agent paying for a tool with no API key or account, though Hacker News commenters report almost no real traffic for x402 so far.

Brave's x402 endpoints take a payment on every request instead of an API key. An unpaid request gets HTTP 402 Payment Required back, with the price and payment details. The agent signs a USDC payment for that amount and retries with it attached. Brave runs its own facilitator (the service that verifies payments), checks the payment, runs the search and returns results with a receipt from the Base blockchain. On HN, one operator who added x402 to a heavily crawled site has seen zero transactions. Others think $5 per 1,000 searches is expensive for agents that search a lot.

Under the hood

  • Price is $0.005 per request ($5 per 1,000), the same for LLM Context (search context for agents), web, news, image, video and local.
  • Payments are USDC on Base for now. Brave says other networks and stablecoins are coming soon, and it covers gas fees for a limited time.
  • The suggested client is Purl, a CLI wallet built by Stripe. You fund it with Base-native USDC and query without a Brave account.
  • HN cost example: a ChatGPT session with 30 web searches would cost $0.15 at this price.

Takeaway. If your agent harness calls paid tools, handle 402 by reading the quoted price, checking it against a budget and retrying with payment. Because cost is now visible per call, track and cap spend per call rather than per account.

Pressler: why program verification has inherent cost, from halting to model checking

Why read · If you expect agents, or Lean, to make correctness cheap, these complexity results show where that hope runs out.

Ron Pressler's 2016 essay, based on his Curry On talk, collects results showing that verification cost is inherent. Bounded halting (does a program halt within n steps?) is Θ(n): you cannot learn what a program does faster than running it. Total languages don't help. Model checking succinct programs is PSPACE-complete, no easier than checking the expanded state graph. A 2005 paper shows modular verification isn't tractable either: correctness doesn't decompose. On HN, commenters said the essay overstates Rice's theorem: one-off proofs and sound over-approximation such as type systems still work.

Under the hood

  • A 10-line C/Java function, with every loop on a decrementing counter, reaches crash() only if Goldbach's conjecture is false. Nobody has managed to prove it never crashes.
  • Stefan O'Rear built a 1919-state Turing machine whose halting cannot be proven in ZFC, about the size of a 100–200 line Python program.
  • Checking finite-state machines against temporal logic costs O(|φ||S|) for CTL and 2^O(|φ|)·O(|S|) for LTL, so cost grows linearly with state count.
  • An int return type proves only a trivial property: the program never terminates or returns something readable as an integer.

Takeaway. No language or tool makes every program cheap to verify. Pick the few properties that matter, check them with sound abstractions such as types, model checking of small state spaces, or abstract interpretation, and test the rest.

Anthropic's playbook for safety evals: right constructs, checked graders, honest stats

Why read · The same discipline applies to any agent or memory eval you build: simulated multi-turn users, binary rubrics, LLM graders checked against humans, and confidence intervals.

Anthropic applies psychology's replication-crisis fixes to safety evals. First, choose the right construct, meaning the thing the eval is really meant to measure. Refusal rate is the wrong one for self-harm, because refusing a user in crisis is itself a failure. Instead they score an appropriate response rate against rubrics written by domain experts, and one bad turn fails the whole conversation. Single-turn suites pair harmful prompts (goal: answer harmlessly) with benign prompts in the same domain (goal: don't refuse). For multi-turn tests, an expert writes a spec covering the user's objectives, tactics, persona and tone. The first user turn is fixed, a separate Claude plays the user and samples from the spec on each run, and a grader model applies the rubric.

LLM graders get yes/no criteria and are told that disclaimers don't make harmful content harmless. They never see how the test was built, and they come from a different model than the one under test. They are checked for bias toward longer answers and toward whichever option is shown first, and they are validated against human labels using chance-corrected agreement. Write down the metrics and thresholds before running anything (preregistration), and use paired comparisons on the same items. Minimum sample sizes are 100 items for multi-turn evals and 1,000 for single-turn.

Under the hood

  • Single-turn harmless response rates sit at 94–98% for every recent model, so these suites are saturated and now serve mainly as regression checks.
  • Confidence intervals on multi-turn API evals can be wider than ±10 points. Opus 5 scored 98% and Opus 5.5 scored 94% on romance scams, and the gap was not significant.
  • Configuration matters: API and claude.ai scores differed by up to 34 points. One self-harm system-prompt mitigation took the score from 60% on the API to 94% on claude.ai.
  • When a grader breaks, the item must be flagged and excluded, not silently scored. Grader agreement with humans is judged against how well humans agree with each other.

Takeaway. For your agent or memory evals, do three things first: name the construct before collecting data, validate the LLM judge against blind human labels using Cohen's kappa, and report confidence intervals from paired per-item differences.

vLLM · 1 min

vLLM serves Inkling 2 Small: 594B MoE, ~630 tok/s per user at TP4

Why read · A production write-up with numbers on making a new architecture fast: fused collectives, sequence-parallel prefill, and a decode kernel fix that cut step time by about 3x.

Thinking Machines' Inkling 2 Small is a mixture-of-experts model with 594B total and 17B active parameters: 48 layers, 384 experts with top-8 routing, text and image input, 1M-token context. vLLM supports it from day 0. Expert weights are NVFP4 in layers 0–39 and MXFP8 in layers 40–47, so the model fits on one node. The model uses block attention residuals: a learned query mixes the outputs of earlier 6-layer blocks. As a result, every sublayer boundary needs an all-reduce plus four memory-bound ops, and vLLM fuses all five into one kernel. With the bundled DSpark draft model, which proposes 7 tokens per step, a single user gets about 630 tok/s at TP4, with an average of 3.5 drafted tokens accepted per step.

Under the hood

  • Decode kernel: the 6:1 query-to-KV head ratio silently turned off FlashAttention-4's head packing. A new Gluon kernel packs 6 heads per tile and cut batch-1 decode at 100K context from 15.1 to 4.8 ms.
  • Prefill sequence parallelism: reduce-scatter, run the fused conv_mix on each GPU's slice of tokens, then all-gather. An 8K prefill is 22% faster at TP4, 26% at TP8, and 1.3–1.9 GiB per GPU is freed for KV cache.
  • Agentic benchmark at TP8 with prefix caching, at 100 tok/s per user: about 1,070 output tok/s per GPU at 32K context (91% cache hits), about 450 at 256K (99% cache hits).

Takeaway. When a model's head layout changes, check that your attention kernel's fast paths still run, because they can turn off without any error. Fuse the memory-bound ops around collectives into one kernel, and shard them by sequence during prefill so every GPU isn't repeating the same work.

Google Developers · 1 min

Google's A2UI 1.0: agents describe UI in a compact DSL, apps render it natively

Why read · This is a stable protocol for agent-generated UI, and its trick of having the model write a compact format that the server compiles to the wire format carries over to any structured-output agent.

Google released A2UI 1.0, the first stable version of its open protocol for generative UI. The agent sends JSON describing which components to show, and each app draws them with its own registered components. Renderers exist for React, Angular, Lit, Flutter and SwiftUI. Agent SDKs exist for Python, TypeScript and Dart. Per the inference-formats docs, the model writes Express, a compact positional DSL (Card(Text($/flight/gate))), and the server compiles it to wire JSON. On a 54-sample suite with gemini-3.8-flash, input tokens fell from 10,980 to 6,000 and output from 807 to 297, with pass@1 unchanged at 98.1%.

Under the hood

  • The server compiler repairs half-finished strings as the model streams, assigns deterministic component IDs and validates each message. Invalid output goes back to the model to fix.
  • 1.0 adds two-way RPC: the agent calls the renderer with callRendererFunction and the renderer calls the agent with callAgentFunction. Each function's catalog entry sets allowedCallers, checked at runtime.
  • Components from several catalogs can now share one surface, and createSurface can carry the whole component tree plus data in one message. Data binding happens on the server, so sensitive values never reach the model.

Takeaway. If your agent emits structured output, let the model write a short, model-friendly notation and compile it server-side into the strict format. Validate the result and send errors back to the model. That roughly halved input tokens here, with no loss in accuracy.

vLLM moves the multimodal encoder to its own tier and stops prefill re-preprocessing media

Why read · A working example of splitting one stage out of a serving pipeline, with per-GPU numbers that show where the split pays off and where it loses.

vLLM's encoder/prefill/decode (EPD) disaggregation runs the multimodal encoder as a separate instance and sends its embeddings to prefill through EC connectors (NIXL, Mooncake). New in v0.32.0 are metadata-only requests: the encoder returns layout data such as image_grid_thw, so prefill no longer fetches and preprocesses the media again. On Qwen3-Omni audio, this raised throughput from 62.21 to 73.13 req/s. Mooncake Store now lets encoders share outputs. On DeepSeek V4.1 Flash (GB200), EPD gave 6.6–9.5% more throughput per GPU and 44–47% lower P90 TTFT at concurrency 64–128. At concurrency 16 it lost.

Under the hood

  • Cross-encoder reuse (6×H20, InternVL3_5-38B, 2E+4PD): repeated encodings fell from 512 to 0 and TTFT p50 from 1.209 to 0.819 s. This was a single best-case run.
  • Encoder-only instances skip language-model checkpoint shards. On a pruned Kimi-K3 checkpoint, the encoder read 2 of 96 shards and weight loading dropped from 683 s to 0.31 s.
  • Transfer buffers are sized from output widths measured per modality (Qwen3-Omni: 8192 visual, 2048 audio). A consumer holding only metadata fails just the affected request instead of crashing EngineCore.

Takeaway. When you split a pipeline stage, send downstream the structure the upstream stage already computed, not the raw input. Count every GPU, including the new tier, when you benchmark. Here the split only paid off at higher concurrency.

How Cloudflare turns Workers usage into hard spending caps

Why read · A metering-to-enforcement pipeline that keeps rating off the request path, and a pattern you can reuse for per-tenant or per-agent budgets.

Cloudflare launched Spend Management in beta for pay-as-you-go accounts, starting with Workers and Durable Objects. You create a policy with threshold_cents, action: usage_block and optional alert thresholds through the dashboard, the cf CLI or the REST API. When spend reaches the cap, new billable invocations are rejected. That includes Cron Triggers and Queue consumers, but static assets keep being served. Spend shows up in under 10 minutes. The billing cycle starts on the subscription date, not the calendar month. Every limit change is recorded in an audit log.

The pipeline aggregates in two stages. Metering parsers group events into one-minute buckets, and a second service merges those into five-minute windows and archives them for reconciliation. The Usage Engine partitions work by account, and each partition keeps local state plus a write-ahead log (WAL, a durable record of changes). Allowances and accumulated spend for an account stay in one place, so no coordination across partitions is needed. The Rating Engine joins usage, subscription data and a pricing catalog. It prices accumulated usage after allowances are applied, rather than rounding each request. Enforcement is asynchronous: caps are written to Quicksilver, Cloudflare's globally replicated key-value store, and the runtime picks them up on a periodic refresh and enforces them using local state.

Under the hood

  • Usage and subscription updates arrive as separate, unordered streams. Usage that has no subscription data yet is held as pending, not treated as free.
  • The Rating Engine never sits in the request path. Caps travel through the existing runtime account-limit system and Quicksilver.
  • To resume service: raise the limit above the spend so far, disable or delete the policy, or wait for the next billing cycle.
  • Planned: enforcement in under a minute, and agent or app tags carried from the runtime to the Rating Engine so one task can be paused across products.

Takeaway. For usage caps, aggregate near the source, keep each tenant's pricing state together in an account-partitioned processor with a WAL, and push decisions to a replicated config store that request handlers read locally. Hold usage you can't price yet as pending instead of dropping it.

Cloudflare open-sources Kitesurf, its browser for agents that runs on Workers

Why read · You can now self-host a CDP-compatible agent browser that uses about one-sixth of Chrome's memory, if you can live with slower renders.

Cloudflare has released Kitesurf under Apache 2.0. It is a browser for agents that runs entirely on Workers, with no browser container. HTML parsing, DOM and layout come from Blitz and CSS from Stylo, both Rust compiled to Wasm. Page JavaScript runs in Dynamic Workers isolates (sandboxed isolates spawned at runtime), with the Boa engine as a fallback for eval. It speaks CDP (Chrome DevTools Protocol), so Puppeteer connects directly. Self-hosting needs the Workers Paid plan. Cloudflare's benchmark page (38 pages, median of 5 runs) puts screenshot CPU at 387 ms against 767 ms for a cold Chrome, and memory at 50 MiB against 329 MiB. Wall time is worse, 1.79 s against 1.01 s, and up to 7x slower on heavy news sites.

Under the hood

  • Engine holds CDP sessions and is the only stateful part. PageRenderer is stateless and called via Workers RPC renderFrame(), so it can be killed and retried.
  • All network access goes through one SandboxOutbound worker. It enforces CORS, keeps a separate cookie jar per page, and returns 403 on policy failures.
  • It passes 215,000+ Web Platform Tests. It cannot yet handle video, WebGL, TLS-fingerprint bot challenges or long authenticated sessions.

Takeaway. For bursty jobs like screenshots and HTML extraction, cost is driven by CPU and memory per session more than wall time. Point an existing Puppeteer or MCP harness at a local Kitesurf (pnpm run dev) and measure your own target sites before switching.

Meta Engineering · 1 min

Meta's TLX adds explicit warp-group control to Triton kernels

Why read · It shows how to give Hopper and Blackwell GPU kernels explicit producer/consumer pipelines while keeping Triton's Python and autotuning, and Meta runs it in production.

Meta's TLX (Triton Low-Level Extensions) adds a layer to Triton in which the warp group, not the thread or the block, is the unit you program. Plain Triton still says what to compute. Inside tlx.async_tasks, you assign roles: producer warp groups do async TMA (Tensor Memory Accelerator) loads, consumer groups run async_dot into TMEM (tensor memory), and epilogue groups write results. They hand off through mbarriers. Layouts are inferred unless you override them, which makes fusion easier. In production it reached 20–25% end-to-end MFU training the GEM ads model on several thousand Blackwell GPUs.

Under the hood

  • IKBO stops copying the shared user features once per candidate in RecSys inference. Its TLX linear-compression kernel is 4x faster on H100, and the attention path cuts compute-intensive latency by up to two-thirds.
  • GDPA, a single kernel that merges GEM's attention-like ops, is up to 2x faster on the forward pass. A TLX distributed grouped GEMM for MoE runs continuously in LLM pretraining.
  • Targets NVIDIA Hopper and Blackwell and AMD MI300 and MI350x. Planned next: MTIA support, auto-generated warp-group annotations, and a torch.compile backend.

Takeaway. When a kernel is memory-bound, first look at overlapping loads and compute across warp groups and at fusion, not at compute. TLX lets you try that without leaving Triton.

LGPO drops GRPO's importance ratio and keeps a trust region by gating likelihood

Why read · This NeurIPS 2026 paper removes the old-policy forward pass from GRPO-style RL, cuts epoch time by about 18%, and fixes a collapse that happens when each rollout batch gets only one gradient update.

Shuibai Zhang, Junhyuck Kim, Gyeongman Kim, Jaewoong Cho

Researchers at KRAFTON and UW–Madison separate the two jobs of the importance ratio in GRPO. One is a correction weight for training on slightly stale samples. The other is clipping, which acts as a soft trust region: a limit on how far one update can move the policy. In Qwen2.5-3B Countdown runs, removing the correction did no harm, but removing clipping made training unstable. With one update per rollout batch, the ratio is always 1, so clipping never fires and GRPO collapses. LGPO instead zeroes the gradient of any sequence whose mean token log-likelihood under the current policy exceeds τ=-0.15. It matches GRPO, stays stable in that one-update setting, and trains an epoch in 2.85h versus 3.37h.

Under the hood

  • Theory: for a probability change δ on a sampled outcome with probability p, the minimum KL cost is δ²/(2p(1−p)), largest near p→1. Hence the gate skips very confident sequences; set τ around the top 10–20% likelihood quantile.
  • Ablations: random dropping at LGPO's rate collapses within 100 steps, as does gating only positive-advantage samples. LGPO gates 24.7% of Countdown tokens: 48.9% zero, 45.1% negative, 6.1% positive advantage.
  • The 18% speedup is measured against verl's default, which recomputes old-policy log-probs because vLLM's differ numerically. A 0.001 KL penalty did not save GRPO with one update per batch. Tested only on 1.5B–3B Qwen2.5 models, with up to 16 updates per batch.

Takeaway. If your RL loop does one gradient update per rollout batch, PPO/GRPO clipping is doing nothing. Add a stop-gradient mask on high-likelihood sequences, including those with negative advantage, before you add a KL penalty.

arXiv (AI/ML) · 2 min

NOPO: reinforcement learning from verifier failures only, never from passes

Why read · If your RL reward is a partial check like unit tests, schema rules or an LLM critic, rewarding passes can reward shortcuts, and this paper shows a way to train on failures alone.

Jiacheng Xu, Shuo He, Fuxiang Zhang, Chaojie Wang, Bo An

NTU and Skywork AI (NeurIPS 2026 spotlight) name the case where a failed check proves an answer wrong but a pass proves nothing one-sided verifiability. Before RL, 20–78% of passes were actually wrong. NOPO treats passes as unlabeled. It applies NPO, an unlearning loss that stops pushing once a response falls below the reference model's probability, only to failed rollouts. Each group's update is scaled by (c/G)^γ, where c of G=16 rollouts passed, so a group where every rollout failed is skipped. Qwen3-4B average pass@16 goes from 46.85 (base) to 52.86, against 48.93 for GRPO.

Under the hood

  • Qwen3-8B average pass@16: NOPO 52.13, w-Reinforce 48.84, GRPO 48.27. NOPO is first in 9 of 10 cells and loses only OlympiadBench-8B, where the LLM verifier flags just 9–13% of failures.
  • CodeContests pass@512 on Qwen3-4B: NOPO 66.95, base 51.05, GRPO 48.54. GRPO has the best pass@1 (37.23) but falls below the base model at large k.
  • Ablation: the linear weight (γ=1) beats γ=0.5 and γ=2, and also beats plain NPO and negative-only REINFORCE. Trained on CodeContests, NOPO reaches 32.12 on unseen CodeForces versus 22.91 for the base model.

Takeaway. If your reward is a partial checker, measure on a small labeled set how often its failures and its passes are actually right. If passes are unreliable, train only on failures, and skip updates for prompts where no rollout passed.

arXiv (systems) · 1 min

Raven: lakehouse catalog keeps transactional metadata in Postgres, statistics in Iceberg/Delta

Why read · The paper's design question applies to any metadata system: which parts need ACID guarantees, and which are bulky analytical data that can live cheaply in object storage.

Keonwoo Oh, Akshay Mehra, Joshua Kimball, Amol Deshpande

Researchers at the University of Maryland and Dolby Labs built Raven, a lakehouse catalog that splits metadata in two. File paths, formats and version lifetimes (start_vid/end_vid) go in PostgreSQL. Per-column file statistics stay in Iceberg or Delta Lake files. A commit is one serializable transaction that acts as a multi-row compare-and-swap, so several tables can commit together under snapshot isolation (write skew is still possible). Extended merge-on-read registers new files in the database right away and writes the table-format metadata later, during compaction. A reference-counting graph engine handles garbage collection across tables. The fetched text ends before the result numbers.

Under the hood

  • Why statistics stay out of the database: DuckLake keeps all metadata in an RDBMS and reached 109.31 GB for 100,000 files × 10,000 columns, over 99.9% of it statistics.
  • In plain Iceberg, appending one file writes three metadata files (manifest, manifest list, root JSON) and then does a CAS on the catalog. Raven drops that final CAS.
  • Garbage collection runs on a separate in-memory graph engine checkpointed to RocksDB. Clients hold TTL-leased session roots to protect the snapshots they are reading, and the schema forbids reference cycles.

Takeaway. Keep only the data that decides visibility and lifetime under ACID, and push bulky analytical data out to cheap storage. For garbage collection, combine reachability with retention windows and let readers pin what they use with leased references.

HF Daily Papers · 1 min

Meta and NYU: VLMs need vision-only parameters, not a pretrained encoder

Why read · A controlled from-scratch study tests the three things a vision encoder brings to a multimodal LLM and finds only one of them pays off.

Ellis Brown, Chris Hoang, Shengyi Qian, Shang-Wen Li, Mike Lewis, Marjan Ghazvininejad, Luke Zettlemoyer, Lucas Beyer et al. — Meta

Meta FAIR and NYU (Zettlemoyer, Lewis, Beyer, Xie) split a vision encoder into three parts: a prior from separate pretraining, parameters that only vision tokens use, and placing those parameters before vision and text tokens interact. They train every model from scratch on shared data and compare them at equal lifetime compute (all training stages counted). The prior adds nothing; an encoder trained from scratch matches pretrained ones. The vision-only parameters matter; encoder-free models trail even with 0.4B extra backbone parameters. Placement does not matter: vision-only branches in the first eight backbone layers match a separate encoder and cut time to first token.

Under the hood

  • In-fusion adds zero-initialized vision-only weights to Q/K/V/O and a vision-only FFN branch, gated by a per-token modality flag (vision or text). Text tokens never touch them.
  • Across backbones from 0.6B to 6.4B, encoder-free models need about 3x the encoder's compute to match it on VQA and caption loss. In-fusion tracks the encoder; text scores are comparable for all.
  • Putting the same vision-only budget in every layer, spread across depth, or in the last eight layers does no better than encoder-free. Only the first eight layers work.

Takeaway. If you drop the vision encoder, don't give its parameter budget to the shared layers. Spend it on vision-only attention and FFN branches in the first few backbone layers and train them jointly with the rest of the model.

HF Daily Papers · 1 min

Ant Group's UniSpark-9B uses hybrid attention for image understanding and generation

Why read · It shows a simple way to keep throwaway intermediate work out of a recurrent model's shared memory state.

Jiancheng Pan, Yuzheng Liu, Hengyuan Cao, Qiyuan Zhang, Yangyan Li, Biao Gong, Zheng Zhang, Ka Long Cheng et al. — Ant Group

Ant Group built UniSpark-9B on Qwen3.5, a backbone that mixes full-attention layers with GatedDeltaNet layers (linear attention that carries context in a fixed-size recurrent state). It adds separate understanding and generation experts, each about 9B parameters. Text is predicted token by token and images are generated by flow matching. The useful idea is how it treats a half-denoised image. That image is a private block: it can read earlier context, but full-attention masks hide it from later blocks, and the linear layers throw away its state updates. Only the finished image is written into the public state. It scores 2470.3 on MME-S and 0.83 on GenEval. The text we have cuts off before the experiments, so there are no baseline comparisons.

Under the hood

  • Public-state rule: S_pub(b+1) = R(block, S_pub) for text and clean images; private noisy blocks start from S_pub and their updates are discarded, convolution history included.
  • Training data: 159.7M generation, 213.4M understanding and 97.9M text-only samples, plus 624.8K interleaved sequences, over four stages that raise image resolution from 256 to 2K.
  • Packed training batches reset the recurrent state and convolution history at each sample boundary; the two experts share one state, so switching experts does not reset context.

Takeaway. If your memory or agent system keeps recurrent state or caches, split speculative or intermediate work from committed context. Let speculative steps read the committed state, and write back only finished results.
