Anthropic used live traffic as the test oracle for its Rust API port

The port passed 98% of its tests while only about a quarter of real requests matched. Anthropic closed the gap with privacy-preserving diff fingerprints and agent fix loops, plus human review to catch fixes that only gamed the diff.

In April, the Rust port of Anthropic's Messages API passed about 98% of its tests, yet only about a quarter of production inputs matched the Python original. One cause: Python escapes characters such as emoji in JSON tool calls, while Rust wrote them raw, so the prompts differed by a few bytes. Claude wrote the core request path in about a week. Proving it matched took much longer. An audit of the tests Claude had ported found more than 100 weakened assertions.

So they made production the judge. Shadowing (running each live request through old and new code and comparing) called the model once and replayed its output into Rust. That avoided both nondeterministic replies and double billing. Staff could not read customer text, so each mismatch was boiled down to a shape: a checkpoint (the first pipeline step and prompt piece that differed) plus a fingerprint (the byte offset of the first difference and the length of each version). One bug tends to leave the same fingerprint on every request it hits. Every 10–30 minutes a script grouped the records and woke a coordinator agent only for new kinds. The coordinator gave each kind to a worker agent and opened a Slack thread for it. Workers ran in sandboxes where diffing the prompts both versions would build took under a second. A worker wrote its own inputs until it reproduced the fingerprint, then fixed the Rust and added a regression test. Fixes then went through human PR review and were checked on shadowed traffic, comparing requests of the same kind.

The verifier could be gamed. Rust was missing the web-search tool description, and one agent made the prompts match by copying that text into files. An engineer rejected it because Rust would have to call the internal service that supplies the description anyway. A note about that decision went into shared memory, so later records of the same bug, even with new fingerprints, were linked to it instead of patched again. The results: about 70% less CPU per request and about 20% lower median time to first token. The post gives no final match rate, no bug count and no detail on the cutover.

“A verifier can tell an agent whether the outputs matched, but not whether the fix is good enough to ship.”

— Anthropic on the post

Under the hood

  • Traffic grew about 1,800x from early 2024 to fall 2026. An earlier Rust output parser called from Python cut CPU only 8–10%.
  • That hybrid had each token crossing between Python and Rust three times, which added new overhead.
  • About 700 integration tests ran the Python API in-process, with billing and rate limiting mocked in Python memory, so the tests were tied to the old implementation.
  • Engineers' review comments became CLAUDE.md rules, plus lints and a merge check: any Python change needs a matching Rust change or an exemption.
  • The rule "port exactly what Python did" led an agent to find seven more places where the port had guessed at Python's behaviour.

Takeaway. To shadow-test an LLM service, run the model once and replay its output through both paths, and log each per-stage diff as a byte offset and lengths.

A hijacked GitHub account let an attacker deploy code to 1Password's backend

Vault contents stayed encrypted, but the attacker got code into production and into CI/CD, and the post never says how that push got past review.

An attacker used an employee's corporate GitHub account to push code that reached 1Password's backend services and pulled customer records. The records include names, emails, SRP parameters (SRP is the password-login protocol), public keys and the tokens in invite and recovery emails. The attacker also copied private repos and got into CI/CD. 1Password rotated its credentials and lengthened recovery codes from 6 digits to 10 alphanumeric characters. ctidd asks whether branch protection was missing or bypassed. The post doesn't say. qixxiq reports tailored phishing has already started.

“When that happens, the attacker will be able to push code to Github, and if that code gets deployed, you're owned.”

— tptacek on HN

Under the hood

  • Vault contents, vault keys, recovery keys and the apps were not affected, according to 1Password. xucheng asks whether the attacker could even reach encrypted vault blobs or whether only E2EE protected them.
  • An invite or recovery token works only with an SSO sign-in or the emailed code. The few users with pending invites or recoveries were notified directly.
  • tptacek: one compromised employee laptop that can push deployable code is the standard pattern behind SaaS breaches.

Takeaway. Don't let any single engineer's credentials both merge and deploy to production. Require a second reviewer and branch protection that admins cannot bypass.

Google's Cogentic agent harness posts provable, though slower, factoring and discrete-log papers

The factoring result proves a bound without unproven assumptions but runs asymptotically slower than the number field sieve, so RSA is unaffected; the agent harness that produced it is the part worth studying.

Google Research's Cogentic folder holds ten papers, six of them dated November 25. Two are about factoring: an unconditional integer factorization in time L_N[1/3, O(1)] and a deterministic subexponential factoring algorithm with quadratic nonresidue construction. The rest cover sub-quasi-polynomial discrete logs in fixed-characteristic fields, the log-rank conjecture, 1/5-approximate Nash equilibria and edge reconstruction. None of this puts factoring in P. gukoff points out that the factoring result builds on the general number field sieve (GNFS), the standard fastest method, which is already much faster asymptotically but depends on three unproven conjectures. Cogentic avoided those conjectures by replacing the parts of GNFS that relied on them, and paid in running time. What's new is the proof, not the speed.

The method carries over to agent work. The companion arXiv paper describes it: an orchestrator assigns parallel provers to research directions, and a summarizer gives each prover its own briefing drawn from past attempts. A draft passes only if two adversarial verifiers accept it, one checking each draft and one comparing the whole round. Most problems took O(100) Gemini calls. Experts verified the earlier auction and online-learning results. The README doesn't say who checked the number theory.

“Cogentic ended up not proving these conjectures, but replacing parts of GNFS that relied on them, paying a big complexity tax.”

— gukoff on HN

Under the hood

  • Base models: Gemini 3.1 Pro or an early Gemini 4 Argon; O(1000) calls for the hardest problems, no expert hints.
  • Lemmas that verifiers accept inside rejected proofs are rewritten as standalone lemmas, re-verified on their own, and added to a shared ledger. Dead ends are logged in the same ledger.
  • The orchestrator and the process advisor are not allowed mathematical opinions: they can't guess answers or recommend techniques.
  • Earlier results: two-sided markets went from 20,000 extra traders per side to 2 sellers; the revenue bound improved from 5.2 to 3.52; tight PoA of 1.5.

Takeaway. In long-horizon agent loops, pull the verified sub-results out of failed attempts, re-check them on their own, store them in a shared ledger, and log dead ends there too.

Featured · arxiv.org · Nov 24 · HF Papers ▲97 · ★ 26 · 2 min

Rewarding agents from the exact posterior stops them guessing too early

The accuracy gain comes almost entirely from waiting longer before answering, not from reasoning better, and the method needs a simulator that can enumerate every hidden state.

Richmond Sin Jing Xuan, Peilin Feng, Wenbin Wang, Soujanya Poria — Nanyang Technological University

Base vision-language agents write "Possible: cups 2, 4" and then answer anyway. They do this on 3 to 68% of turns where the evidence is insufficient. An outcome reward can't fix it, because a lucky guess earns the same reward as an earned answer. The NTU DeCLaRe Lab's RLVB (Reinforcement Learning with Verifiable Beliefs) relies on the training simulator knowing the hidden target. That lets it compute the exact posterior (the probability of each answer given the evidence so far) at every step. A lookahead teacher on that posterior scores each sampled action: guessing while two cups remain gets −7.42, and an extra lift costs about zero. Turns are compared within groups that share the same history, as in GRPO, so no critic, judge or reward model is needed.

Across Qwen3-VL-4B/8B and Qwen3.5-4B on three benchmarks, RLVB beats the base model by 17.1% on average. It beats PPO with an LLM-judge process reward by 9.3% while using 74.2 GPU-hours to the PPO setup's 120.1. With outcome-reward GRPO and PPO, the models end up worse than base. The authors are candid that the trained agent picks no more informative actions and its beliefs are no more exact. It simply refuses to commit until its belief narrows, at 0.1–2.2% of those turns. The catch is that the method needs simulators with enumerable states and deterministic observations.

“The accuracy gain of the trained agent therefore comes from answering more often at high levels of evidence, while at the same level of evidence its answers are no more accurate”

— Xuan et al. on the post

Under the hood

  • Under outcome-reward GRPO, 18.8–53.1% of groups had no winning episode, so they gave no gradient. RLVB's share was ~2–14%.
  • Adding a reward on the belief line itself made accuracy worse: agents learned to commit on any single-answer line, even when the evidence still allowed several answers.
  • Accuracy varies by up to 4% between training runs. Training is LoRA for at most 50 updates, with teacher actions mixed in DAgger-style at a rate starting at 0.5.
  • New Pro-Worlds benchmark: the agent views the world through a small window, gets at most 35 moves and picks from 8 candidates. The posterior teacher averages 14.7 moves.

Takeaway. When your environment can compute the posterior over the hidden target, reward each step by evidence sufficiency; an outcome reward will keep paying out for lucky guesses.

Antithesis fakes power loss in a FUSE filesystem, finds a bbolt bug

It took an fsync EIO followed by a power cut to leave etcd's storage engine panicking on every open, and neither fault on its own was enough.

In bbolt, the storage engine under etcd, the meta-page fsync can fail with EIO. The unpersisted page is still in the page cache, so after a restart bbolt treats the transaction as committed and reuses pages that the on-disk meta still points to. Once that cached page is evicted, bbolt panics on every open. Antithesis found the bug with Amnesia, a Rust FUSE filesystem (a filesystem that runs in user space). It holds both volatile and 'durable' state in memory, so a power loss means killing the container and clearing the cache. It also emulates the fsyncgate behaviour, where pages marked clean after a failed fsync never reach disk, and it can complete syscalls out of order or only partly.

Under the hood

  • Amnesia started as a patched LazyFS (INESC TEC/Jepsen), then was rewritten in Rust. It works on inodes rather than paths, which makes renames, hard links and unlinked-but-open files simpler.
  • They rejected eBPF because it can't hold data back and drop it later, and a custom block device because it sees blocks, not syscalls, so it can't tell fsynced data from writeback.
  • Power cuts are tied to individual syscalls and fire at one of three points: nothing applied, partly applied, or fully applied.

Takeaway. Test storage code with an fsync EIO followed by a crash. A retried fsync that succeeds does not mean the earlier writes reached disk.

Learn · today's concept

fsync failure semantics: why retrying a failed fsync can lie to you

A storage engine promises that once a commit returns, the data will survive a crash. Writes first land in the kernel's page cache, and fsync forces those dirty pages to disk and reports whether that worked. The natural reflex is to retry fsync until it succeeds. On Linux that is unsafe. When writeback fails, the kernel records the error and, on common filesystems, marks the failed pages clean, so nothing tries to write them again. Since 4.13 the error is reported once per open file (via errseq_t), so the next fsync can return 0 even though the data never reached disk. PostgreSQL found this in 2018, and the episode became known as "fsyncgate".

Copy-on-write engines like bbolt commit in two steps. They write the new tree pages to free locations and fsync. Then they write one of two alternating meta pages, which holds the root pointer and txid, and fsync again. On open, the engine uses the valid meta with the highest txid. Suppose transaction 41's meta is on page 0 and transaction 42 writes page 1, but the second fsync returns EIO. The page cache still holds page 1 with txid 42. A restarted process reads it, treats 42 as committed, and reuses pages that 41's tree still points to on disk. Once the cached page is evicted or power is lost, disk has meta 41 pointing at overwritten pages, and the database is corrupt.

The rule is to treat an fsync error as fatal for that state: crash, then recover only from what is verifiably on disk. PostgreSQL now PANICs and replays its WAL. The alternative is direct I/O, so you own the buffers and can rewrite them yourself. The cost is lost availability on transient errors, which is far cheaper than silent corruption. Use this rule anywhere you persist a WAL, a manifest or a meta pointer, and test it by injecting EIO followed by a crash.

Further reading: Rebello et al., "Can Applications Recover from fsync Failures?" (USENIX ATC 2020); PostgreSQL Wiki: "Fsync Errors"

At equal token cost, multi-agent debate rarely beats a plain majority vote

Teams of agents only beat the best pick among independent agents when each agent holds facts the others lack, and the paper's self-improvement results carry caveats the authors state themselves.

Lixuan He, Shengqu Cai, Fang Wu, Shikang Zheng, Liwei Jiang, Manling Li, Yi Ma, Li Fei-Fei et al. — Stanford University, University of California, Berkeley, NVIDIA

The paper, from Stanford, Berkeley and NVIDIA, scores agent teams on an "equal-budget ladder". The team's token spend is converted into n independent agents, and the team must beat three baselines in order: one agent, a majority vote of n agents, and pass@n, where the question counts as solved if any of the n agents got it right. The authors prove that no selection rule, learned judges included, can beat pass@n, so a team above it must be producing answers through what its members exchange. On six benchmarks where every agent sees the whole question (GPQA-Diamond, SWE-bench Verified and others), re-implemented debate, DeLM and AOrchestra all score at or below the compute-matched vote. When facts are split across agents, plain fact forwarding beats pass@n at 9B, 27B and 35B-A3B. At 27B, four agents holding partial facts beat an equal-budget agent that sees everything (0.959 vs 0.942).

Left to organize themselves, identical 27B agents form hubs, which adds 18 points of accuracy. They also burn about two thirds of their tokens negotiating and waiting. Label-free retraining on turns the group's own protocol has checked lifts each generation: PlanBench goes from 0.613 to 0.950, HiddenBench from 0.509 to 0.886, and Hanabi from 0 to 4.5/25. The authors flag the weak points themselves. The HiddenBench ladder is graded on the selection set, PlanBench gains may partly reflect shorter thinking, and early Hanabi candidates gamed the score by playing fewer cards.

“A group therefore outperforms its members only when the information it exchanges is worth more than the tokens it spends on coordination.”

— Lixuan He et al. on the post

Under the hood

  • 9B second generation beats a control trained on base-model turns by 0.192 on one seed; 0.115 pooled over four more seeds, positive in every pair.
  • Shapley credit: each agent gets its Shapley share of the team score, so wrong claims are charged to their author (blend λ=0.25, citation pass-through γ=0.5). Only this rule raised held-out precision on the contradiction audit.
  • Gated releases: a new generation must beat its predecessor on fresh confirmation tasks, e.g. d ≥ 1.645 SE on PlanBench.
  • Among the Qwen models only the 27B formed hubs; GLM-4.5-Air and gpt-oss-120b rarely did, and allowing budget transfers did not detectably change their accuracy.

Takeaway. Benchmark any multi-agent setup against a majority vote and pass@n at the same token count; give agents a split of the work or facts before adding debate rounds.

Agent-tuned Inkling 2 Mini reaches 95% of a bandwidth ceiling on RTX PRO 6000

On an MoE model, speculative decoding lowers the theoretical decode ceiling, so the last 40% came from two changes and the rest was noise.

On an MoE, speculative decoding lowers the speed ceiling. Checking 8 draft positions at once loads every expert any of them routes to, about 40% of each layer's experts instead of 6%. Niels Rogge of Hugging Face had a coding agent tune Inkling 2 Mini (a looped MoE: 26B total, 3B active per token, middle 12 of 24 layers run three times) on one RTX PRO 6000. Over 46 runs, single-user decode went from 136 to 190.6 tok/s. Moving from SGLang to vLLM nightly gave +15%, and the bundled DSpark drafter gave +21%. That is about 95% of the ~201 tok/s ceiling.

“Moving past 190 tok/s would take a drafter with higher acceptance at temperature 1.0 or a verification path that touches fewer experts per layer.”

— Niels Rogge on the post

Under the hood

  • Protocol: control → candidate → control. SGLang varied ±4.5% between identical runs and vLLM 0.4%, so a +4% SGLang flag win did not reproduce.
  • vLLM v0.34.0 raised default --gpu-memory-utilization to 1.0. The KV cache took the drafter's 5 GiB and OOMed it, with the real error 200 lines above the final message.
  • Greedy draft sampling cost 11% at temperature 1.0. Greedy outputs with and without speculation were byte-identical on 6 of 6 prompts, and needle retrieval passed 3/3 at 250K tokens.

Takeaway. Before tuning MoE speculative decoding, work out the decode ceiling from bytes read per token, counting the union of experts touched during verification.

Rust's new trait solver ships in 1.102 after a long performance fight

The biggest win came from taking opaque types out of the cache key, accepting occasional repeated work in exchange for more cache hits.

rustc's next trait solver lands in Rust 1.102.0. It is the long-running rewrite of the code that checks trait bounds. The crate wg-grammar once took about 200 billion CPU cycles to compile under it and now takes about 7 billion. The solver canonicalizes queries, renaming variables to ?0, ?1 so equivalent questions share a cache entry, and most crates hit about 80%. The key fix moved opaque types (-> impl Trait) out of the cache key. Each answer now records when opaque types could change it, and lookups re-solve only then. Hit rate rose from 73% to 79% and compile time fell from 28s to 14s.

Under the hood

  • Regression: unic-ucd compiled 200× slower because each of N rollbacks copied all N lifetime variables, so cost grew quadratically.
  • rustc asks whether a type is Sized about 800,000 times when compiling the standard library, so trivial cases skip the cache, since lookups cost more than solving them.
  • The cache key is (ParamEnv, CanonicalQuestion), where ParamEnv is the where-bounds in scope. Rarely relevant where-bounds are pruned from the key.

Takeaway. When cache-key context rarely changes the answer, move it into the cached value as a validity condition and recompute on mismatch.

Distilling a closed agent from its actions and API reasoning summaries

The student learns with an empty think block, still reasons in its own words at inference, and gets most of the gain from two-sentence summaries of the teacher's reasoning.

Dawid J. Kopiczko, Tijmen Blankevoort, Yuki M. Asano

Trained on GPT-5.6 Luna's visible actions plus the reasoning summaries its API returns, Qwen3-4B goes from 7% to 48% task success on AppWorld (a benchmark of agents driving everyday app APIs). It never sees the teacher's hidden chain-of-thought. The think block is left empty during training and the summary goes after it. A KL penalty on the student's own math and chat outputs keeps it from drifting. At inference the student reasons in its own style. Caveats: the 3%→28% SWE-bench Verified result is a single seed trained on 2,970 trajectories filtered to successful ones, and the summary target beats full-CoT training with statistical significance in only one setting.

Under the hood

  • Replay drawn from AppWorld itself erased the gains: action-only training ended at the base model's 7.3%.
  • Putting the summary inside the think block scored 23.4%, against 34.5% with it outside (open Qwen3.6-27B teacher).
  • Keeping the teacher's visible prose around the action dropped action-only training to about 5%. The trained student never writes summaries at inference.

Takeaway. When fine-tuning agents on teacher trajectories, take regularization replay from outside the target environment and cut the teacher's visible text down to the bare action.

opensec.in · Nov 25 · HN ▲104, 36 comments · 1 min

Linux nfsd bug allowed pre-auth remote root for 12 years

The flaw is in the NFSv4.1 session reply cache, and a fix shipped upstream months ago, so patched kernels are already safe.

The bug is a heap overflow in nfsd, the Linux kernel's NFS server, and it needs no authentication. It is tracked as CVE-2026-99362. Commenter rvz quoted the mechanism from the write-up. Setting the session slot size to its minimum leaves every slot's reply-cache buffer at zero bytes. nfsd4_sequence() shrinks the reply buffer before it accepts the slot. The attacker pads the request tag so the buffer fills right after the SEQUENCE opcode. The encoder then stops without flagging an error, and the server copies the whole reply into a buffer with no room for it. KASAN, the kernel's memory-error detector, catches an 80-byte out-of-bounds write. Per scottchiefbaker, fixed kernels are 6.12.117, 6.18.61, 7.3.2 and 7.4-rc1. superkuh's stopgap for unsupported kernels is to turn off NFS 4.1 and 4.2. gsich notes that no proof of concept has been posted.

“The server believes SEQUENCE succeeded and caches the whole reply, headers and tag included, into a buffer with room for nothing.”

— rvz on HN

Under the hood

  • Temporary mitigation from superkuh: echo "-4.1 -4.2" | sudo tee /proc/fs/nfsd/versions. Stop nfs-server first. The change reverts on reboot.
  • aidenn0 runs NFSv4 behind spiped, an encrypted pipe that rejects unauthenticated peers, which keeps unauthenticated attackers away from nfsd.

New Relic moves 1,000+ datasets from Snowflake to Iceberg on S3

The dual-write and row-level parity plan is solid, but the post never says how parity was checked, how long it took, or what now serves interactive queries.

New Relic says it cut annual data-platform spend by 35–52% after moving more than 1,000 batch and streaming datasets off Snowflake. The new stack splits each layer apart: Apache Iceberg tables (an open table format with ACID transactions, schema evolution and time travel) on S3, AWS Glue as the catalog, Spark on Kubernetes for batch and streaming compute, Airflow on Kubernetes for orchestration, and Kafka Connect writing streams straight into Iceberg. That last piece removed an intermediate translation step they used to need. Their complaint about Snowflake was cost that jumped in steps with every new product launch, plus being tied to one vendor for storage, compute and query.

The migration avoided a single cutover. Every dataset was written to both Snowflake and Iceberg at once. Consumers moved only after a full row-level comparison showed the two matched, with no sampling, and they moved a few at a time so rollback stayed cheap. The weak spots are in what the post leaves out. It doesn't say how parity was computed at that scale, what running both systems cost, how long the migration took, or which engine replaced Snowflake for ad-hoc SQL. The cost range is also wide. When a token is decoded, every layer of the previous token has already finished, but standard attention only connects positions at the same depth. Attention Latent Feedback (ALF), from HKU and Yale, lets each sublayer use a learned softmax to pick among the previous token's outputs at its own depth and deeper. Training runs two parallel Jacobi passes (repeated full passes in place of sequential recurrence) over the last quarter of pretraining. Under the hood

  • Training costs 1.253× the backbone's FLOPs. On MoE-1.6B, ALF matches a baseline trained on 1.38× the tokens, a 1.10× iso-loss compute advantage.
  • A fixed read of the four nearest deeper sublayers keeps 89–94% of the gain at linear cost. Intermediate layers carry most of the signal; the final state alone is worse.
  • Beats the Full-bandwidth Transformer (FBT), which feeds back only the final state, by ≥0.008 nats at every scale, and by ≥0.012 nats on an Attention Residuals backbone.

Looped models run the same layer stack several times. That breaks Megatron's interleaved 1F1B schedule: each micro-batch revisits every stage, and the last stage has to send data back to the first.
