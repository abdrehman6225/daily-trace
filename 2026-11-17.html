Google's Tunix gets bitwise-identical sampler and trainer logprobs for on-policy RL on TPU

A synchronous RL loop can still drift off-policy because of floating-point rounding. This post shows how to remove that drift completely, and how to find where it enters any RL stack.

Google's Tunix team reports Zero-TIM (zero train–inference mismatch). At the same weights, the sampler and the trainer assign bitwise-identical logprobs to every sampled token. They verified it on 64 TPU v5p chips split as DP8×TP8 (8-way data parallel × 8-way tensor parallel). The root cause is that floating-point addition is not associative, and bfloat16 makes this easy to see. The sampler decodes one token at a time. The trainer runs batched forward-backward passes. JAX specializes compiled code to input shapes, and differentiation changes the program. So the two paths add numbers in a different order with different intermediate precision. The result is a hidden off-policy gap that grows over multi-turn trajectories.

The contract is to compare raw bytes, with zero tolerance, across three paths: sampler decode, serving prefill and trainer forward. Prefill sits in the middle, so a mismatch can be traced to one side of the serving/training boundary. The recipe has four parts. Batch-invariant Pallas kernels (Pallas is JAX's custom-kernel language) process fixed contraction blocks in order and accumulate in float32. Cross-shard reductions send partial sums with ppermute, then every rank adds them in a fixed source-rank order. All paths share one logprob tail: the same sampling transforms and one fixed log-softmax, applied to the recorded token. jax.custom_vjp lets the trainer reuse the serving forward pass.

In the test, Qwen3-8B played FrozenLake (grids 2×2 to 9×9, up to 5 turns) with a GSPO-token loss and RLOO advantages (each sample's baseline is the mean reward of the others). Zero-TIM's logprob gap was exactly 0 at every step. Standard training sat at 0.0144–0.0233 and token-level TIS (truncated importance sampling) at 0.0049–0.0254. Solve rates at step 200 were 88.2%, 62.7% and 66.9%. Caveats: this is a single seed on a synthetic environment. The Zero-TIM arm also used exact token-in/token-out and ran with evaluation off, so the comparison is not a clean ablation. The repo's reproduction README says that exact tree has not yet been launched on a cluster. Support for MoE and linear attention is in progress.

Under the hood

  • Kernel core: jnp.dot(..., preferred_element_type=float32). Each tile adds into a float32 scratch accumulator, and the next tile builds on that accumulator, not the cast output.
  • Custom VJP: forward values come from the Pallas kernel. The backward pass uses a differentiable copy that mirrors the kernel's accumulation and casts.
  • They set --xla_allow_excess_precision=false in XLA_FLAGS so XLA keeps no extra precision in the ops around the Pallas kernels inside the differentiated program.
  • Long trajectories are scored in fixed-size chunks that carry the paged KV cache forward. Gradients flow back through the cache, and parameter gradients are combined before the optimizer step.
  • Setup: 32 prompts × 8 generations = 256 trajectories per update, lr 1e-6, temperature 0.7, TIS threshold 2.0. Zero-TIM uses the rollout logprobs directly as the old-policy logprobs.

Takeaway. Add a serving-prefill re-score as a midpoint check in your RL loop, and log the exact byte difference in sampler–trainer logprobs. TIS only reweights the mismatch, while fixing reduction order and precision removes it.

Microsoft 365 outage: July lock-contention bug surfaced months later and cascaded across gateways

A preliminary postmortem with a latent concurrency bug, load tests run on the wrong hardware, a retry cascade, and a fleet that could not be rolled back.

Microsoft's preliminary report says a July update to Microsoft 365 network gateway servers caused lock contention inside an internal Windows process. Threads fought over a lock until CPU and memory ran out, and the effect was worse on newer machines with more cores. The update had passed load testing, but those tests "tended to focus on weaker hardware with fewer cores." On November 12, Teams failed over onto the primary gateway that serves Exchange Online while about 14% of gateway capacity was offline. Microsoft says either event alone was within headroom; together they triggered the bug. Each server that failed pushed its traffic to the next healthy one, and within two hours more than 80% of servers were unresponsive.

Servers brought back were overwhelmed again straight away. Automated recovery was not built for a state where most of the fleet was down, and a plain rollback was not possible because the change was months old. Engineers wrote a new update that restored the old Windows code path and rolled it out to groups of servers. On HN, one commenter compared the recovery to a power-grid "black start", where load is reconnected in blocks. Another asked why Microsoft did not shed load by admitting only some IP ranges at a time, rotating through them.

Under the hood

  • Timeline (UTC): Teams failover 01:07 Nov 12; anomaly detector fires 16:03; first support case 16:33; root cause traced to connection negotiation 00:30 Nov 13.
  • The fix reverting the defective change went out at 07:20 Nov 13, and service was healthy at 16:10. All deployments and config changes were frozen during the incident.
  • Teams, OneDrive, SharePoint and Office apps moved off the faulty gateway. Exchange Online could not, "for scale reasons", which is why email was down longest.
  • Adding capacity and rerouting traffic did not help: new servers took the full load immediately and fell over again. A final report is due November 20.

Takeaway. Load-test concurrency changes on your largest production hardware, because lock contention gets worse as core count grows. Also build and practise a way to bring a fleet back gradually behind admission control, since a months-old change cannot simply be rolled back.

lend: remote coding agents run credentialed commands on your laptop, with approval

If you build or run agents on throwaway VMs, this pattern keeps tokens and SSH keys off the VM entirely.

lend is a proxy that sits in front of your SSH agent, and you forward its socket to the agent VM instead of the real one. SSH and Git signing keep working, and an SSH agent extension lets the VM ask the laptop to run commands. The request comes from lend exec or from an MCP tool, run_local_command, which requires a reason. A policy on the laptop denies anything not listed and asks for Touch ID on each request. Rules can pull 1Password secrets into environment variables, so the token never reaches the VM. The top HN objection is that the approve button is ceremony, not informed consent.

Under the hood

  • Policy rules match the executable's full path plus an args_prefix such as ["pr","view"]. Unlisted SSH keys are hidden from the VM. max_signatures caps how many signatures a key can make per session.
  • A lease (for example 5 minutes or 3 uses) covers only the exact command and arguments you approved. It ends when the session ends or the screen locks.
  • Limits: approved commands run unsandboxed as your user. Approving sh, env, op or anything that reads stdin gives everything away. Caller details come from the VM and can be faked. There is no PTY, and Touch ID works only on macOS.

Takeaway. Keep the credential and the code that uses it on a trusted host, and give the agent only the command's output, behind a deny-by-default allowlist. Never allowlist shells, interpreters or secret readers, because each one gives the agent everything.

S2 replaced Route53 with a Go DNS server that reads Spanner on every query

A small case study in what happens when you put a database lookup on the public DNS path, and what it costs to protect it.

S2, a streaming-storage service, gives every basin (its top-level namespace for streams) its own CNAME, such as my-basin.b.s2.dev. Route53's API allows about 5 UPSERTs/sec. When an attacker created tens of thousands of basins, the backlog held up normal DNS updates for hours. GCP Cloud DNS, Cloudflare and Azure throttle updates in a similar way. S2 wrote its own authoritative server in Go on miekg/dns. It runs a live SELECT against Cloud Spanner for each query, runs in two GKE regions, and sits behind Cloudflare DNS Firewall to absorb floods of queries for names that don't exist (NXDOMAIN floods). HN commenters asked why they didn't use PowerDNS, CoreDNS or per-cell wildcards.

Under the hood

  • Goal: a new basin must resolve immediately, with no cached NXDOMAIN. That ruled out batching, which still wouldn't have felt unlimited.
  • They wrote the A/AAAA/NS/CNAME/SOA responses by hand and tested them with unit tests, the Ferret RFC-compliance tester from the NSDI'22 SCALE paper, and a smoke test against live data after deploy.
  • Origins accept traffic only from Cloudflare IPs. NS and SOA answers always point to Cloudflare, and an ns-leak-test checks that origin IPs never leak.
  • ACME DNS-01 challenges for the wildcard certificates are CNAME-delegated to a separate Route53 zone, so the server never serves dynamic TXT records.
  • An HN commenter noted that basins never move between cells, so a *.<cell>.s2.dev wildcard would have avoided database lookups on queries.

Takeaway. Before you put a database read behind a public protocol, work out the cost of a random-miss flood (here, NXDOMAIN). Also check whether an immutable mapping, like a basin's cell, lets you use static wildcards instead.

Optimizely snippets on 178 sites, including Zoom and GitLab, served card skimmers and iOS exploits

A real-world check of which CSP settings stopped a third-party script compromise and which ones let it through.

On 16 November, someone added a loader to the Project JavaScript (projectJS, custom code customers write in Optimizely's dashboard) in 188 Optimizely Web snippets belonging to 178 organisations, including Zoom, GitLab, the BBC and HSBC. The files still came from the trusted cdn.optimizely.com. They loaded track.js, which swapped crypto wallet addresses, skimmed card details, stole cookies and screenshots, and sent iPhones and iPads to exploit kits. Report URI, a CSP-monitoring vendor, checked the CSP on 256 affected hosts. 68 had no CSP, 50 let everything through, 17 stopped the data theft with connect-src, and 24 blocked the payload outright with a tight script-src.

Under the hood

  • Three loader variants: a plain script tag, the same URL hidden in base64 and decoded with atob(), and a full inline copy run through eval if 1688360.cc was blocked.
  • HSBC's CSP blocked track.js, but 'unsafe-eval' (which Optimizely's docs tell customers to allow) let the inline copy run. 'strict-dynamic' also let the payload through.
  • The attacker rebuilt the payload 26 times and received about $7,040 in roughly nine hours. Nobody yet knows how they got write access. HN commenters suspect stolen credentials and argue for hosting vendor scripts yourself.

Takeaway. Allowing a vendor's host in your CSP does nothing if the vendor's content changes. List each script host by name, avoid 'unsafe-eval' and 'strict-dynamic' for third-party loaders, limit connect-src, and turn on reporting.

Jiff 1.0: BurntSushi's Rust datetime library makes time zones explicit

A good model for designing APIs around a hard domain. Ambiguous local times get explicit handling, and durations keep the units they were written in.

Jiff, already used by uv, Cargo, Jujutsu and AWS LLRT's Temporal implementation, reaches 1.0 with a promise of no further breaking releases. Its types build on each other: civil Date/Time/DateTime (no location), Timestamp (nanoseconds since the Unix epoch), TimeZone, then ZonedDateTime. DST gaps and folds (skipped or repeated clock hours) resolve by a "compatible" default or explicitly via earlier/later/unambiguous. A Span keeps each unit, so 2h ≠ 120min field by field. HN: a former chrono maintainer says chrono's API couldn't be fixed without breaking users.

Under the hood

  • Fold default: the first occurrence. Gap default: the later time. ZonedDateTime::tomorrow() across a fall-back day returns a 25h span.
  • ISO 8601 durations lose detail: 2000ms prints as PT2S and parses back as 2s. Jiff's 'friendly' format (3d 4h 59m) keeps the original units.
  • SignedDuration is a 96-bit nanosecond count for physical time only; Span mixes calendar and clock units but is heavier and slower.

Takeaway. Store instants as RFC 9557 strings (offset plus IANA zone, e.g. -05:00[America/New_York]) so the time can be re-checked against the zone later. Make callers choose how ambiguous local times are resolved instead of picking silently, and use Instant (monotonic time) for elapsed time.

GRPO on Qwen3-0.6B: full RL step cut from 100 minutes to 56 seconds on TPU v7

At sub-billion scale, RL step time comes from coordination costs such as host dispatch, sync points and KV-cache lifecycle, not from matrix math. This write-up measures each fix.

Meta ranking researchers ran synchronous GRPO on Qwen3-0.6B (256 prompts × 8 generations, 8,192-token responses) on a 64-chip TPU v7 slice. One rollout-to-update cycle fell from ~100 minutes to ~56 s, and decode rose from ~4K to ~183K tokens/s. The biggest gains: a compiled multi-step XLA decode loop that avoids a host round trip per token (616→369 s), separate KV-fetch and compute tile sizes in the Pallas attention kernel (+48% decode), and 128 single-device vLLM engines. All 23 PRs are merged upstream.

Under the hood

  • KV persistence: resetting prefix mappings already makes old-policy blocks unreachable, so the HBM allocation is kept across the weight update. Setup fell from ~37 s to 3 s on the earlier TP4 stack.
  • Rollout is 85% of the final step (49.1 s of 57.9 s median); 27.8% of completions hit the 8,192 cap. Least-loaded routing across 128 engines cost ~35 s/step versus round-robin.
  • Negative results: INT8 weights gave no decode gain; FP8 KV doubled cache capacity but gave little speedup; shared-prefix cascade attention showed no net gain against the production kernel.

Takeaway. For small-model RL, measure the whole rollout-to-update cycle. Run many decode steps per host return, and treat invalidating the cache as separate from freeing its memory. Benchmark new kernels against the production kernel at production batch size, not against a naive reference.

Learn · today's concept

Sampler–trainer mismatch and truncated importance sampling

In RL for LLMs, an inference engine (the sampler) generates the rollouts with policy μ, and a separate trainer computes gradients with policy π. Both use the same weights, so the loop is called on-policy. In practice their kernels, batch shapes, reduction order and precision differ. Floating-point addition is not associative, so the same token gets a slightly different logprob on each side. The gradient therefore treats samples from μ as if they came from π. Small gaps add up over long sequences and in MoE routing, and they can quietly destabilise training.

There are two fixes. The first corrects for the gap. Weight each token's policy-gradient term by w = min(π(a)/μ(a), C). This is truncated importance sampling (TIS), and the cap C keeps rare tokens from dominating. Example: the sampler gives a token logprob −2.30 and the trainer gives −2.10, so w = exp(0.20) ≈ 1.22 and the token stays. For a rare token, with −9.0 versus −6.5, the raw ratio is exp(2.5) ≈ 12.2. With C = 2 it is cut to 2, which avoids one token getting twelve times the weight. The second fix removes the gap. Make both sides run the same kernels with the same reduction order and precision, so the logprobs are bitwise identical and w = 1 exactly.

TIS is cheap and works with any engine. The cost is some bias from the truncation, and the mismatch is still there, only reweighted. Removing the gap is exact, but you need control of both stacks, and batch-invariant kernels can lower throughput. Use TIS by default. Always log a mismatch metric, such as mean |Δlogp| between sampler and trainer. Aim for bitwise identity when you own the whole stack or are tracking down unexplained instability.

Further reading: IMPALA: Scalable Distributed Deep-RL with Importance Weighted Actor-Learner Architectures (Espeholt et al., 2018); Defeating Nondeterminism in LLM Inference (Thinking Machines Lab, 2025)

Google's cost model for parking idle agent sandboxes on GKE

If you host long-lived agents, the user's prompt rate decides whether snapshotting idle sandboxes saves 40% or loses money.

Drake Williams and Ivan Nardini of Google Cloud cite a study of GitHub Copilot agent traces by Liu et al. In it, an agent waits for the user about 80% of a session, and a turn (one prompt plus the full response) averages 396.3 s of agent work. The authors assume 2 prompts an hour, which means the agent works 22% of an 8-hour day. Giving each session its own Pod (1 vCPU, 1 GiB) puts 100 agents on 34 c3-standard-4 nodes, about USD 1,288 a month. Scaling to zero between prompts keeps files but loses the process and its memory. Agent Substrate 1.0 is generally available on GKE and has been donated to the CNCF. It separates an *actor* (one agent's processes, files and identity) from a *worker* (a pooled Pod that hosts several actors). SuspendActor snapshots an idle actor to object storage, and any warm worker can restore it. AX sits on top and declares a Task (image, command, limits) and a Workspace (repositories, files).

With a 2-minute idle timeout, a session holds a worker 29% of the time it is open. A pool sized at p99 concurrency plus 15% needs 15 nodes, plus one node for the control plane and PostgreSQL. That saves 40%. At 4 prompts an hour the saving falls to 4%, and above about 4.5 one Pod per session is cheaper. Parking pays from about 37 coding sessions. Overcommitted Pods (0.25 vCPU request, 1 vCPU limit) fit the same 100 agents on 9 nodes. The model does not price the same overcommit for Substrate.

Under the hood

  • Substrate never suspends idle actors on its own (issue #424). Your harness must call suspend. When idle actors hold every worker, new requests wait 5 s, then get HTTP 503.
  • ax suspend currently uses a volume snapshot: files come back on resume, but the agent's processes start fresh.
  • Gateways add credentials to outbound traffic based on the actor's identity, so a prompt-injected agent never holds API keys.
  • Autoscaling follows worker Pods, not suspended actors. A pool left running all 730 hours a month costs about twice the one-Pod-per-session bill, so scale it to zero after hours with a scheduled job.

Takeaway. Before you build suspend and resume for agents, pull prompts per hour at your busiest hour from your gateway logs. Then compare parking against overcommitted Pods with the same CPU guarantee.

Go 1.28 will let you write return {}, err without the type

An accepted Go language change that cuts repeated types from returns, options structs and struct fields, with clear limits on where it applies.

Damien Neil filed this proposal in 2015. It was accepted in April after about 260 comments and is merged for Go 1.28, due February 2027. Redowan's write-up shows that a bare {...} now works wherever Go already knows the type: typed variables, assignments, arguments, channel sends, struct fields and returns. When a pointer is expected, Go adds the & itself, as in TLSConfig: {MinVersion: tls.VersionTLS13}. It does not work with :=, any, an explicit &{...} or type parameters. The review group chose not to restrict it to cases that read well, and no tool will strip types automatically.

Under the hood

  • Spec change: one new assignability rule. {...} is assignable to T if T{...} is a valid literal, and the composite literal section extends this to *T.
  • slices.Index(pts, {3, 4}) fails because the literal is checked against E, not inferred from pts. Generic structs like Box[T] also fail.
  • gofmt -s is unchanged. The gopls compositeLiteralTypes inlay hint shows elided types. You can try it with gotip and go 1.28 in go.mod.

Takeaway. Leave the type out only when the reader can see it nearby, as in a return or a clearly named field. Keep it for channel sends and arguments whose types are declared elsewhere.

How Aerogramme fixed IMAP SEARCH/FETCH with a reference test suite and roundtrip fuzzing

A practical method for testing parsers against vague specs and broken real-world input, applicable to any query layer over messy documents.

Aerogramme is an experimental geo-distributed email server built on Garage, the team's own distributed object store. Its developers explain how they made IMAP SEARCH and FETCH correct. Mailbox state and parsed headers live in Garage K2V, a key-value store, and message bodies live in S3 storage, so SEARCH reads only precomputed metadata. They used Dovecot's ImapTest as a reference (an "oracle") and compared outputs. It showed their BODY[<section>] implementation was conceptually wrong in many cases. They fuzzed their parser, eml-codec, with a print-then-parse roundtrip property, then ran it on more than 100k real emails.

Under the hood

  • Roundtrip: the fuzzer generates an AST, prints it, parses the output and checks the ASTs match. Comparing strings after parse-then-print fails because headers can be line-folded in several valid ways.
  • Context-dependent RFC2047 (non-ASCII header encoding): in From, =?utf-8?q?@[?= X] is a valid address, not an encoded word. In Subject, the same bytes decode to @[ X].
  • Parser made total (always returns an AST) by dropping fields it cannot parse. Logged drops on real mail led to targeted fixes, e.g. Apple Mail Content-IDs without @.
  • Still open: ImapTest expects SEARCH FROM foo@example.com to match <"foo" (comment) @ example.com>. The spec defines no canonical way to print an address for substring matching.

Takeaway. If a format has both a parser and a printer, fuzz the generate-AST, print, parse, compare loop. For messy input, first make the parser total with coarse discards, then log every discard and work through the logged cases on a real corpus.

Coral saves an agent's working tool-call code as reusable, permissioned tools

Coral gives agents procedural memory: a TypeScript program that worked once is saved as a tool that later agents can find and call, and every call passes a policy check.

Coral is an open-source gateway written in Rust and licensed Apache 2.0. Its authors first built it for an AI SRE agent. It sits between agents and services such as GitHub, Linear and Slack. Agents don't call tools directly. They write short TypeScript programs that run in a V8 isolate with no network access and no credentials. When a task succeeds, the program can be saved as a custom tool. Later agents find it in the same search as the provider tools. On Coral's own 34-task benchmark with Opus 5.5, tokens fell 37%, cost 31% and time 29%.

Under the hood

  • The gateway checks every tool call against workspace policy before it attaches credentials. A provider can run under the caller's own account, so teammates can share tools without sharing API tokens.
  • Benchmark totals: 12.2M→7.7M tokens, $9.86→$6.79, 47→33 min, 33/34→34/34 correct. Biggest win: one Slack lookup went from 1.18M to 128K tokens and from 516 s to 27 s.
  • The gains vary by task. Several runs got slower, for example 50 s→118 s with 25% more tokens. Each task appears to have run once per setup, with no variance reported, and the vendor ran the benchmark.

Takeaway. If you build agents, save successful code-mode programs as named tools with their own permissions. This is a cheap form of procedural memory. Test it on repeated runs, though: Coral's per-task numbers swing widely.

AG-UI 1.0 freezes an event-stream protocol between agents and frontends

TIDE gives idle rollout GPUs to training while RL stays on-policy

A simple feedback controller recovers 77–97% of optimal throughput in synchronous GRPO training. It needs no off-policy tricks and no per-workload tuning.

In synchronous colocated RL, rollout and training share the same GPUs and a barrier separates the two phases. Long-tail rollouts make this wasteful: GPUs that finish early sit idle for up to 30% of runtime, and shrinking decode batches waste another 9.8%. Measured against a utilization-optimal bound, colocated runs reach only 57–83%. TIDE comes from the University of Washington, Brown and collaborators. Its key observation is that on-policy training only needs a barrier before the optimizer step, not before training starts. So an engine that finishes its rollouts hands its GPUs to training on completed GRPO groups. The remaining rollouts are moved as tokens, not KV cache, to the least-loaded engine, which keeps its decode batches large.

Migration starts when an engine's remaining rollouts fall below a threshold B. A linear controller modelled on TCP Vegas updates B after each step using one binary signal: whether any trainer GPU sat idle. If one did, B drops by 8; otherwise it rises by 8. A KV cache veto delays a migration if the receiving engine's KV cache is already full. The tests used Text2SQL (Qwen2.5-Coder-7B) and DAPO-Math (R1-Distill-Llama-8B) on hardware from 4×L40S to 8×H200. TIDE ran up to 1.36× faster than plain colocated training and beat RollPacker and TLT. TLT uses speculative decoding, and it ended up slower than its own setup without speculation. All tests were on a single node.

Under the hood

  • Train Router: sends trainers 64 rollouts at a time, then at most a quarter of what remains near the end of a step. Without this, trainers pulling work greedily left some idle (1.03× → 1.12×).
  • Ablation on DAPO-Math, 8×H200: adding migration raises the speedup from 1.12× to 1.20×. On 4×H100, migration without the KV veto gives 1.09×, worse than load balancing alone at 1.11×; with the veto it reaches 1.14×.
  • Adding GPUs to FSDP training means gathering gradients into a pinned CPU buffer, re-sharding and rebuilding the NCCL (GPU-to-GPU communication) groups. This costs 2–3%. Gradient clipping and the optimizer step wait until the whole batch is done.
  • Case study, one DAPO-Math step on 8×H200: idle GPU time fell from 20.8% to 3.2% after three migrations (80, 80 and 88 requests). The step took 595s instead of 746s.

Takeaway. The ordering only has to be enforced at the weight update, so work can stream into training as rollouts finish. Grow the thresholds that trigger this with a cheap starvation signal, AIMD-style, instead of tuning them by hand.

KL, JSD and entropy lose precision when the two distributions are nearly equal

If your RL or distillation loss has a KL term, its gradient can round to zero, or stay nonzero for identical logits, right where the policy sits near its reference.

Brandon Amos

Brandon Amos (Reflection AI) extends Barron et al.'s work on softmax cancellation to more losses: forward and reverse KL, generalized JSD, entropy, and the K1/K2/K3 Monte Carlo KL estimators used in GRPO and Kimi k1.5. When the two distributions are nearly equal, log-softmax outputs rounded separately cancel each other out. Signed KL sums also lose the small quadratic term that is the actual answer. FP32 gradients then vanish, or stay nonzero at identical logits. The fixes: rebuild log-ratios from logit differences, sum nonnegative p·E2(s) terms (E2(x)=e^x−1−x, computed by Taylor series near zero), and correct gradients so they sum to zero. JAX code is included; there are no training-scale results.

Under the hood

  • K3 (the estimator DeepSeekMath uses in GRPO): computing expm1(-s)+s in FP32 gives zero value and zero derivatives at s=1e-8. Fix: E2(-s) with derivatives ±expm1(-s), guarded by |s|≤1/2.
  • Sampled log-ratio: compute (z_a−z_ref,a)−(logZ−logZ_ref) instead of subtracting log-probs. Each model only has to send two scalars per sampled token.
  • Limits: the rebuild overflows far from equality (e^100 at h=50) and needs a fallback. The logit subtraction alone erases 2^-25 gaps, an open problem. BF16 makes everything worse.

Takeaway. In KL-regularized RL code, compute the per-token log-ratio from logit and log-normalizer differences, and evaluate K3 as a Taylor-series remainder rather than expm1(-s)+s. This matters most under BF16, where the paper notes Adam can amplify the leftover rounding error into real parameter updates.

Callo turns agent context-edit cache misses into speculative decoding on stale KV

If your agents mask, summarize or rewrite memory mid-session, this shows how to get back part of the re-prefill latency with no change to outputs.

Jianjun Ou and Matthew Lentz (Duke) target a cost that agent harnesses pay often. When a harness masks old tool outputs or summarizes, the prefix cache misses from the edit onward and the request waits for re-prefill (recomputing KV for the rest of the prompt). Callo runs on disaggregated vLLM (prefill and decode on separate GPUs), with no source changes. While the prefill instance recomputes, the decode instance re-rotates the previous request's now-invalid KV to the new positions and drafts with the target model itself. The prefill instance streams exact KV into the same blocks layer by layer. Once all of it lands, one forward pass verifies the drafts. Only accepted tokens commit, and unverified KV never enters the prefix cache. Offline, stale KV's top-1 token matches exact KV at 98.3% of positions. A full 32-token window passes in 65% of misses, vs 12% for prompt-lookup n-grams (drafts copied from matching prompt text).

On two H200s replaying SWE-agent sessions (Llama-3.3-70B, Gemma-4-31B, Mistral-Small-3.2-24B), Callo beats vLLM by 1.05–1.19× on all requests and 1.06–1.24× on misses at moderate load, recovering ~47% of the miss penalty. A 96-GPU simulation weighted by Azure traffic gives 1.130× at a 1:2 prefill:decode GPU ratio, down to 1.027× at 3:1. It needs session affinity, the old KV still cached and spare decode capacity. Gains are small when long reasoning outputs dominate.

Under the hood

  • Early stop: the product of per-draft agreement probabilities, calibrated from logit gaps, stops drafting below θ=0.3. This discards 30% fewer drafts and keeps 97% of accepted ones.
  • Drafts fail where the model hesitates: top-1/top-2 logit gaps under 0.5 are 2.4% of positions but 60% of first mismatches.
  • Exact KV arriving layer by layer heals the draft state: with half the layers exact, acceptance matches fully exact KV. Position-by-position arrival gives no gain.
  • Correctness check: 44,792 committed tokens, no mismatches. Requests that don't speculate run 2–6% slower. Decode-side runtime buffers cost 0.75 GiB (1.5% of the KV pool).

Takeaway. A stale cache is still useful for drafting: propose tokens from it, then commit only what the exact state verifies. If your memory layer rewrites context, this kind of overlap makes edits cheaper than the append-only default suggests.
