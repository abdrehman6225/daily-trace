Uber's agents file their own bug reports against 5,000 internal skills

The eval and cost methods are practical and specific; the headline ablation results come from an LLM judge, and most of them are summarised as "a majority of cases".

One of Uber's pull-request skills wrote commit messages to a shared temp file, so two concurrent sessions overwrote each other's PRs. No person reported it. An agent filed it through log-papercut, an always-on skill that any agent can call when it hits friction. Each report records what the agent tried, what it expected, what happened and what would fix it. Agents filed thousands of these in three months and hundreds were fixed, including a deploy skill that passed epoch seconds to an API that expects milliseconds. All of this runs on a Git-backed marketplace that grew from 1 skill to more than 5,000 in a year, with over 1M invocations a month. A skill is a SKILL.md directory loaded in three stages: a ~100-token description that is always in context, a body under 500 lines loaded when the skill runs, and scripts read on demand.

The eval mix is about 5% golden cases with tool mocks, 80% real prompts graded on trajectory (whether the agent used the right skills and tools in the right order), and 15% cases the author judges. Evals run on remote sandboxes, which caught skills that depended on files or tools on the author's laptop. The team argues that a suite passing 70–90% of runs tells you more than one passing 100%, because a perfect score may mean the eval misses real changes in the answer. For ablation, they replay real prompts with and without a skill and a blind LLM judge picks the better answer. Without the warehouse-query skill, sessions made 13% more tool calls, hit 6× the tool errors and took 31% longer, and the answer with the skill won 87% of comparisons. Beyond that one example, the post gives no counts, only "a majority of cases".

Cost per invocation is the change in the session's running cost between the snapshot before a skill call and the one after. It is a rough measure, because the window also includes other tool calls. A cheap-model subagent that returns only a bounded summary cut a tracing skill's cost by 46%, but a deployment skill showed no drop. With more than 100 MCP tools installed, the tool definitions alone took 50–70k tokens before the user typed anything. Uber moved its common flows into scripts that call tools through a gateway, an approach borrowed from Cloudflare's Code Mode, and now blocks .mcp.json in skills.

“In our experience, evals that pass 70%-90% of runs can be more useful than those that pass 100%.”

— Andrew Mager, Jason Varbedian, Uday Kiran Medisetty on the post

Under the hood

  • aifx CLI merges six config layers (company → team → repo → dir → user → local); later layers only add plugins, never remove them.
  • Running a skill's script at load time cut a search skill from four turns to three and its mean cost by 32%.
  • In the 20 highest-spend sessions, notification turns were about a third of the cost, so PR-monitor polling moved to a background agent on a cheaper model.
  • Skill linter: numbered single-objective steps, a concrete command checked after each step, and an error-recovery table ("try again" does not count).
  • Authors write spec.md first; Skill Workshop compiles SKILL.md and test prompts from it and recompiles when a model or agent changes.

Takeaway. Give agents an always-on skill for filing structured friction reports (tried, expected, got, fix), then group the reports by skill; agents can spot silent failures that humans never report.

Audit of 12 agent benchmarks finds graders wrong in eight

Eugene Yan's review finds graders that fail correct work and pass hallucinated work, which matters more as model errors shrink and grader bugs stay put.

Eugene Yan reviewed twelve public agent benchmarks. In eight, audits or issue reports show the grader failing work that should have passed. Preference Model rebuilt 65 Terminal Bench 4.0 tasks and found 41 graded on requirements the prompt never stated. Once those requirements were made explicit, one model went from 63% to 89%. DeepSWE swaps in hidden test files that clash with tests the agent wrote, so agents that check their own work hit compile errors. Graders also pass bad work. Harvey's legal benchmark uses an LLM judge that never sees the source documents, and Artificial Analysis found material hallucinations in over 60% of deliverables that passed every criterion. On AutomationBench, 57% of assertions are substring checks. One task passes any email containing a "3" and a "4", so an email with the two counts swapped still passes.

Yan's fixes: report pass^k, where a task counts only if all k trials pass. Two agents that both average 70% can score 70% and 17% over five trials. Discount cost per task, because agents can fail cheaply: AutomationBench models falsely declared success in 72–91% of the failures analysed. Treat a score as belonging to a model plus its harness (the prompts, tools and loop around it). On Terminal Bench 2.0, one model scored 32.6% on a neutral harness and 19.6% on its provider's own. Yan says some of these takes are "vibes", and the article's own numbers slip in places (55% vs 57% substring assertions).

“Saving on token costs may be token-wise and attention-foolish if an engineer has to spend days reviewing outputs”

— Eugene Yan on the post

Under the hood

  • Laban et al.: models scored 39% lower in simulated multi-turn conversations than single-turn; OSWorld 2.0 agents guess instead of asking and miss mid-task messages.
  • GDPval: GPT-4o cost about a tenth of GPT-5 per task, but counting expert review and redo time, it was slower than an expert working alone.
  • BrowseComp: human trainers who solved a question disagreed with the reference answer on 50 of 367 questions (14%).
  • Terminal Bench uses a do-nothing agent and an adversarial agent as negative tests, yet reviewers found 44 of 65 v4 tasks passable by cheating.

Takeaway. Evaluate candidate models inside your own production harness, score pass^k over repeated trials, and audit passing transcripts for wrong work, not only the failures.

Featured · planetscale.com · Nov 23 · 2 min

How hand-rolled sharding breaks over a store's first 1,000 days

PlanetScale wrote this to sell a product, but its failure catalogue holds up, and that product still leaves cross-shard atomic writes to the application.

The web app is deployed with % 8, so it sends user 13's order cancellation to shard 5. A worker still running % 4 marks the same order shipped on shard 1. Replication has already flipped direction and now copies only from shard 5 back to shard 1. When the worker redeploys and reads shard 5, the shipment is gone. That window, when processes on different versions disagree about where a user lives during a reshard, is the sharpest failure in Ahmed Darwich's walk through a made-up marketplace's first 1,000 days on app-level sharding. The usual fixes, making the old shards read-only or moving routing into a config service every process watches, make the window smaller. They do not close it.

The rest makes a good checklist. Each shard's own bigserial counter gives out order ID 1042 on two different shards. Instagram-style IDs embed a logical bucket, so a reshard moves buckets and never rewrites IDs. Etsy's single unsharded lookup database could cause a full site outage. One big seller forces an exceptions dict into shard_for. On one shard, an ALTER TABLE waits behind a 20-minute report, and every new query waits behind the ALTER. The ending pitches PlanetScale's Neki, sharded Postgres in preview, which by the post's own admission does not make cross-shard writes atomic.

“You ended up building a sharding layer, even though your team's actual job is running a marketplace.”

— Ahmed Darwich on the post

Under the hood

  • Instagram ID layout: 41 bits of milliseconds, 13 bits of logical shard, 10 bits of sequence; a separate table maps buckets to servers.
  • Saga for store credit: debit plus an outbox row in one local transaction, then an idempotent worker that retries the credit, plus a pending state and an undo step.
  • CREATE INDEX CONCURRENTLY can fail on a single shard and leave an INVALID index there that someone has to find and drop.
  • Notion's 2023 reshard: about 100 PgBouncer instances with up to 6 connections per shard each, so the poolers had to be sharded too. Slack took 3 years to reach 99% of traffic on Vitess; Etsy took 5.

Takeaway. Put a logical bucket number, never a physical shard, into generated IDs, and keep a bucket-to-server map so resharding moves buckets without rewriting keys.

Learn · today's concept

Logical buckets: sharding so that resharding moves data, not keys

The naive way to shard is shard = hash(key) mod N. It works until N changes. Going from 4 shards to 8 moves half of all keys. Going from 4 to 5 moves 80%, because a key stays put only when h mod 4 equals h mod 5, and that holds for 4 of every 20 hash values. Worse, if the shard number is baked into IDs or caches, every one of them goes stale at once, and processes still running the old N route writes to the wrong place.

The fix adds a level of indirection. Choose a fixed, large number of logical buckets B, say 1,024, and never change it. Each key maps to bucket = hash(key) mod B, and generated IDs can carry that bucket number. A separate, versioned map says which physical server owns each bucket. Start with 4 servers holding 256 buckets each. To grow to 8, each old server hands 128 buckets to a new one. Only half the data moves, which is the minimum, and no key is rewritten. Moving one bucket works like this: copy it, tail replication until it catches up, briefly fence writes to it, flip its map entry, and bump the map's epoch. Servers then reject requests stamped with an old epoch, which closes the mixed-version window where two processes disagree about where a key lives.

The costs: B is fixed for good, so pick it 10 to 100 times your largest expected server count. The map has to be stored durably and cached consistently. A hot key can't be split below its bucket. Cross-bucket transactions are still your problem. Use this whenever you shard by hand, because it is far cheaper to build in from day one than to retrofit.

Further reading: Dynamo: Amazon's Highly Available Key-value Store (DeCandia et al., SOSP 2007); Vitess documentation: Sharding, Keyspace IDs and Vindexes

Most never-solved SWE-Gym tasks have tests that reject correct fixes

Filtering out unsolved tasks does not help, because the mislabelled tasks that actually shape the policy are the ones the model sometimes solves.

Yikai Zhang, Mai Xu, Yunbei Zhang, Qirui Jin, Kenan Li, Yuwen Jia, Jinwei Yao, Xiangyu Zhang et al. — AMD

An AMD-led audit of SWE-Gym found that 74% of the tasks a Qwen3.5-9B base model never solves have a hidden test that rejects correct fixes, such as one demanding the upstream warning text word for word. The figure is 20% for tasks it sometimes solves. A verdict counted only when an executed alternative fix actually failed. GRPO on 512 audited tasks beat 512 original ones by 2.4 points on SWE-bench Verified and 2.7 on Pro. Simply dropping never-solved tasks did nothing, because they carry almost no gradient. The flawed tasks the model sometimes solves supply a fifth of the gradient-carrying groups. Caveats: one model and three seeds, and the per-benchmark runs overlap.

“A pass rate shows whether a task yields reward, not whether that reward is right”

— Yikai Zhang et al. on the post

Under the hood

  • Release: SWE-Gym-Verified, 1,087 tasks (184 with repaired statements), with every verdict and its executed evidence, under Apache 2.0.
  • 26.1% of passing patches were wrong. New tests caught a quarter of them, and held-out scores moved −0.1/+1.1 pp, within seed noise.
  • Adding one missing requirement to a statement raised the base pass count by 2.1 of 8 on average. getmoto/moto-4846 went from 0 to 7.

Takeaway. In RL coding datasets, check the tests of tasks the model sometimes solves as well as the zero-pass ones; pass-rate and reward-variance filters keep the label errors that carry gradient.

Featured · research.google · Nov 23 · 2 min

Google's DeepCrossAttention lets each transformer layer pick which earlier layers to read

A 30-layer model beats a 42-layer baseline, but the gains shrink as models get wider and larger, and the blog's speedup figure is bigger than the paper's.

The ablation in Google Research's DeepCrossAttention (DCA) paper (ICML 2025) shows the biggest perplexity gain comes from the simplest part: one learned scalar weight per earlier layer in place of the plain residual sum (DenseFormer-style). DCA extends this. Each block keeps a stack of earlier layer outputs and mixes them using per-dimension weights plus a per-token ReLU term. Three separate mixers produce attention's queries, keys and values, so a block can draw each one from different depths. To keep memory bounded, k-DCA stores only the input, the sum of the middle layers and the last k outputs. Setting k=2 cuts inference latency by 48% compared with k=24. Because DCA starts out identical to a plain residual network, it can be added to a pretrained model: 60k more steps cut perplexity by 0.19, against 0.02 for continued normal training.

On LM1B, a 30-layer DCA beats a 42-layer transformer. DCA reaches the baseline's final perplexity in a third of the time, beats Hyper-Connections by 0.59 perplexity and shows no loss spikes. The caveats: the models are 512 wide and trained on 128-token sequences, and gains shrink with width and model size, as the paper's own theory predicts. The blog's "up to 5x fewer steps" and "30-40%" parameter savings go beyond the paper's 3x and 29%.

“The biggest improvement in perplexity comes from GRN-v1, followed by DCA and GRN-v2.”

— Heddes et al. on the post

Under the hood

  • Training: 64 TPUs, 500k steps, batch 2048, 131B tokens, AdamW lr 0.0016 with inverse-sqrt schedule.
  • Overhead: under 0.2% extra parameters. ViT-S/16 on ImageNet gains 0.7% accuracy.
  • Theory (low-rank linear model): learned residual weights help most when the summed rank of the layers is low relative to the model width.
  • The blog says Moonshot's attention residuals and Thinking Machines' Inkling 2 use related designs; the fetched Moonshot paper was empty.

Takeaway. For anyone testing residual tweaks, start with learned per-layer scalar weights: the ablation credits most of the gain to them, and they can be added to an existing checkpoint.

arxiv.org · Nov 25 · 1 min

One in four agent recoveries after partial writes leaves lasting damage

A third of the damage is deletions and wrong first-time writes, which duplicate detectors and idempotency keys cannot catch.

Artem Trofimov, Boris Novikov

When an agent's code block throws after some of its API writes have landed, the agent usually rewrites the block and runs it again. In recorded AppWorld runs, 30 of 143 confirmed partial executions ended with harm still in the database, a weighted estimate of 24.6%. Two thirds were duplicates. The rest emptied carts that existed before the run or placed orders nobody asked for, which a repeated-call detector cannot see; it catches 41% of all harm. Idempotency keys chosen by the model did not help either, because gpt-oss-20b generated a new ID each time it retried the same operation. The weak points: an LLM did the labelling, and the sample is mostly one shopping app and one gpt-oss-20b setup.

“The footprint of the failed block is evidence of what was done but not a permission.”

— Artem Trofimov and Boris Novikov on the post

Under the hood

  • Keys hashed from call content (sorted JSON arguments) would have caught every harmful write in only 14–18 of 30 recoveries, and would also have blocked 250+ cart writes the task needed.
  • Routing every write through the idempotency wrapper stopped all direct writes that skipped it (0/184 vs 503/823), yet harmful runs went from 5 to 7. The pilot was 17 episodes, one prompt.
  • 49 of 51 harmful continuations were never repaired. Data, labels and scripts are at github.com/flame-stream/agent-recovery-harm.

Takeaway. Before an agent retries, check the current state against the task. Idempotency keys, from the model or from call content, miss deletions and wrong first-time writes, and can block legitimate repeated writes.

Featured · arxiv.org · Nov 23 · alphaXiv ▲35, 607 reads · 2 min

On-policy distillation that uses verifier agreement to steer extrapolation

The idea is neat, but at n=4 rollouts about 65% of prompt groups give no verifier signal and fall back to a fixed coefficient, and the margin over that fixed-coefficient baseline is 1.1 points.

Juntong Shi, Stefano Ermon, Jure Leskovec, Minkai Xu — Stanford University, Google DeepMind

The method comes down to one scalar per prompt, c_x. It is the within-group correlation between the verifier's reward and the teacher's cumulative implicit reward, log pT(Y)/pref(Y) summed over the response. On-policy distillation (OPD: the student samples, then minimises reverse KL to the teacher's logits at each prefix) gives dense feedback, but nothing ties it to whether the answer is right. GRPO is tied to verified outcomes but sparse. VOPD, from Stanford and DeepMind, adds λ·c_x·Σ_a pθ(a|s)·log(pT/pref) to the OPD loss. That is the same as distilling toward pT^(1+λc_x)·pref^(−λc_x). When teacher and verifier agree, the target moves past the teacher; when they disagree, it moves back toward the reference. The term sums over the whole vocabulary, so tokens the student never sampled also get the verifier-weighted signal, with no extra verifier calls.

In the 4B-to-4B setting (Qwen3), the average over eight math benchmarks goes from 64.71 with plain OPD to 66.38. That beats the teacher (64.16) and ExOPD, the fixed-extrapolation version (65.25). The 1.7B student reaches 53.32. The caveat: with 4 rollouts per prompt, about 65% of groups are all-correct or all-wrong. There c_x is undefined and VOPD falls back to ExOPD's fixed λ=0.25. The paper reports no seeds or variance, and it needs teacher logits plus a frozen reference model.

“With n=4, approximately 65% of rollout groups have zero verifier-reward variance on average.”

— Juntong Shi et al. on the post

Under the hood

  • Setup: trained on DAPO-Math-17k with top-16 token distillation in VERL/FSDP, vLLM for rollouts, 8×A100 per run, λ=0.25.
  • λ ablation: 0.25 is best on AIME 24 and 25; larger values degrade, which the authors read as over-amplifying modes the teacher already prefers.
  • c_x is positive on average but widely spread: a nontrivial share of groups come out neutral or negative, and those are where VOPD differs from ExOPD.
  • With n=8 there are slightly fewer zero-variance groups and results are similar or slightly better. Cost: one extra reference forward pass per rollout batch.

Takeaway. During OPD runs, log the per-prompt correlation between the teacher's log-ratio and verifier reward. Negative groups show where imitating the teacher works against task success.

Agents sharing a vLLM server can signal through kernel rounding and the KV cache

The channel works perfectly on an idle server with a fine-tuned reader, mostly breaks under real traffic, and closes with settings vLLM already ships.

Two Qwen3-8B agents on one vLLM server, with no direct way to message each other, passed an 8-way colour choice in 1,221 of 1,221 rounds. vLLM picks a GPU kernel based on how many tokens an engine step processes, and each kernel leaves its own deterministic rounding pattern in the activations. A shared prefix-cache entry keeps the pattern of whoever computed it. The reader was fine-tuned and told the protocol. Under replayed Azure traffic at full speed, the KV channel's success rate fell to 49%. Batch-invariant kernels, per-user cache isolation or separate engine instances close it. amluto on HN notes that browsers learned to partition caches by origin long ago.

“Web browser developers learned, quite a while ago, that caches need to be separated for different origins.”

— amluto on HN

Under the hood

  • Colluding monitor, step-size signal: let through 354/354 signalled attacks, caught 85–92% of honeypots, flagged 0/1,596 benign actions.
  • Untuned frontier models decoded the KV mailbox from helper log-probs in context, but only with the protocol given; success jumps above ECI ~150.
  • Worked on SGLang, LMDeploy and TensorRT-LLM; step-size channel on A40, 4090, 5090 and H100, though the trained detector did not transfer across GPUs.

Takeaway. Serve monitor models on a separate engine instance from the policy, and key prefix caches per security context so tenants cannot probe each other.

lucumr.pocoo.org · Armin Ronacher · Nov 25 · 1 min

Rust mutex poisoning turns one panic into a lasting outage

The Rust libs team is weighing non-poisoning locks as the next edition's default, and Armin Ronacher brings bug reports from real projects to argue for it.

In Rust, a panic while holding a std::sync::Mutex poisons the lock: every later lock() returns an error, so every lock().unwrap() panics too. Thread pools, request handlers and tokio tasks catch panics, so the process stays up but stops working. A Neon safekeeper failed every timeline lookup this way, and Mozilla's application-services saw PoisonError reach rank 5 in crash stats, then moved to parking_lot. Because PoisonError holds the lock guard, m.lock()? can deadlock. Ronacher wants nonpoison locks as the default and an opt-in Poison<T> wrapper.

“In the entire history of the standard library, we have never once seen a single report of anyone attempting to recover from poison.”

— Josh Triplett on HN

Under the hood

  • The standard library's own stdio, backtrace and panic-capture locks ignore poison, and an open PR moves its internals to nonpoison. Tokio, Wasmtime, crossbeam-channel and tracing-subscriber ignore it too.
  • RefCell never poisons, yet panics caught in a tokio LocalSet leave the same broken state. An early return via ? also breaks invariants without poisoning anything.
  • clear_poison only arrived in Rust 1.77. He rejects the counter-proposal to make lock() panic on poison. Opposing view: sunshowers' 'In defense of lock poisoning'.

Takeaway. Look for lock().unwrap() on shared statics in code that catches panics. Either set panic = "abort" or use a lock that does not poison.

PyTorch's KL divergence is badly wrong for nearly identical distributions

The usual fix is to clamp negative values to zero, but that hides the many wrong values that stay positive and zeroes their gradients, and FP64 does not fully fix it either.

When two distributions are close, KL is tiny (it shrinks with the square of their difference), but PyTorch builds it by adding and subtracting much larger terms, so rounding swamps the result. Once the true KL nears FP32 rounding precision (about 6×10⁻⁸), 86% of values are off by at least 1%, and about 30% come out negative at smaller values. Running the same formulas in FP64 still leaves 7–51% significantly wrong. The fix is to rebuild KL from terms that are never negative, such as x − log1p(x), and compute it from logits. On HN, fluxem calls near-identical distributions contrived. The paper's counterexamples are rollout-versus-trainer gaps in RL and checking how far an 8-bit quantized model has drifted.

“Here we go, a slop paper for a contrived problem. They assume two near identical distributions, which is never the case in real training”

— fluxem on HN

Under the hood

  • Distillation test: a student starts as an exact copy of its teacher, so it should never move. Under Adam it drifts to 31–47% top-1 disagreement in FP32 and 97.4% in FP16.
  • Qwen2.5-1.5B vs its 8-bit copy: F.kl_div misreports mean KL by −19% with 30% of tokens negative; the logits path matches the FP64 reference on every token.
  • Repairs are unoptimised reference code, 2.4–5.9× the official call on GPU for five families; the code is at github.com/xi-xiaoran/stablekl.

Takeaway. Compute KL penalties and drift metrics straight from logits with a stable formulation; F.kl_div on log_softmax outputs inherits rounding error that no clamp or operator fix removes.

Tencent's Loop-PP brings pipeline parallelism to looped transformers

It saves up to 32.8% of peak memory. At PP8 it trains slower than simply unrolling the loop, because thin stages leave too little compute to hide the feedback traffic.

Yunjia Xi, Jiarui Qin, Di Yin, Xing Sun — Tencent

Megatron's interleaved 1F1B assumes each micro-batch passes through each pipeline stage once. A looped model breaks that: the last stage feeds the first again, and the schedule stalls. Tencent Youtu's Loop-PP treats each pass through a stage as its own step, schedules those steps in 1F1B order with a priority Kahn sort, and compiles a fixed send/receive/compute order for every GPU. One copy of the weights is kept. On 8B–60B MoE models it cuts peak memory by up to 32.8% and gives 12.7% more throughput on 32 GPUs. At PP8 it is slower than unrolling the loop.

“sufficiently thick compute chunks are important for amortizing the recurrent pipeline overhead, and Loop-PP should avoid overly fine pipeline partitions.”

— Xi et al. on the post

Under the hood

  • vs Lockstep (conservative dependency-respecting 1F1B): 1.9× faster at PP2, over 6× at PP8 on 30B.
  • Matches a single-stage reference bit-exactly over 5 steps; after 1,000 steps at 3 loops, loss differs by 5.43e-4.
  • Doubling chunk size (VPP2→VPP1) lifts throughput from 64.7k to 71.3k tokens/s; going from 2 to 4 loops erodes the advantage.

Takeaway. When training looped models with pipeline parallelism, keep pipeline stages thick, because cross-stage recurrence wait time is almost entirely dependency-limited.
