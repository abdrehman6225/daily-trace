Gemini 4 Hydrogen: Google's fast execution model, plus Orchestrator for in-session model handoff

A cheap model adapted from Carbon scores just above Argon on Artificial Analysis, and it comes with a planner/executor routing design worth copying in your own agent harness.

Google DeepMind released Gemini 4 Hydrogen, the fast model in the Gemini 4 family, sitting below Carbon and Argon. The model card says it is "adapted from Gemini 4 Carbon" and gives no architecture, data or distillation details. It has a 1M-token combined input/output window, 64K synchronous output, and up to 1M output via "background long decode". Knowledge cutoff is March 2026. Pricing is flat across the full window: $1.50 per million input tokens and $7.50 per million output. There are four thinking levels: low, medium, high (the default) and a new xhigh. It scores 51 on the Artificial Analysis Intelligence Index at high (Argon scores 50) and 54 at xhigh. Against Gemini 3.8 Flash, Google reports 57% vs 18.2% on Terminal-Bench 4.1, tasks finished 2.5x faster, and more than 5x fewer fabricated claims.

The part most relevant to agent work is Orchestrator in Antigravity. Google argues that static routers, which pick one model from the first prompt, stop working on long tasks because difficulty only shows up partway through. Orchestrator switches models in both directions within one trajectory. Carbon runs a read-only phase to explore the code and writes a plan with explicit re-planning triggers. Hydrogen then edits files and runs tests. When Hydrogen hits friction, it hands back to Carbon, which inspects the state and repairs the plan. Google reports near-Carbon success with 24% less quota and 19% faster runs. The posts disagree on the benchmark: the main blog says Terminal-Bench 4.0, the Antigravity blog says 4.1. For parallel work, Carbon coordinates while Hydrogen runs worker and verifier agents in isolated workspaces.

On safety, the model card is less flattering than the blog. Unjustified refusals rose 5.57 percentage points over 3.8 Flash, mostly on multimodal prompts. Hydrogen also reaches the alert thresholds for biological and cyber risk under Google's Frontier Safety Framework, though not the critical capability levels (CCLs) themselves. The full safety report is "coming soon".

Under the hood

  • Hydrogen batches file-read and search tool calls in parallel. Partners report 2x to 2.8x speedups and 12% to 23% fewer tokens than 3.8 Flash.
  • Other reported scores: HLE-Diamond 58.8%, Vals Tax Agent Bench 52.3% (#1 overall), Multimodal Knowledge Agent (MKA) 53.4%, Agents' Last Exam v1.1 71.6%, Agent Arena #5.
  • Agent safety claims: up to 81% less overreach, 12x fewer misaligned or shortcut actions, 2.3x more resilient on the Gray Swan prompt-injection benchmark, 96.7% honesty rate on Google's internal eval.
  • A Material Capability Change (MCC) check found no gain over Argon, so Google skipped the full suite of frontier risk tests and ran only targeted CBRN and cyber assessments.
  • The Antigravity SDK lets you assign roles to each model directly. Google's demo uses Hydrogen for issue triage and fast edits, and Carbon for refactors and security checks.

Takeaway. If your agent harness routes each task once at the start, try routing by phase: a strong model plans in read-only mode and sets explicit re-plan triggers, a cheap model executes, and it hands back to the planner on failure. Treat the benchmark numbers as vendor claims for now, since the two posts even disagree on which Terminal-Bench version was used.

A 22-year-old Postgres type-confusion bug becomes reliable RCE

A database-internals masterclass: how Postgres's untyped Datum plus mutable composite types let any low-privilege login corrupt memory and hijack control flow.

Postgres stores every value as a Datum, an 8-byte carrier that does not know its own type. The type is decided externally by an OID row in the pg_type catalog, which picks the typinput/typoutput functions. Mehmet Ince (reporting alongside core devs and OpenAI/Anthropic researchers) found you can bind a value as one type and read it back as another. The trick: PREPARE a query that casts a crafted string into a one-field composite type whose field is uuid, then ALTER TYPE ... ALTER ATTRIBUTE key TYPE bytea CASCADE, then EXECUTE. ALTER TYPE rewrites the row layout but not the already-stored bytes, so record_out() feeds the old UUID bytes to byteaout().

Because bytea is varlena, a leading 01 byte marks an external expanded object and the next 8 bytes are read as an ExpandedObjectHeader*. The chain crashes dereferencing NULL at EOH_get_flat_size(). Supplying a fake header plus methods table turns eohptr->eoh_methods->get_flat_size(eohptr) into system(H), with H's first bytes holding the command string. No superuser needed; every managed provider tested was affected.

Under the hood

  • Crash path: record_out -> byteaout -> detoast_external_attr (01 02 -> expanded) -> DatumGetEOHP NULL -> EOH_get_flat_size(NULL) -> SIGSEGV.
  • Control hijack: fake header H points to methods table M holding system@plt; H is reused as the argument, so id>x fits in its first 8 bytes before the +0x08 methods pointer.
  • ASLR defeat: alter an array element from uuid to bigint[]; unnest() returns a by-reference text pointer that SQL then prints as a bigint, leaking an address.
  • Three adjacent UUIDs (16 bytes each) build the 48-byte minimum array; the final +4 skips the text header to reach the payload.
  • Fixed 9 Nov 2026: CVE-2026-6460 umbrella adds composite-attribute versioning; 21 variants reported, 6 of 52 release CVEs tied to this. Primitive dates to a 2004 commit, exploitation to 2015's expanded-object pointers.

Takeaway. When a value's type tag lives outside the value itself (here in a catalog that can mutate between prepare and execute) you have a TOCTOU gap no memory-safe language can close. Treat any "the type decides which function runs" dispatch as attacker-influenced unless the binding is immutable; note HN's point that this needs an authenticated DB account, so it is privilege escalation to host RCE, worst for multi-tenant and managed Postgres.

Atuin Threads syncs coding-agent sessions so you can resume them in another harness

It treats agent transcripts as append-only logs on an encrypted sync engine and exposes them to agents over MCP, so past sessions become searchable memory.

Atuin 18.24 adds Threads. It captures sessions from Claude Code, Codex, Pi, Omp and OpenCode and makes them searchable. You can resume a session, or fork it into a different harness on another machine, with atuin resume. Threads reuses Atuin's end-to-end encrypted sync engine, which syncs anything that can be modelled as an append-only log, and agent transcripts fit that model. Capture is opt-in. Sync can run on Atuin's hosted server, on a server you run yourself, or stay local. An atuin mcp server lets agents search past sessions themselves, for example to find abandoned attempts and the reasons they were dropped.

Under the hood

  • Fork example: an IO-bound investigation moved from a slow box to a MacBook, and the original thread later pulled the Mac's benchmark results to build a fix.
  • HN measurement: ~22 GB of sessions added 8.1 GB, because each conversation is stored twice, once encrypted for sync and once for search. A Tantivy index built in place stayed under 1 GB.
  • HN pushback: many sessions are throwaway noise. Alternatives include agents writing summaries to a shared doc, and hybrid BM25 plus embedding search over local logs.
  • Opt-in session sharing for teams, so a thread can be handed off like a Git branch, is still being built.

Takeaway. Agent transcripts are append-only logs, so any log-sync or log-index system you already run can store them as long-term memory. Plan for storage growth if you keep separate encrypted and searchable copies, and decide how you will filter throwaway sessions.

Rust 1.100 stabilizes the never type, custom allocators, DropGuard and Cargo dependency cooldowns

This release finishes several long-running Rust features and adds a supply-chain defense to Cargo that you can turn on today.

After 10 years and five failed attempts, Rust 1.100 stabilizes the never type !, the type of code that never returns, such as return or exit. You can now write it anywhere, as in Result<T, !>. Infallible becomes an alias for it. In editions before 2024, the fallback type changes from () to !, a small breaking change. The core Allocator trait now works with Vec and Box. core::mem::DropGuard runs a closure when the guard goes out of scope, and dismiss skips it, which gives you rollback on error. Cargo adds dependency cooldowns, unused-dependency warnings and a new build-dir layout.

Under the hood

  • Turn on cooldowns with [registry] global-min-publish-age = "3 days". The resolver skips newer versions unless they are already in Cargo.lock. cargo install ignores the setting.
  • The new cargo::unused_dependencies warning only appears when every target that could use the dependency is built. It never checks dev-dependencies.
  • The build-dir now puts the build-configuration hash on the parent directory instead of the file name. This prevents wrong or extra rebuilds when worktrees share one build directory.
  • An HN commenter points to #17388: cargo install now uses the lockfile shipped inside the published crate by default, so --locked no longer does anything.

Takeaway. Add global-min-publish-age to .cargo/config.toml now, since malicious crate versions are usually caught within hours or days. Use DropGuard with dismiss when a function must undo its changes on any error path.

GitHub Actions lockfiles replace manual SHA pinning, with gaps

If you run CI on GitHub, there is now an official way to pin action versions without filling workflow files with commit SHAs, but it does not cover everything yet.

GitHub Actions now supports workflow lockfiles. The usual advice was to pin each action to a full commit SHA, because tags can be moved to point at malicious code. Hugo van Kemenade's setup works like this: install the github/gh-actions-lock extension for the gh CLI and run gh actions-lock. It changes the uses: lines back to readable vX.Y.Z tags and writes .github/workflows/actions.lock, which records the commit SHA, owner_id and repo_id for each action. Renovate and Dependabot already update the lockfile. A separate CI job running gh actions-lock --verify fails when the lockfile is out of date with the workflows or a pin no longer checks out upstream.

Under the hood

  • The lockfile maps each workflow to its actions, and each action to its ref and a sha1- commit. The owner and repo IDs guard against a repo being deleted and recreated under the same name.
  • The verify job runs on the lightweight ubuntu-slim runner and pins the extension itself with --pin v0.4.1, which still has to be bumped by hand.
  • zizmor (a security linter for Actions) supports lockfiles from v1.32.0. Older versions still tell you to hash-pin.
  • zizmor's maintainer (HN): reusable workflows and Docker uses: are not locked. Composite actions are covered only through the workflows that call them. By default the tool also strips their hash pins, which leaves outside callers unpinned.
  • HN: all forks share one object store, so a pinned SHA could be a commit from a fork. Commenters want immutable tags made mandatory.

Takeaway. Adopt the lockfile together with a --verify CI job and dependency cooldowns. Keep hash pins on reusable workflows, Docker images and any composite actions you publish, because the lockfile does not cover them yet.

48 agents scan NASA lidar for Maya ruins, then miss the prior paper

This is a cheap multi-agent pipeline for visual search. Its weakest step was the literature check, not the vision work.

A software engineer, not an archaeologist, turned about 1,200 km² of public NASA lidar strips covering the Maya region into images. He had 48 agents inspect them one by one against a written guide. They flagged pyramids, plazas and platforms and rejected hills, sinkholes and roads. No classifier was trained. The agents then checked the raw point cloud to confirm the shapes were on the ground, not in the canopy. A literature-and-archive search called one hilltop civic centre unregistered, and INAH (Mexico's heritage institute) found no record of it. The site had in fact been published in Estrada-Belli et al. 2025, and the agents missed it.

Under the hood

  • The site has a levelled plaza, an oval pyramid at least 8–12 m tall, a raised courtyard and a possible aguada (rainwater reservoir), likely Classic period (AD 250–900).
  • It took under 72 hours from idea to INAH's reply. The report was written and translated into Spanish by the agents.
  • HN: commenters linked an earlier Bluesky post about the site, warned about looting, and pointed to lidarmap.uk, where amateur finds are reported almost weekly.

Takeaway. Fanning images out to many agents with a precise rubric is a workable way to search large visual datasets. Treat an agent's claim that something is novel as low-recall: check it against the primary literature yourself.

Gemini plus Z3 finds Go bounds panics, and shows a gap in go test -fuzz

A practical way to find latent slice panics in Go parsers, and a one-line fuzz-harness change that catches most of them in under a second.

Karl Weinmeister of Google DevRel compiles each Go function for RISC-V with -gcflags="-S -d=ssa/check_bce/debug=1". This lists the runtime.panicBounds traps left after the compiler's SSA prove pass has removed the bounds checks it can prove safe. He then gives the source and the disassembly to Gemini 4 Argon, which writes a Z3 model of the path to each remaining trap. Z3 is an SMT solver, a tool that finds inputs satisfying a set of logical constraints. A sat result comes with concrete bytes, and go test replays them, so every hit is a real bug. unsat only means "maybe correct." The LLM takes about a minute per function and Z3 takes milliseconds. The pipeline caught 3 planted bugs, cleared 3 safe parsers and found 3 latent bugs in his skill-lint CLI.

The most useful finding is about the fuzzer. In Go, a slice expression such as buf[a:b] is checked against the slice's capacity, not its length, and fuzz inputs almost always have spare capacity. In 386,741 fuzz calls, only 0.07% had cap == len. A uint8 overflow bug triggered by 19.4% of inputs survived three 60-second fuzz runs. Clipping the input with data = data[:len(data):len(data)] let the fuzzer find both overrun bugs (median 0.28 s and 0.17 s).

Under the hood

  • ParseTwoChunkFrame: the uint8 sum hdrLen+bodyLen wraps at 256 before the length guard. Z3 found a 59-byte input (48, 236) that slices to index 288.
  • skill-lint bug: overlapping LLM-generated line edits in ApplyReplacementChunks panic or silently overwrite earlier edits. The fix is to reject overlaps after sorting.
  • Only pure helpers go to the solver. A 10-line parser links 1,559 runtime symbols, and the 28 MB skill-lint binary has 32,321 symbols.
  • Extracted helpers must include their entry guards. With them, Z3's first sat answer caused a real panic in all six buggy functions. Results held with comments stripped.

Takeaway. Add data = data[:len(data):len(data)] to every Go fuzz target that slices byte buffers. Use a solver only on parsers that compute offsets from header fields or line ranges and still pass a short fuzz run.

Pathways is now on Google Cloud: one client runs training across the whole cluster

This is how Google trains Gemini: an RL loop with a sampler, reward model and trainer is described as a single dataflow graph, not as SPMD processes coordinated by hand.

Google made Pathways generally available on Google Cloud. In SPMD setups such as DDP or FSDP, every process runs the same program in lockstep, so a pipeline or an RL loop has to be coordinated by hand. With Pathways, one Python client writes JAX code against virtual devices. A resource manager maps them to TPU slices. Each block is a compiled SPMD program, and each edge is a tensor that the runtime moves and reshards. Futures let the runtime set up buffers and transfers before upstream outputs exist. A central scheduler puts all operations in one order, so collectives don't deadlock.

Under the hood

  • The post says hardware failures interrupted Gemini 2.5 training several times per hour. Pathways remaps work from a dead host to healthy chips instead of restarting from a checkpoint.
  • On TPU v5p, chips get 1,200 GB/s to each other inside a group but only 50 Gb/s (about 6 GB/s) to the datacenter network. Cross-group collectives therefore show up directly in step time.
  • Shared Pathways Service keeps a cluster running on GKE. Clients connect from a laptop or VM, borrow slices and give them back when they disconnect. The authors say Ray works one layer up: it orchestrates jobs, while Pathways changes how the training step itself executes.

Takeaway. When a workload has different stages that need to overlap, such as RL rollouts, scoring and training, describe it as one graph run by a central scheduler instead of peer processes syncing through blocking collectives. Using virtual resource handles also lets you remap work after a failure and start compiling before the hardware is ready.

Google tests its agent anomaly detector on five outside security benchmarks

A careful way to evaluate an async monitor for agent goal hijacking, with its results and blind spots stated plainly, including poisoned long-term memory.

Google ran its Agent Anomaly Detection, unchanged, on five public benchmarks it did not write: AgentDojo, InjecAgent, ASB, AgentDyn and AgentHarm, 1,774 sessions in total. The detector reads ADK agent traces and logs asynchronously and flags sessions that go out of bounds. The agent ran on gemini-2.5-flash. Each session's label comes from the benchmark's own code checking final app state, not from a model. The detector flagged 87% of the harmful instructions the agent carried out. On office tasks, 2–4% of benign sessions were false alarms. Poisoned long-term memory is the weak spot: it caught 4 of 18 such sessions.

Under the hood

  • Each harmful session is sorted as never read, resisted, or carried out. The detector flagged 11–25% of resisted injections and 1 of 141 never-read ones.
  • Cold start: on AgentDyn, recall was 33% with about 220 benign sessions of baseline and 99% with about 360.
  • False alarms reached 16% on AgentHarm, whose benign tasks use high-impact tools. About 6% of sessions returned no result. The detector only reports and does not block.

Takeaway. When you evaluate an agent monitor, label sessions with deterministic checks on final state and count recall only on harm that was actually carried out. Keep detection off the hot path and put blocking controls before tool execution.

Uber's Shard Manager places shards by reported load, not by hash

Uber moved Cadence off consistent hashing to central placement. The hottest host's CPU fell 38%, and the same traffic now needs about 40% fewer hosts. The design is simple enough to copy for any stateful sharded backend.

Cadence used to assign shards with Ringpop, a consistent-hashing library. Each host worked out ownership from its own gossip view, and no record was authoritative. Equal shard counts still left load uneven, and the hottest Matching host ran at about twice the average. Autoscaled hosts took shards by hash, not load, so the hotspots stayed. Shard Manager is open source and built with Go, gRPC and etcd. It elects one leader per namespace to place shards. Executors heartbeat liveness and per-shard load, and each application defines what load means (Matching counts tasks per task list). Spectators keep the shard map from a gRPC stream and route requests directly, so Shard Manager stays off the request path. Operators use smctl to look up owners and drain hosts or single shards.

The balancer is greedy. It smooths load and leaves alone hosts inside upper and lower bands around the average. Each cycle moves at most 1% of shards, from a hot host to the coldest, picking the shard that brings the two closest. Example: hosts at 160 (100+60) and 40; moving the 60 leaves both at 100. Shards that just moved must cool down first. On Matching, the hottest host's CPU fell 38% and its load relative to the average dropped from 2.3× to 1.4×. In 24 snapshots, load spread came within 5% of a constraint solver's optimum in 23 and within 1% in 14. Spread is the standard deviation of host load divided by the mean.

Under the hood

  • Two namespace types. fixed has a set shardNum, which suits History. In ephemeral, shards are created on demand and retire when they report DONE or sit idle past ttl_shard.
  • Each executor implements ShardProcessor (Start/Stop/GetShardReport/SetShardStatus). Every GetShardProcess call resets the idle clock, so don't cache the handle.
  • A drained shard returns FailedPrecondition. The docs say to handle it separately from Unavailable, because retrying won't find an owner.
  • Uber rejected Apache Helix: its interface is mainly Java and it needs ZooKeeper. Migration flags moved to Cadence's database-backed config so every instance agrees which ownership system is active. Uber also plans to make etcd optional.

Takeaway. If your cluster is sized for its hottest host, give each shard an explicit owner and place shards using load the application reports. Add hysteresis bands, a cap on moves per cycle and a cooldown so the balancer doesn't keep shuffling shards.

Netflix's synopsis fact-checker: cheaper and more accurate with specialised judges and a confidence cascade

A production LLM-as-judge design that cuts cost by half and catches more errors by escalating only uncertain cases and rechecking the judge's own doubts.

Netflix's old synopsis fact-checker made five identical calls to a reasoning model over contexts of 100k+ tokens and failed a synopsis if any call did. It now uses a cascade. A literal judge asks whether the synopsis is true. An implicature judge asks whether it misleads a new viewer. Both report a confidence score, and high-confidence verdicts stand. Low-confidence cases send the judges' own assumptions and doubts to a router. The router turns them into atomic claims (single checkable statements) and sends each to a web judge or a targeted source recheck. On show-level synopses, cost falls 52.4% and Recall-FAIL rises from 0.77 to 0.86. Median latency goes up.

Under the hood

  • Stage 2 flips FAIL→PASS only if every concession, including the original failure reasons, is supported. It flips PASS→FAIL if any concession is contradicted.
  • An LLM judge scored overlap with human rationales on gold-FAIL cases (0, 0.5 or 1). Overlap rose from about 69% to about 82%.
  • In ablations, more reasoning effort made the old judge too lenient and a smaller model made it too strict. Episode-level checks needed a full-show summary in the prompt to avoid over-failing.

Takeaway. Sampling the same prompt again only fixes randomness, not systematic reasoning errors. Split judges by error type, escalate only low-confidence verdicts, and recheck the doubts the judge itself admits as small, specific claims.

Training ColBERT-style encoders to keep their accuracy after token pooling

A small change to the loss function cuts the number of stored vectors per document by 4x and recovers most of the retrieval quality that pooling normally loses.

Tom Aarsen at Hugging Face trains multi-vector retrievers, which store one vector per token, so their documents still retrieve well after token pooling. Pooling uses Ward clustering to merge similar token vectors and keeps the mean of each group. The training loss averages the normal contrastive loss with the same loss computed on documents pooled to about 1/4 of their vectors. Clustering is a discrete step, so gradients reach the member tokens through a straight-through estimator. With ModernBERT-base trained on 120k MS MARCO triplets, NanoBEIR nDCG@10 at pool_factor=4 rose from 49.03 to 51.23. That keeps 97.8% of the unpooled score instead of 94.6%, with 74.8% fewer vectors.

Under the hood

  • The gains also showed up at budgets the model never trained on. With a hard cap of 4 vectors per document, nDCG@10 went from 37.22 to 43.00. Adaptive pooling at about 30 vectors kept 97.3% of the unpooled score, against 93.3% for the normally trained model.
  • Storage math from the post: 200 vectors of 128 dimensions at 4-bit residuals take 12.8 KB per document, so 12.8 GB per million documents. Pooling to 50 vectors brings that to 3.2 GB.
  • MultiVectorTokenPoolingLoss wraps an existing retrieval loss. Every pooler reuses the same encoder pass. The CUDA Ward clustering kernel runs 30–150x faster than SciPy.

Takeaway. If you store late-interaction indexes, fine-tune on the compressed form you will actually deploy, and measure against a baseline trained the same way except for the loss. Quantize first, then pool, then shrink dimensions with Matryoshka truncation.

Learn · today's concept

Late interaction (ColBERT MaxSim) and why token pooling costs accuracy

Single-vector retrieval squeezes a whole document into one embedding, so specific details like an entity name, an ID or a rare term get blurred. Cross-encoders read the query and document together and are very accurate, but they must run once for every query-document pair, so nothing can be precomputed. Late interaction sits between the two. The query and document are encoded separately, so document vectors can be indexed offline. But each token keeps its own vector, and the two sides are compared only at search time.

How scoring works: the encoder outputs one normalized vector per token (ColBERT uses 128 dimensions). For each query token, take its highest cosine similarity against all of the document's token vectors. Then add up those per-token maximums. This is called MaxSim. Example: a 3-token query against a 200-token document takes 3×200 = 600 dot products. You keep the best match in each of the 3 rows, say 0.91, 0.62 and 0.80, and the score is 2.33. The catch is storage: 200 vectors × 128 dimensions × 2 bytes is about 51 KB per document, or about 51 GB for a million documents. Token pooling clusters similar token vectors in a document and averages each cluster. With a pool factor of 4 the document keeps about 50 vectors (around 12.8 KB). But averaging blurs the sharp token matches that MaxSim depends on.

This is the trade-off today's paper tackles: train the model on the pooled form you will actually deploy, so it learns to keep its accuracy after compression. Use late interaction when exact detail matters, as in agent memory, code, entities and long domain text. A common setup uses a cheap single-vector or BM25 search to pick candidates and late interaction to rerank the top results. The cost is a larger index and more complex serving, for example PLAID-style candidate generation.

Evolving Infra: branch-aware KV eviction and in-place prefill/decode switching for agents

The agent harness reports forks, compactions and finished branches to the serving layer, which uses them to keep the right KV cache and rebalance nodes in seconds rather than minutes.

Hao Kang, Weili Xu, Ziyang Li, Zheng Du, Hanchen Li, Tian Xia, Song Bian, Tushar Krishna et al. — MIT HAN Lab

Prefill–decode (PD) disaggregated serving splits GPU nodes into prompt-processing (prefill) and token-generation (decode) roles. Today it fixes each engine's role at launch and indexes the KV cache (stored attention keys and values) locally, so rebalancing is costly. On Claude Code traces, Dynamo, NVIDIA's serving framework, takes 681 s per switch. Arrow switches in place but loses 55.5% of the available KV reuse. LRU eviction also discards KV for branches waiting on tools and keeps history that compaction has already replaced. Evolving Infra, from MIT HAN Lab with Georgia Tech, UIUC, Berkeley and NVIDIA, extends SGLang with one scheduling loop that serves both phases. It pools every node's host memory into a shared KV store readable over RDMA and keeps a cluster-wide prefix tree that counts the active agent branches referencing each block.

A planner learns iteration-time models online. It switches the split only when the predicted gain exceeds twice its standard error over 10 slices of a 600 s window. Blocks with zero count are evicted first. Requests go to the node with the lowest predicted time to first token (TTFT), and their KV is fetched while they wait in the queue. On 36 GB300 GPUs with GLM-5.2 and Kimi K2.6, throughput is 1.10–2.73× Dynamo's, mean latency falls 1.15–4.12×, P95 TTFT falls up to 13.92× and a switch takes 6.2 s versus 754 s.

Under the hood

  • Prefill time = c0 + c1·Σuncached + c2·Σ(t_uc·t_c + t_uc(t_uc+1)/2) + c3·Σrestored. Coefficients are fit by NNLS (non-negative least squares) during warmup; error is under 7%.
  • The decode model uses the expected fraction of MoE experts touched, 1−(1−k/E)^(t_fwd·B), plus a per-request term. Context length is ignored because it shifts timing only 2–7%.
  • A transfer between nodes of the same phase moves the branch's counts. A transfer across phases keeps them on both copies. Each branch counts at most one copy per phase.
  • On Claude Code traces, LRU eviction caused 39% of Dynamo's lost KV reuse. Late-loading pool fetches pushed P95 TTFT to 95 s.

Takeaway. If you own the agent harness, send branch IDs and fork, compaction and finish events to the cache layer. Reference counts tell it which KV is dead, which LRU cannot. Rebalance only when window-average workload signals show a significant gain, not on queue depth.

SparseRead limits what agents read, cutting tokens by up to 92.9%

A reusable reading layer for agent tools with a provable cap on downside cost. You can copy the pattern directly into memory and retrieval tooling.

Zedong Liu, Jiaan Wu, Xinyang Ma, Le Xu, Kai Wang, Yuanchao Hu, Dingwen Tao, Guangming Tan et al. — Institute of Computing Technology

SparseRead (ICT, Chinese Academy of Sciences) sits between an agent and the pages, files and tool outputs it reads. The agent states a Read Intent; Readers return an EvidencePack of source-anchored snippets plus which evidence slots remain unresolved. A Budgeted Read Gate caps cumulative sparse payload at the full-view length L, then falls back to the full view, bounding exposure at 2L per episode. Across six models (including Claude Opus 5) and five scenarios, tokens fall 15.7–92.9% (median 61.4%), with score kept or improved in 29 of 30 settings.

Under the hood

  • Forcing sparse reads on the wrong tasks raised token use by 309% on global statistics and 210% on rule coding. That is why the gate skips small artifacts and can fall back to a full read.
  • Compared on 15 settings against static RAG, agentic RAG, ACON (history compression) and observation masking: only SparseRead kept or improved score in every one. Static RAG lost score in 9.
  • Ablations: hybrid retrieval found the evidence 65.3% of the time at about 1,490 returned characters, against 60.1% for BM25. Combining session and access intent cut repeated reads per task from 4.8 to 1.5.

Takeaway. Have read tools take an explicit intent and return anchored snippets with a record of what is still missing. Cap total partial reads at the cost of one full read, after which the tool falls back to that full read, and compute exact results (like table sums) inside the tool so only the answer enters context.

Updating a world model's weights after every move teaches it unseen game rules within one play

A clean way to measure how fast a world model learns a new environment, plus evidence that gradient updates at test time beat an in-context recurrent state at this scale.

Ku Onoda, Haruto Kawano, Shota Takashiro, Kohei Hayashi — Third Intelligence, Inc.

Third Intelligence and the University of Tokyo ask how many exposures (prior occurrences of a game rule) a world model needs to predict a new mechanic. MechEval instruments 20 ARC-AGI-3 game programs to label 69 mechanics. It scores predictions only on the cells each mechanic changes, because copying the last frame already gets 98.8% of cells right. WARC is a 35M-parameter vision transformer pretrained on other games. It takes 20 gradient steps after every transition. Its accuracy on mechanics is 69.1%, against 18.4% when frozen. Four in five mechanics reach 80% accuracy, half of them within about 80 exposures.

Under the hood

  • Each update is a minibatch of 8 from the 10 latest transitions, 20 random older ones (replay) and rotated copies. Optimizer is Muon+AdamW. LoRA matches a full-parameter update.
  • Updating only every 5 transitions costs 10.5 points over the first four exposures. A frozen conv-GRU brings only 16% of mechanics to criterion, DreamerV3 9%.
  • In closed-loop play, a graph explorer ranks actions by how novel WARC's predicted frame is. This lifts its efficiency score (RHAE) from 0.15 to 0.46 (0.18 with frozen WARC). An oracle model reaches 1.39. Kaggle hidden-set score is 0.20.

Takeaway. If an agent must adapt within a single session, update its weights after every transition and replay older data, and don't count on a recurrent state alone. Score adaptation per rule on the state it changes, not on overall accuracy, which unchanged state inflates.

SimpleHC drops residual mixing and halves Hyper-Connections memory traffic

Frontier models already use Hyper-Connections. This paper finds which parts actually help and cuts the training overhead from about 7% to 2.4%.

Xiangdong Zhang, Xiaohan Qin, Sunan Zou, Tuo Dai, Bizhao Shi, Zhuo Xia, Yebin Yang, Yizhou Chen et al. — dots studio

Researchers from Shanghai Jiao Tong University and Xiaohongshu's Dots Studio take apart Hyper-Connections (HC). HC keeps several parallel residual streams and adds learned read gates, write gates and stream mixing; mHC is the variant that constrains mixing with Sinkhorn normalization. Two setups each match mHC on their own: learned gates with no mixing, or unconstrained mixing with fixed gates. Sinkhorn wipes out most of what mixing gains. SimpleHC drops mixing, so each sublayer just adds its output to the streams. Gates for 4 sublayers are computed from one shared starting state, reads are batched, and writes wait until the end of the group. Small scalar corrections recover the earlier outputs exactly. Memory traffic per sublayer halves, from 18C to 9C.

Under the hood

  • 30B-A2B MoE: loss is 1.561, the same as mHC. Benchmark average is 63.1, vs 62.9 for mHC and 62.8 for identityHC. It trails mHC on GSM8K and both on HumanEval.
  • At width 6144, training overhead is 2.4%, vs about 7.0% for mHC/identityHC and 27.7% for xHC. mHC adds under 1% FLOPs but 7–27% wall time.
  • Ablations: dropping the corrections raises loss from 1.660 to 1.705. Reusing one gate pair across the group drops the average from 55.0 to 53.5. At 10× learning rate on 230B-A6B, mHC's gradient norm spikes to about 1.9e6; SimpleHC's stays bounded.

Takeaway. Measure memory traffic, not FLOPs. If updates are purely additive, you can batch reads and defer writes across steps and fix the result exactly with cheap corrections. The custom kernels matter too: in plain PyTorch, SimpleHC's overhead is still 22.5%.

Meta's e-means beats Lloyd's k-means loss in about two epochs

The Faiss team's mini-batch k-means is 10–45× faster than Flash-KMeans on GPU and needs no hyperparameter sweep, which cuts the cost of training IVF vector indexes and quantizer codebooks.

Swann Bessa, Pierre-Emmanuel Mazaré, Gergely Szilvasy, Hugo Touvron, David Picard, Matthijs Douze, Hervé Jégou — Meta

FAIR at Meta (the Faiss group, including Douze and Jégou) turns mini-batch k-means into an exponential moving average (EMA) update. Each cluster keeps a decayed count N_j and a decayed sum S_j, and its centroid is S_j/N_j. On top of that they anneal the step size on a cosine schedule, revive a dead cluster every five batches by splitting a larger donor cluster, and finish by setting each centroid to the mean of its points from the last epoch. Batch size and peak step size come from log-linear scaling laws fitted on 75k runs, so no sweep is needed. e-means reaches the test loss of 25-epoch Lloyd k-means in 1.4–2.6 epochs, which is 9.5–45.5× faster than Flash-KMeans on an H100.

Under the hood

  • The laws were fitted only on DEEP and carried over to SIFT, SPACEV, arXiv and AG-News. On held-out datasets the batch law costs a median 0.19% extra MSE.
  • DINO10B: 10B DINO embeddings were split into 16.7M clusters in under one GPU-day. Assigning points through an IVF index over the centroids was 34× cheaper than exact search at 10B and gave no gain at 100M.
  • Starting from random centroids, e-means ends below Lloyd started with k-means++. The laws work poorly on low-dimensional or tiny datasets.

Takeaway. If you train IVF centroids or a quantizer codebook with 25 Lloyd iterations, try EMA mini-batch updates with a cosine-annealed step and dead-cluster splitting. They should reach the same loss in 2–3 passes over the data.

inclusionAI's Duo v1 combines an LLM that decides when to speak with a streaming audio-video generator

A full-duplex agent design worth studying: an explicit speak-or-wait decision every 0.71 s, causal masking across modules, and distillation on the system's own outputs.

Hengyuan Cao, Biao Gong, Guoshan Lu, Qiyuan Zhang, Lin Liu, Yiding Tian, Yilei Jiang, Yuxin Ma et al. — inclusionAI

inclusionAI's Duo v1 splits a real-time talking-avatar agent into two parts. The Intent module is a LoRA-tuned multimodal LLM that emits <speak>+text or <wait> for every 17-frame chunk (about 0.71 s at 24 fps). Its layer-50 hidden states then condition a causal audio-video diffusion transformer, initialized from MiniMax-H3, that generates the avatar's video and stereo audio. Distribution matching distillation (DMD) trains the generator on its own outputs rather than recorded ones, giving a four-step streaming generator. The fetched text contains no quantitative evaluation.

Under the hood

  • Most chunks are waits, so the loss is reweighted by category (idle wait, wait during user speech, opening, interruption) to stop the model from waiting forever.
  • Each chunk sees only inputs available at its decision point: the last frame is repeated rather than grouped with the next chunk's first frame, and noisy media tokens are masked from their clean targets.
  • In DMD's 'dual rollout', the frozen Intent module writes the final assistant turn and the generator conditions on its own history; camera drift is penalized using frozen VGGT rotation estimates.

Takeaway. When an agent is trained on recorded histories but runs on its own outputs, finish training on self-generated rollouts. Make 'act or wait' an explicit token and reweight the loss so the common no-op doesn't take over.

inclusionAI's ZoomGain-9B: RL data built from what a crop reveals

A cheap, model-agnostic way to make verifiable RL questions: find details that only show up when you zoom in, then ask about them on the full image.

inclusionAI

inclusionAI's ZoomGain builds training data for vision-language models from the global-to-zoom perception gap, meaning details that are clear in a crop but missed in the full image. Several models agree on where a target is and crop that region. Captions of the crop and the full scene are compared, and the details only the crop reveals become questions about the full image. Each answer is checked against the crop, ambiguous questions are dropped, and so are questions a model can answer without the image. Qwen3.5-4B and 9B were then trained with GRPO, a reinforcement learning method. The results table is only an image on the card, so no numbers can be quoted here.

Under the hood

  • ZoomGainBench has 1,000 questions over 941 images, in English and Chinese, covering attributes, counting and OCR, each with an evidence bounding box. The best of 28 models scored 61.08.
  • The RL set has 9,000 records over 7,713 images. Training uses a bundled EasyR1: one epoch, batch size 64, eight rollouts per question, on 8 GPUs.
  • The code is Apache-2.0. Evaluation runs on vLLM 0.19.1 at temperature 0 with Qwen3.5 thinking turned off.

Takeaway. To get RL data with answers you can check, look for a gap between a cheap view and an expensive view of the same input, then keep only questions the expensive view can verify. Also drop any question a model can answer without the input, which is a simple shortcut filter worth copying.
