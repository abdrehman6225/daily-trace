GrepMem: summaries plus a grep-searchable raw log beat structured agent memory

Why read · A USC paper finds that an append-only text log and one regex tool beat summarization and MemGPT-style memory on exact recall, and the setup is easy to copy into an agent harness.

Ziyan Yang, Taiwei Shi and Jieyu Zhao at USC start from SUPO, an RL method that summarizes the context when it fills and then resumes. GrepMem keeps that loop for the 32K-token working context. On top of it, the harness writes every message, tool call, output and summary to an append-only plain-text log. After the first compaction the agent gets one extra tool, grep_history. It runs case-insensitive regex over the log and returns paginated matches, oldest first, with surrounding lines. It can also just count matching lines. There are no embeddings, no index and no second model. They train Qwen3.5-9B with the same GRPO recipe under five strategies: ReAct, observation masking, SUPO, MemGPT-style memory and GrepMem.

On ContextBench (key-value and log recall over 33K–968K-token streams, questions asked afterwards), the trained GrepMem scores 97.4% / 95.3%. SUPO and masking get 6.6–20.7%. GrepMem uses 29% of MemGPT's tokens. On BCP-Multi (three BrowseComp questions per episode, 25–27 compactions each), it scores 46.9%: +8.8 points over SUPO for 6% more tokens, and +7.0 over MemGPT. When summaries already keep what matters, grep adds little. On AMA-Bench stream, which asks causal questions, the gain is 0.9 points and not significant, at 2.3× SUPO's tokens. The limits: one model and lexical search only.

Under the hood

  • Grep output: 10 matches per page by default (max 30), 1 context line (max 3), 6K-char cap per response, 10 s timeout.
  • Earlier grep results are skipped when searching the log, so the agent never re-matches its own old search output.
  • Training mix: 4,000 episodes, 70% single-question research, 15% three-question sessions, 15% synthetic ContextBench-style streams. Rewards are binary correctness.
  • RL raises GrepMem's average by 5.9 points to 66.4%. Log Triage gains 20.3; AMA-Bench barely moves (-0.6 / +0.3).

Takeaway. Do not let compaction be the only copy of the history. Keep the raw trajectory append-only beside the summaries and give the agent a paginated regex tool with a count mode. Run it before you build an embedding index, and expect gains mainly on questions that need exact IDs, values or counts.

Learn · today's concept

GRPO: group-relative advantages without a critic

PPO-style RL needs an advantage for each action: how much better was this action than expected? Usually a learned value network (the critic) supplies the 'expected' part. For LLMs the critic is often as large as the policy, which doubles memory. It is also hard to train when the only reward arrives at the end of a long completion. Group Relative Policy Optimization (GRPO), introduced in DeepSeekMath, removes the critic. It uses the average score of other samples for the same prompt as the baseline.

Step by step: for each prompt, sample a group of G completions from the current policy. Score each one with a reward, such as tests passed or a correct final answer. Normalise within the group: A_i = (r_i − mean(r)) / std(r). Give that same advantage to every token of completion i, then maximise PPO's clipped probability-ratio objective with a KL penalty toward a reference model. Example: G = 4 with rewards 1, 0, 0, 1 gives mean 0.5 and std 0.5, so the advantages are +1, −1, −1, +1. Now suppose all four rewards are 0, or all are 1. Every advantage is then zero, so the prompt produces no gradient. That is why the Hugging Face recipe drops tasks the base model always or never solves.

Trade-offs: GRPO saves the critic's memory and is simple to implement. In exchange it needs G rollouts per prompt, and its credit is coarse. Every token, and every tool call in an agent trajectory, gets the same score. That is why work like Tencent's ECA adds step-level credit for retrieval. Use GRPO when rewards are verifiable and rollouts are affordable. For long-horizon agents, add process-level or step-level rewards.

Further reading: DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models (Shao et al., 2024); Proximal Policy Optimization Algorithms (Schulman et al., 2017)

Thinking Machines' Inkling 2 Mini: open-weights MoE that runs its middle layers three times

Why read · A rare open looped transformer with ablations: running the middle layers repeatedly buys reasoning depth without adding parameters, but adds no stored knowledge, so the model relies on search and tools.

Thinking Machines released Inkling 2 Mini under Apache 2.0. It is a 24-layer multimodal MoE (mixture-of-experts) with 26.4B total and 3.4B active parameters. The middle 12 layers run three times per token, so 24 layers of weights do 48 layer applications, about 5.4B effective active parameters. Each token goes to 8 of 128 experts, and context is 1M tokens. The weights were trained in the format they ship in: NVFP4 (4-bit) for 20 layers and MXFP8 (8-bit) for the last 4. That means no conversion loss, and the checkpoint is about 20GB, enough for a 32GB Mac or a DGX Spark. Against Qwen3.8-27B it leads on DeepSWE v1.1 (48.2% vs 42.2%) and BrowseComp (79.0% vs 61.6%). It trails on multi-turn chat, many-constraint instructions and factual recall, and more passes do not improve recall.

There is no single residual stream. Each sublayer reads a learned softmax mix of earlier block outputs (Kimi's attention residuals). On passes 2 and 3, a "message" from the previous pass goes through a learned gate that starts fully closed, so looping can be introduced stably during training. Looping the middle 12 layers beat looping the last 12 on 27 of 28 evals. A non-looped twin cost 7.5% less to train but needed 140% more inference compute to match loss on 512k-token agentic traces. Goodfire's interpretability write-up found one activation coordinate holding 46% of the normalised squared norm. It flags the third block for the next pass to read, and the model clears it after the final pass.

A variable-loop variant was released for research. Its no-CoT task horizon (task length in human time it solves half the time without visible reasoning) rose from 16s at one pass to 37s at three. Its GPQA reasoning shrank from 3,703 to 1,661 tokens at five passes and stayed as readable. On HN, users reported 27 tok/s on a Ryzen 395 with llama.cpp Vulkan (a small patch adds about 30%) and about 10 tok/s on an M1 Pro. Some saw it get stuck reasoning in circles on knowledge-heavy prompts; the model card recommends capping output tokens.

Under the hood

  • Layout: four 6-layer blocks; layers 1-6 run once, 7-18 run three times with shared weights, 19-24 run once to produce the output. Model width is 2304.
  • Pruning: started with 8 of 384 experts per token and cut to the 128 most-used experts per layer in mid-training. It then trained on 1T tokens distilled from a larger internal model to recover lost performance.
  • Post-training: SFT, then RL over 2.2T tokens in 2,000 steps, plus on-policy distillation for alignment.
  • Stanford intelligence-per-joule on DGX Spark: 0.703, vs 0.430 for Qwen3.6-35B-A3B and 0.159 for Gemma-4-26B-A4B.
  • Runs on vLLM, SGLang, Ollama and llama.cpp GGUF (Unsloth) at launch; RL fine-tuning via SkyRL, Miles and NeMo AutoModel.

Takeaway. Looping adds compute per token, not stored knowledge, so pair a model like this with retrieval and tools rather than expecting it to recall facts. If you build agents on it, cap output tokens and agent turns, and require confirmation before destructive actions, as the model card advises.

Postgres 19 builds table-bloat cleanup into core with REPACK

Why read · If you run large, write-heavy Postgres tables, Postgres 19 moves bloat cleanup out of extensions such as pg_repack and into core.

The Snowflake blog post returned a 403, so this story relies on the title and the Hacker News thread (177 points, 29 comments). According to the post's title, Postgres 19 adds a built-in, faster REPACK for reclaiming table bloat, the dead space that UPDATEs and DELETEs leave behind in Postgres's MVCC storage (MVCC keeps old row versions for open transactions). Commenters quote the post as saying you need 2x the space of the table and its indexes during the operation, because two copies exist for a while. They also mention a USING INDEX option. One commenter asked whether it weakens MVCC consistency, so queries could briefly see missing rows. The thread didn't answer that, so read the original before relying on it.

Under the hood

  • Commenters compare pg_repack, which captures concurrent changes with triggers, to pg_squeeze, which reads Postgres's internals. One prefers the internals approach.
  • A commenter objects that the 2x temporary space and I/O spike is a footgun, unlike LSM storage engines, which compact gradually.
  • An operator says modern autovacuum keeps most table bloat in check. Index bloat is still the problem, and they handle it with scheduled REINDEX CONCURRENTLY.
  • Another commenter says Postgres 19's new plan hints are set with SET rather than in comments, which adds a round trip per query unless you pipeline.

Takeaway. Before you repack a large table, check that the disk can hold a second copy of the table and its indexes. Until the original post confirms what REPACK guarantees, treat its MVCC consistency as unknown.

MoQ author argues WebRTC drops audio that voice agents could wait for

Why read · If you build voice agents, the post argues that how long your transport waits for lost audio should match how long your model can wait.

kixelated, the creator of Media over QUIC (MoQ) and formerly at Twitch, argues that WebRTC is the wrong transport for voice AI. Audio retransmission is off by default, and NetEQ, WebRTC's jitter buffer, won't wait for retransmitted packets anyway. Playback follows arrival time, not timestamps. An LLM needs only the last word of a prompt on time, so the transport has seconds to recover lost audio. One second of Opus at 64Kbps is 8KB, about 6 QUIC packets. On HN, OpenAI's Sean DuBois replied that WebRTC NACKs (retransmission requests) already let the server decide whether to wait.

Under the hood

  • Each MoQ subscription carries a maximum latency, for example 500ms for speech-to-speech and 5s for STT→LLM→TTS. Both are merged into one upstream subscription that fans out.
  • Text-to-speech is generated faster than real time, buffered in RAM and played by timestamp: 2 minutes of audio is about 1MB. To handle interruptions, the server opens a new audio track and removes the old one. This behaviour is not IETF-standardized.
  • He calls Opus FEC (forward error correction) weak because each packet carries a copy of only the previous frame, and congestion loss comes in bursts. Pipecat now supports MoQ.

Takeaway. Set how long your transport keeps retransmitting to how long your model can wait for its input, not to how fast people talk. Audio is small enough to buffer for seconds, which costs little.

One-byte heap overflow in Ruby's upcase gives pre-auth RCE on stock Rails

Why read · If you run Rails or classic Sinatra on Ruby 2.4 through 4.0.9, you need to upgrade Ruby itself, not a gem.

Veria Labs found a bug in how Ruby's single-byte encodings (several ISO-8859 and Windows-125x) change case. These encodings have no capital ß, so upcasing it writes two bytes, SS, but the loop checks bounds for only one. The output buffer is sized at input length plus 20, so 21 ß characters overflow it by one attacker-placed byte. Default Rails and classic Sinatra reach this code path. Fixed in 3.3.14, 3.4.13 and 4.0.10. Ruby 3.2 and older are end-of-life and get no fix. A working exploit will be published on 25 November.

Under the hood

  • The overflow writes S (0x53) when upcasing or s (0x73) when case-folding. Copying the result back out also reads one byte past the buffer.
  • Reached through upcase, swapcase, downcase(:fold) and casecmp?. UTF-8 strings take a different code path and are safe. The upstream fix is commit ruby/ruby@d582f8f.
  • GitHub Enterprise Server 3.22.5 and earlier has no fix yet. GitLab, Mastodon, Chatwoot, OpenProject and Discourse have patched releases. HN commenters noted that AI tools now make it cheap to turn a one-byte overflow into a full exploit chain.

Takeaway. Check the Ruby version that actually runs in production, including Ruby bundled inside self-hosted products, and upgrade before the exploit is published on 25 November. If you write buffer code, check bounds on every byte you write, not once per character.

OpenSSL base64 overflow: real bug, disputed 9.8 score, and a fix that took four tries

Why read · Unless your service base64-encodes buffers of about 1.5 GB or more, the risk is low. The review thread is still a useful lesson in how to fix a C API that cannot report errors.

EVP_EncodeBlock() is OpenSSL's base64 encoder. With an input length near INT_MAX, the encoded-size calculation overflows, and the function can write past the caller's buffer. An input of exactly INT_MAX can also send it into a runaway loop. The pull request for OpenSSL 4.x (not yet merged) changed course several times. Returning -1 was rejected because existing callers may cast the result to size_t. OPENSSL_assert was rejected because it aborts even in release builds, which turns the bug into a crash anyone can trigger. The current version returns 0 and pushes ERR_R_PASSED_INVALID_ARGUMENT onto OpenSSL's error stack.

Under the hood

  • The new guard rejects input lengths above (INT_MAX/4)*3, because anything larger has a base64 output that does not fit in an int.
  • EVP_DecodeBlock passed its length check with n = -4, because -4 is a multiple of 4. The new test now gets -1 where the old code returned 3.
  • The bug is reachable from the CLI: pass a huge openssl s_client -proxy_pass through env:VAR with GOST. http_client.c only rejected len > INT_MAX.
  • OpenSSL and NVD rate it Low: no known path for an attacker to reach it, and the caller needs a buffer of about 2 GB. A CISA issue disputes the 9.8 score, and HN commenters note TLS itself never base64-encodes.

Takeaway. Size calculations in C should use size_t, and the function should take the output buffer's length so it can check it. Don't use an abort-on-failure assert for a case a CVE has shown can actually happen, because that turns memory corruption into a crash attackers can trigger at will.

OpenAI runs Codex agents as a state machine to fix ChatGPT regressions

Why read · A production agent harness with durable task state, event wake-ups, adversarial reviewers and spoiler-free backtest evals, all of which carry over to any agent workflow you build.

OpenAI's Performance Factory has four parts. A task service defines each workflow as a config.toml, which lists the states, the allowed transitions and the steps that need a human, plus one Markdown prompt per state. A dispatch loop checks on a timer for tasks ready to move and starts a Codex turn for each one. An internal API runs those turns inside OpenAI's network under a scoped service identity, with access to metrics, logs, traces and profiles. Subscriptions to PR comments, failed CI checks or finished deployments wake tasks that are waiting. State and findings live on the task, not in an agent's context, so agents and engineers can hand work back and forth.

The Regression Workflow moves each alert through four states: needs investigation, root caused, fix proposed, resolved. A perf-forensics skill holds the playbook: find when the slowdown really began, which can be hours before the alert fired; tell apart requests that got slower from a shift toward requests that were already slow; then check deployments and feature flags. A separate Codex session then tries to disprove each diagnosis and each fix. In just over three months it ran 1,700+ investigations and root-caused 600+. In a manual review of 100 diagnoses, 70% were graded accurate. Fixes are harder: proposals can be more complicated than needed, introduce new bugs, or need architecture tradeoffs a human has to make, such as a cache that risks stale data.

Under the hood

  • Investigation evals replay past incidents with a fresh agent that cannot see saved memories, incident writeups or earlier runs. Transcripts are checked afterwards for leaked answers.
  • Scored separately: when the problem began, how big it was, which requests were hit, and how causes were ranked. Getting the timing right can still mean blaming the wrong deployment.
  • After a fix ships, an agent checks whether performance is back to baseline. If recovery is partial, it resolves the task and opens a new one for the rest of the slowdown.
  • A daily agent scans recent runs for tool failures and permission errors, then opens fix tasks in the same factory to repair them.

Takeaway. Store agent work as explicit states on a durable task, wake it with events, and give a separate reviewer agent the job of disproving each conclusion. Build your evals from past incidents with the answers stripped out, and score each step separately.

METR: agents struggle more on tasks that are costly to turn into RL environments

Why read · If you evaluate agents with LLM judges or cheap containerized tasks, METR's data shows where those tests overstate capability.

METR's Q4 2026 update covers models up to Opus 5.5 and GPT-6 Astra. Across its older TH1.1 suite and the new 36-task TH2 suite, time horizon (the length of human task an agent finishes 50% of the time) doubles every ~3.6 months. On its own verifiable optimization tasks, models beat every expert METR hired as a human baseline. But tasks that are costlier to build into an RL environment are harder at the same human task length. METR also finds model judges overrate work from models as strong as or stronger than themselves by about 0.2 on a 0–1 scale.

Under the hood

  • Lifecycle Cost: the cost to build a container for a task plus run and score it 100 times, estimated by an Opus 5.5 judge. METR tuned the prompt against its own estimates on ~10 tasks.
  • The high-cost task subset is 2.9x costlier and gives 2.9x shorter time horizons (1.5 doublings). Both subsets improve at about the same rate.
  • TH2 verifiable subset: 27h horizon, doubling every 1.65 months (95% CI 0.79–3.99). METR suspects less varied task sets produce shorter doubling times.
  • Agent swarms beat best-of-k only on verifiable tasks with a clear metric and fast feedback. Elsewhere the effect was unclear or negative.

Takeaway. Don't let an LLM judge grade output from a model as strong as or stronger than itself without checking it against human labels. Also weight your agent evals toward tasks with slow or fuzzy feedback, because the cheap, automatically scored ones look like what labs train on.

Reflection's Beam: open-weight 501B MoE with 1M context and a 100M-rollout RL run

Why read · This is a frontier-scale agentic model that comes with a detailed recipe: stability tricks, scaling-ladder rules and asynchronous RL infrastructure numbers.

Reflection Team, Adam Abdulhamid, Osama Abuelsorour, Yasmin Alameddine, Carlo Alfano, Duarte Alves, Brandon Amos, Selvaraj Anandaraj et al.

Beam is Reflection's first open-weight model. It is a mixture-of-experts model (only some expert sub-networks run per token) with 501.3B total and 23.4B active parameters: 52 layers, 256 experts, no shared experts. It was pretrained on 23.8T tokens on 6,144 GB300s in under four weeks, at 21% MFU and 92.3% goodput. Two midtraining stages extend context to 1M tokens. The asynchronous RL stage used 10.5K GPUs for four weeks and produced over 100M rollouts, and scores were still rising when it ended. Reflection says Beam competes with GLM-5.2 while using 3–4x less inference compute. The excerpt does not state a license.

Under the hood

  • Attention: local and global layers at 5:1, with a 512-token sliding window. GQA uses 48 query heads and 8 KV heads. RoPE in local layers, no position encoding in global layers, plus per-element gated attention.
  • Depth-scaled residual: the residual stream is scaled by 1/√n, where n is the number of sublayers so far, which keeps its size constant with depth. The rate at which expert routing biases update decays on a cosine schedule.
  • RL platform: 110K concurrent rollouts, 12-second weight updates, 99.99% batch packing. Serving uses FP8/NVFP4 quantization and a 1.93B DFlash 2 drafter for speculative decoding.

Takeaway. Before adopting a change, run it at several model sizes and keep it only if it improves compute efficiency by more than 5% at every size. Below that, the gain can't be told apart from seed noise.

NVIDIA Dynamo for RL rollouts: cache-aware routing, delta weight refits, worker recovery

Why read · If you run RL post-training, this shows how to cut rollout stalls and where Dynamo leaves the hard work of keeping weights consistent to your framework.

NVIDIA places Dynamo between the RL framework and its inference workers. The router weighs cache reuse against queue depth: it sends repeated attempts at the same prompt to a GPU that already holds that prompt's KV cache, without piling them all onto one worker. ModelExpress pushes new weights from trainer GPUs, S3 or an already-updated peer over NIXL (NVIDIA's GPU-to-GPU transfer library). It can send an XOR delta (only the changed bits) against an exact base version. CoreWeave reports deltas of 0.14–0.95% of the BF16 checkpoint. The linked docs say all refit paths are Experimental, and there is no fleet-wide atomic update.

Under the hood

  • CoreWeave's '15×' compares the fastest delta Hot-Load with the average cold-start redeploy: Nemotron 3.5 Lightning, four replicas on GB300 NVL72.
  • During a Hot-Load the replica pauses but keeps in-flight requests and KV cache, so one request can span two policies. Strict on-policy runs must request a cache reset.
  • Docs: KV entries made under one policy are invalid under the next even if the tokens match. Version strings are caller labels, not tensor digests, and responses carry no per-token policy version.

Takeaway. Treat each policy refresh as a transaction your orchestrator owns: stop new rollouts, apply the weights, clear every cache tier, then check an immutable checkpoint ID. Admit a worker back only after it produces output on the new weights.

Gemini 4 Neon: Google's mid-tier agent model, with benchmarks that need context

Why read · If you send long-context or sub-agent work to a cheaper tier, Neon's numbers are strong, but some of them come mostly from the test setup.

Google DeepMind says Gemini 4 Neon is adapted from Gemini 4 Carbon. It is sold as the faster, cheaper middle tier for tool-heavy agents and sub-agents. The model card gives no size, architecture or price. What it does give: a 1M-token context, 64K synchronous output tokens (up to 1M through background long decode) and a March 2026 knowledge cutoff. Against Claude Opus 5.5 and GPT-6.2 Sol it leads GraphWalks long-context BFS (95.2% vs 66.8%/80.1%) and AutomationBench (56.3% vs 42.5%/41.3%). Under the hood

  • SWE-sweep: 39.0% vs 10.1%/8.3% with each vendor's own harness (Antigravity-CLI has a sub-agent fan-out tool), but 12.8% vs 3.6%/11.6% under the shared mini-SWE harness.

  • Safety: a Material Capability Change (MCC) check against Argon fell below threshold, so Google skipped full frontier evals and reused Argon's results.

Takeaway. Benchmark Neon in your own harness before routing sub-agent or long-context retrieval work to it. Its biggest coding lead came from a harness that fans work out to sub-agents, not from the model alone.

Hugging Face RL-trains LoRA adapters for specific agent harnesses on Qwen3.8-27B

Why read · The full recipe is open: GRPO runs inside the harness exactly as it ships, tasks are filtered before training, and the results are accuracy gains plus 50–70% fewer tool calls.

Hugging Face trained one rank-32 LoRA for Qwen3.8-27B per agent harness (Pi, OpenCode, Hermes Agent). Training used GRPO inside the unmodified harness, with a proxy between harness and vLLM recording the exact tokens. On the 51 hardest SWE-bench Pro tasks, Pi went from 39.2% to 64.7%. On Terminal-Bench 2.1 the adapters gained 6–16 points. On tasks both models solved, they made 53–72% fewer tool calls. Training tasks first passed openenv validate, then were kept only if the base model solved them some of the time but not always (171 of 442 scored tasks).

Under the hood

  • Merging: the three adapters' updates are nearly orthogonal (cosine 0.01–0.02). Concatenated to rank 96 at weight ½, they beat base under all three harnesses; at full weight agents drop to 13 tool calls per task and Pi falls back to base.
  • Recipe: TRL AsyncGRPOTrainer on 2×B200 (one GPU for vLLM, one for training); reward is verifier pass/fail plus a 0.1 tool-efficiency bonus; LR 1e-4 collapsed rollouts (turns 18→6), so they used 2e-5.
  • Caveats: the thinking-off adapters learned to write short reasoning-like text before tool calls ('reasoning leakage'); on out-of-distribution AutomationBench all adapters land between 17.7% and 27.0% vs 23.0% base, mostly within noise.

Takeaway. If your agent runs in a fixed harness, train in that exact runtime. Drop tasks the base model always or never solves, since GRPO gets no learning signal from them. Then check whether the cheaper runs come from the model quietly reasoning in plain text before tool calls.

NVIDIA Dynamo's Rust tool-call parsers come with a shared test corpus

Baseten's security design for 100+ GPU clusters across 20+ clouds

Why read · A concrete, reusable checklist for limiting blast radius when you run on untrusted, inconsistently hardened infrastructure.

Baseten moves inference workloads freely across hyperscalers and more than a dozen neoclouds (smaller GPU providers), which often hand over machines with public IPs and open ports. To apply one standard everywhere, it uses a threat model with four trust boundaries: the provider's infrastructure, partners who operate parts of the stack, customer workloads, and its own engineers. The main rule is that no credential or trust root covers more than one cluster. Each cluster gets its own certificate authority (CA) and a read-only deploy key, so an attacker who takes over a whole cluster cannot reach any other cluster or the control plane.

Under the hood

  • Customer builds run in microVMs, each with its own kernel. Customer images and platform images are kept in separate registries.
  • RDMA (direct memory transfer between nodes) goes through a node agent that approves each transfer. Cross-cluster traffic uses mTLS.
  • Credentials for distributing data rotate within an hour. SSH is key-only, granted on demand with MFA. The Kubernetes API sits behind an allowlist. A node cannot add itself to a cluster.
  • Audit, host, DNS and SSH logs are shipped off each cluster to one central system that pages on-call. Every cluster's external perimeter is scanned daily.

Takeaway. Check that no key, token or CA in your fleet is valid across clusters, and that each cluster pulls its config with a read-only key. Then send audit logs off the host so someone with access cannot erase them.

Fast-JEPA scores whole plans by predicted endpoint, not step-by-step rollout

Why read · The world-model planner keeps step-by-step prediction for building a plan and drops it when comparing finished plans, which cuts planning latency 2.4x without losing success rate.

Researchers from Wuhan University, Zhongguancun Academy and DeepCybo start from one observation. When you build a plan you need predicted intermediate states, because later actions are not chosen yet. Once a candidate plan is complete, a terminal visual-goal objective only needs its predicted endpoint. Fast-JEPA trains one latent world model to answer anchored queries: given the current observation's embedding z_t and an action prefix of length k, it predicts the k-step outcome directly, without feeding predicted states back in. A goal-conditioned action generator builds a proposal one chunk at a time, using intermediate queries. Then CEM (cross-entropy method: sample candidates, refit a Gaussian to the best ones) searches around that proposal and scores each candidate with a single terminal query. Cost falls from (NI+1)HW to HG+(H+NI)W.

Across four tasks (PushT, Reacher, Cube, TwoRoom), average success is 96.50% at 10.88 ms per plan. INTACT reaches 95.58% at 26.19 ms. On the authors' new DynaGoal benchmark (moving goals, deadlines, response delays), success is 73.83% vs 56.25% under goal and geometry shifts, and 87.67% vs 75.33% under deadlines. The limits: all tasks are small simulated ones, and DynaGoal was written by the same authors.

Under the hood

  • Ablations: without the proposal, success drops to 68.17% at the same search budget. Proposal only, with no CEM, gives 93.83% at 5.53 ms.
  • Terminal scoring vs recursive scoring: 96.33% vs 96.08% success. Scoring time falls from 11.16 to 2.32 ms.
  • Setup: H=5 chunks of B=5 actions, N=64 candidates, I=2 rounds, K=8 elites, ViT-Tiny encoder with 192-dim latents, SiGReg regularizer. Timings are batch-one on an RTX PRO 6000.
  • Training costs 5.95 GPU-hours, against 6.67 for INTACT and 188.05 for Fast-LeWM. Code: github.com/Sofilyzia/Fast-JEPA.

Takeaway. Spend expensive step-by-step computation only where intermediate state actually informs a decision. If only the final state matters, train the model to predict it directly from the anchor and score candidates in one batched call.

Allen-Zhu's 64-run study: Canon layers save 30% of tokens, linear models fail recall

Why read · A rare controlled architecture study at 1–8B scale shows that standard benchmarks miss the in-context retrieval failures that matter for agent memory.

Zeyuan Allen-Zhu

Zeyuan Allen-Zhu, with the experiments run at FAIR (Meta), trained 64 models from scratch at 1.3B, 3B and 8B on 1–2T Nemotron-CC tokens. The architectures were Llama, Mamba2, gated linear attention (GLA) and Gated DeltaNet (GDN). Each 8B run cost about $100k. Every configuration was trained at its 2–3 best learning rates, and the linear models were matched on parameter split, recurrent state size, heads and data batches. At 1.3B/100B tokens the architectures were nearly indistinguishable. At 1T the differences show. Canon layers are residual 4-tap causal convolutions that mix each position with its three predecessors, inserted at up to four points per block. They add 0.8–1.5 points on lm-eval (a 13-benchmark average) and reach vanilla's final MMLU with ~28% fewer tokens at 8B. With Canon, plain GLA ties GDN to within 0.3 points and beats Mamba2. That suggests most of what the delta rule (GDN) and the selective state-space update (Mamba2) add is short-range token mixing.

Standard benchmarks hide a weakness. In a test with five stated birth years and 500 unrelated filler tokens, linear models recall 72–98% against ≥99.5% for Transformers. At 2k filler tokens, no linear model goes above 73.3%. On a two-hop version of the task, where random guessing scores 33.3%, no model reliably beats chance.

Under the hood

  • Canon: h' = h + conv1d over the current and 3 previous positions, at positions A/B/C/D. It adds 0.07–0.15% parameters and 2.1–3.3% step time when fused with neighbouring ops.
  • LlamaCanon keeps RoPE (rotary position encoding) on only 1/4 of each head's dimensions. At 8B it matches Llama-3.1-8B using about 1/15 of the model-size × tokens budget.
  • GLA5/GDN2 replace the full-rank output gate, which takes 1/3 of the layer's parameters, with a rank-16 gate (6.55M vs 1.07B parameters at 8B). The freed parameters go back into the layer.
  • 8B Transformers reach about 50% on two-hop with no filler, but most of that edge is gone at 500 filler tokens. The paper says to put in-context reasoning data into pretraining early.

Takeaway. Compare full training curves and run targeted retrieval probes, not just benchmark averages; a model that wins lm-eval can still fail to recall facts from a short context. For long-term memory, keep attention in the path for retrieval rather than trusting a linear backbone.

TripleKV loads agent KV cache from SSD into DRAM while tools run

Why read · If you serve agents, KV caches evicted during tool calls are the main source of tail latency, and the tool call itself gives enough time to hide the reload.

Shashwat Jaiswal, Chloe Alverti, Mengmei Ye, Chen Wang, Hubertus Franke, Fan Lai, Tianyin Xu, Josep Torrellas et al.

UIUC, NTUA and IBM Research treat agent KV cache (stored attention keys and values) as three cache levels on vLLM: GPU HBM, host DRAM and SSD. An agent's next prompt reuses a prefix already known, so only the timing is uncertain. A per-tool latency predictor in the agent harness reads each call's arguments and live output. It times SSD-to-DRAM prefetch to finish just as the request is admitted, and never prefetches into the GPU. With 20 Qwen3-30B-A3B agents on one H100, critical-path SSD reads fall from 45–76% of requests to under 10%. P95 TTFT (time to first token) drops up to 49% against tiered vLLM.

Under the hood

  • Prefetch issue time is t_end + q − S_L3/B − ε, where q is vLLM's live queueing delay. The predictor's error averages 1.1 s, against 7.6 s for TokenCake's moving average.
  • DRAM is made non-inclusive with eviction order CACHED > BACKUP > PREFETCHED and a 120 s TTL. A watch list refetches GPU-evicted blocks from SSD, like a victim cache.
  • Built from about 3000 lines in vLLM plus a predictor under 300 lines of Python. It stays within 5% of an oracle and gets 2.9–3.5× the throughput of TokenCake and Continuum.

Takeaway. When you know what data comes next and only the timing is uncertain, predict the timing per operation type, prefetch into the cheaper tier, and keep scarce GPU memory for demand requests. Protect prefetched data in the cache, but let normal traffic still evict it under pressure.

Tencent's ECA gives RL search agents credit for each retrieval that helped

Why read · A cheap way to get step-level reward for retrieval agents without labelled passages, and a fix for the zero gradient you get when every GRPO rollout for a question fails.

Wen Wang, Jindong Wang, Jiahua Bao, Tu Yongsiqi, Yihao Liu, Junwei He, Wenkui Fan — Tencent

With an outcome-only reward, GRPO gives every search in a trajectory the same credit. When all rollouts for a question fail, the advantage is zero and the question teaches nothing. Researchers from Tencent and several Chinese universities add a signal used only in training. A frozen snapshot of the policy computes the log-likelihood of the reference answer, averaged per token, given only the question and the deduplicated documents retrieved so far. The agent's own thoughts and queries are left out, so it cannot raise the score by rewording them. The gain in that score is normalized, gated on novelty, scaled by 0.1 and added to each search call plus the reasoning tokens before it. Across seven QA benchmarks, the ECA-Horizon variant beats GRPO by 1.03 points of macro exact match on Qwen2.5-3B and 4.80 on 7B.

Under the hood

  • The signal is nonzero in 97.8% of all-failure groups (3,213 of 3,285). A variant that credits only the query tokens reaches 98.0% but scores 35.27 EM, below GRPO's 37.19.
  • Cross-fold normalization: the 8 rollouts are split into two folds of 4, each scored against the other fold, so one lucky spike does not set its own baseline. σmin=0.25, clip ±2.
  • Novelty gate: a search that returns no new document IDs gets no positive credit. Episodes with repeated queries at 3B: GRPO 42.40%, RLOO 54.07%, ECA-Horizon 24.84%.
  • At 7B: 42.62 EM vs RLOO 40.56 and GiGPO 41.09. Zero-shot on MultiHop-RAG: 89.22 vs GRPO 82.84.
  • Stated limits: tested only on QA. Using one answer alias misses bridge documents that do not yet raise the final answer's likelihood.

Takeaway. When you reward retrieval steps, score the evidence in a context that excludes the agent's own reasoning so the reward cannot be gamed. Give the credit to the reasoning that produced the query, not just the query tokens.

FlashMorph2 tests whole hybrid models to choose which layers keep full attention

Why read · The paper shows how to choose which layers keep full attention when converting a Transformer to a cheaper hybrid, and how far off scores measured one layer at a time with teacher inputs can be.

Disen Lan, Xuanda Wang, Jianbin Zheng, Huafeng Kuang, Wei Tang, Yu Cheng — ByteDance Seed

ByteDance Seed and Fudan's FlashMorph2 decides which layers keep full attention when converting a pretrained Transformer into a hybrid of full and linear attention. The earlier FlashMorph scored layers using soft blends of both attention types, fed with the original model's hidden states, while the weights stayed frozen. FlashMorph2 instead samples real hybrid models that meet the budget exactly, using Gumbel-Top-K (add random noise to learned scores, keep the top K). Each sample runs end to end on its own hidden states, and the weights train under the same distillation loss used later. On Qwen3-0.6B/1.7B it beats FlashMorph by +2.42 on RULER and +1.08 on LongBench.

Under the hood

  • Top-K is not differentiable, so a straight-through estimator passes gradients through a sigmoid version whose threshold τ is found by binary search so the soft mask sums to K.
  • Ablation on Qwen3-1.7B with Gated DeltaNet: without the end-to-end forward pass, RULER drops 29.55 points and all 7 full-attention layers end up in layers 20–27.
  • At a 6:1 linear-to-full ratio it scores 60.12 (GLA) and 64.45 (GDN) on RULER, beating uniform interleaving by 10.65 and 7.86 points. Selection takes 0.72–3.57 GPU hours from 0.6B to 8B, about 2× FlashMorph's cost but 8.4–20.8× less than HALO's.

Takeaway. When choosing parts under a budget, test whole discrete candidates end to end and let the weights adapt to each one. Scores measured one layer at a time with teacher inputs miss how errors build up, so they can point you to the wrong layers.
