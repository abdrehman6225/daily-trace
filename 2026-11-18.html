A private engineering paper for Abdul Rehman

Today's thread is agent memory and the harness around it, and how to measure both honestly. I've made the Apple study on memory in context versus memory in weights the lead instead of GPT-6.2, because it bears most directly on a memory engine: replaying past successful attempts verbatim is the baseline any memory layer has to beat, and memory can teach agents to skip their own checks. Three more papers come at memory from other angles: HEAMS tests deletion, leakage and poisoning; another paper shows recalls across several stores return mixed revisions unless the whole read is protected; and NVIDIA's FlashREINFORCE shows how to run asynchronous agent RL without groups of rollouts per prompt. OpenAI's GPT-6.2, the 27,280-run harness-cost benchmark and Dan Luu's eval of testing prompts for coding agents all say the same thing: re-measure cost per task and step count on every new model.

Agent memory: replayed past attempts beat weight updates, and RL on top helps further

A controlled Apple study compares memory in context with memory in weights for agents that keep working in one environment, and finds memory makes agents skip checks.

Parsa Mirtaheri, Mohammadreza Armandpour, Keivan Alizadeh, Iman Mirzadeh, Parshin Shojaee, Aryo Lotfi, David Harrison, Mehrdad Farajtabar et al.

Apple and UC San Diego ask where an agent that keeps working in one environment should store its experience: in its context window, in its weights, or both. They run Qwen3.5-9B on 109 tasks split into four "worlds": one xarray repo from SWE-bench Verified, the file-system app in AppWorld, ScienceWorld measurement tasks, and one BIRD-Critic-SQLite database. Each world is run in five task orders. On every task, 16 attempts are scored before the agent adapts to that task. Raw-trajectory ICL, which replays past attempts word for word, raises mean success from 28.8% to 49.4%. GRPO training on a persistent LoRA adapter helps less on its own. SDPO alone scores lower still. SDPO is self-distillation toward a teacher that also sees a successful sibling attempt. The best combination is ICL plus GRPO, at 51.6%.

The traces show why. ICL cuts code, API and environment lookups and shortens attempts. It also starts skipping checks the current task needs: on BIRD it more and more often submits SQL without running a single query. Adding GRPO keeps the fewer lookups and brings verification back. Querying recovers, tests are rerun after edits, and state is read back after API writes. SDPO does not reliably do this. The authors guess its teacher picks up ICL's shortcuts. The study's limits: one model and small task subsets.

Under the hood

  • Context policies: FIFO evicts the oldest episodes; Prefix stops adding after the first overflow. Admission is All (best attempt per round, even failed) or Successful.
  • Prefix–Successful was the best ICL policy. Both Successful-admission policies beat the baseline in 20/20 seed pairs; All admission sometimes hurt on AppWorld and BIRD.
  • GRPO setup: rank-32 LoRA, AdamW, lr 1e-5. Advantage is reward minus the round mean, with PPO's clipped loss, no KL penalty, no std normalization.
  • GRPO added to Prefix–All gained 6.3 points and won all 20 stream pairs. Under the other ICL policies it won 13–14 of 20. Framework is built on verl.

Takeaway. For an agent memory system, replaying past successful attempts verbatim is a strong baseline that any summarization or retrieval layer should have to beat. Track whether the agent still inspects and verifies its work, not just its success rate, because memory can quietly train it to skip checks.

Agent harness cost depends on the model, and on step count more than prompt size

A 27,280-run benchmark finds that the cheapest harness changes from model to model, and that cost follows the number of agent steps, not prompt size or tool count.

Runta and Baseten ran 22 harness configurations on 5 open models (GLM-5.3, GLM-5.3 Flash, DeepSeek V4.1 Flash, Muse, Kimi-K3), with 62 terminal tasks and 4 attempts each: 27,280 runs and 83B tokens. The model explains 92.8% of the variance in cost. With the model fixed, the harness still changes cost per task by 1.8 to 5.0 times, and the cheapest harness differs by model: Codex CLI ranks 1st with GLM-5.3 and 16th with Kimi-K3. Spending more did not raise pass rates. Cost per pass followed steps per pass (ρ=+0.51), not prompt size, tool count or cache hit rate. Of all spend, 64.5% went to runs that failed.

Under the hood

  • Every step resends the whole context, so a trial averaged 2.0–4.8M input tokens. mini-SWE-agent has the smallest first prompt (882 tokens) but took 38 steps per pass and ranked 17th of 22 on cost per pass.
  • The best-value harnesses lean on one shell tool (61–93% of tool calls), only ever append to the context (91–94% cache hits) and rarely use subagents. Most failed runs (68–82%) ended with a confident final answer.
  • HN: one commenter's analysis of 927k runs found little harness×model interaction. The authors' own pass rates carry ±10-point 95% intervals, and passing the tests does not mean the code is good.

Takeaway. When you switch models, re-benchmark the candidate harnesses on your own tasks. To cut cost, reduce the number of agent steps, not prompt tokens; a check before the agent stops could catch some of the confident failures (the authors suggest this but did not test it).

How Claude Code gates agent-written code: verify skills, diff-triggered checks, locked rules

A production team describes the verification harness that lets it run many coding agents in parallel without a human reading every diff.

Addy Osmani writes that Claude writes and reviews about 90% of the Claude Code team's code. Each repo has a verify skill in .claude/skills/ that starts and drives the real app. If a check still fails after three fix attempts, Claude stops and calls a human. A 39-item reliability checklist runs only the items whose trigger matches the diff, usually 3 to 10. Review rules in REVIEW.md are read from the base branch, so a change can't edit the check that judges it. New commit gates run in observe mode before they block anything.

Under the hood

  • In internal tests on structured file generation, a separate grader scoring against a rubric raised task success by up to 10 points over a plain prompting loop. Gains were largest on the hardest tasks.
  • A missed bug becomes a rule only if the pattern shows up in at least 2 PRs, survives 3 agents trying to disprove it, and a human approves it. Flaky tests must be root-caused or deleted with a written reason, never retried or padded with sleeps.
  • HN: the top comment says a deterministic Playwright suite (a browser-test tool) gives the same coverage at near-zero ongoing cost, compared with agent browsing that spends tokens every run. Others question whether the token budget is sustainable.

Takeaway. Keep agent gates where the change can't edit them, trigger checks from the diff, and score recall separately at each review stage. Write cheap deterministic tests for repeated checks and save agent-driven runs for new behaviour.

Dan Luu re-runs his agent testing eval: with GPT-6 Astra, several testing techniques now beat Default

A $90k eval of which testing and verification prompts actually help coding agents, plus evidence that a skill tuned for one model can hurt on the next.

Dan Luu re-ran his agent testing eval on GPT-6 Astra. Implementing Zstd from its RFC is now solved: Astra gets every holdout test passing in over 99% of runs for $1 at medium effort. GPT-5.6 Sol managed 63% for $3.50. So he moved to Pandoc, with 25 runs per condition, about 14 turns each and roughly $90k at list price. With Sol, no testing instruction beat Default (no instruction). With Astra, many did: differential testing, the theorem prover ACL2 and the Rust property-testing library proptest did well, and TDD lagged again. The sample is small, so confidence is low.

Under the hood

  • Differential testing made agents look closely at boundary conditions. Hegel skills cost more than Hegel with no skill, for similar correctness. His testing skill tuned on Sol underperformed on Astra.
  • He rejects a viral DeepSWE claim that agent-written tests are useless. It showed only a 9% cost saving on easy problems, and the grader penalizes tests whose names clash with its hidden tests.
  • Reader case study: rewriting a TypeScript state machine took 30k lines of production code and a 300k-line generated-test harness, which found about 20 of 230 bugs. Agent reviewers found the rest.

Takeaway. Keep a no-instruction baseline and re-measure testing prompts and skills on each new model and at your real task size, because results so far have not carried over. If you add one testing technique, try differential or property-based testing before TDD.

Java4Shell: padding bug in HotSpot's AVX-512 Base64 decoder enables RCE

If you run Java 17.0.6+ on recent Intel or AMD servers, any endpoint that decodes Base64 can become a heap-corruption path, so patch or set one JVM flag.

Calif disclosed CVE-2026-114938 (CVSS 4.0 9.2), a memory-corruption bug in the x86-64 Base64 intrinsic, the hand-written AVX-512 VBMI assembly the C2 JIT swaps in for Base64.Decoder. For a padded tail like = or X=, output_len computes to 0 then is decremented to -1/-2. Because bzhiq(-1, output_len) leaves the mask all-ones, the masked evmovdqub store writes all 64 bytes. Input 64*'A' + '=' allocates a 50-byte array then writes 62 bytes past it (128 A's on JDK 17). Java throws IllegalArgumentException, but neighbours are already corrupted. Affects OpenJDK 17.0.6+ on CPUs with avx512vbmi; ARM64 is immune.

The overwrite is fixed-value, so Calif groomed the G1 heap: corrupt a writer array's length to get a chosen-value linear write, corrupt a reader for a Heartbleed-style heap leak (JavaBleed), then repair damaged objects and escalate into the Code Cache. They showed pre-auth RCE in Keycloak, Jira, Confluence, Artifactory, Jenkins and PingFederate, and post-auth RCE in Kafka, Solr and Elasticsearch. Codex found the bug; weaponization took ~3 hours and under $200 in tokens.

Under the hood

  • Trigger input runs only after the decode method is JIT-compiled to C2 tier via repeated calls (PoC loops 200k times).
  • Remote exploit streams partial HTTP bodies and waits for TCP ACKs to control allocation order; RTT/jitter-sensitive, so they rented a VM in the target's region.
  • Chain stages: WARM (JIT), REHEARSE (calibrate), TRIGGER, DISCLOSE (leak), REPAIR (restore headers to avoid JVM crash), FINISH.
  • Mitigations: -XX:-UseBASE64Intrinsics or -XX:UseAVX=2 (x86-64 only; breaks ARM startup); patch shipped 1pm PT Nov 17.
  • No universal payload: each target needs a decoder route, live writer, feedback reader, heap layout and app action; nginx body-buffering blocks some but not Elasticsearch or post-WebSocket frames.

Takeaway. Memory-safe runtimes still ship C/C++/assembly intrinsics where off-by-one math corrupts the heap; audit the native fast paths and padding/length arithmetic, not just your own code. If you run x86-64 Java servers that decode untrusted Base64, patch now or disable the intrinsic.

Microsoft's ONNX Runtime repository is gone from GitHub, no explanation given

If your inference or eval pipeline pulls ONNX Runtime from GitHub, it may already be failing.

The microsoft/onnxruntime repository, which a commenter puts at 22k stars, no longer resolves on GitHub. Our fetch of its README returned 404. Microsoft has not said why, and the HN thread (172 points) found no advance warning. One team noticed only because its evals broke that morning. One commenter guesses a connection to a recent compromised Microsoft agent-framework PyPI package, but nothing confirms it. Intel's OpenVINO fork (intel/onnxruntime) was the most up-to-date copy anyone found.

Under the hood

  • The README fetch from raw.githubusercontent.com returned HTTP 404 (curl error 56), which fits the repo being deleted or made private.
  • A commenter says ONNX Runtime sends telemetry by default, and the only opt-out is building from source with it disabled or blocking DNS.

Takeaway. If a build or eval job fetches a dependency from GitHub, keep a local mirror or vendored copy pinned to a known commit. Know which fork you would switch to before the upstream disappears.

NVIDIA's eight rules for designing sparse attention indexers that run fast on GPUs

With sparse attention, long-context cost moves into the indexer that picks which keys to read, and these measurements show which design choices control that cost.

NVIDIA engineers tested a production FP8 sparse-attention kernel across its main design settings. In sparse attention, a small attention block called the indexer still scores all N keys before Top-k keeps a few thousand of them. In DeepSeek V3.2 prefill, the indexer plus Top-k take 47% of the layer. Their main guidelines: keep G×(D+1) within one Tensor Core tile of about 200 rows, where G is query heads per key head and D is the number of speculative draft tokens. Use one key head with a cross-head reduction and head dimension 128. Run the epilogue (the post-matmul step) in FP16. Fuse Top-k into the indexer and select large blocks rather than single tokens.

Under the hood

  • Decode runtime grows 7.6x from 1 to 8 key heads, because each extra key head re-reads the whole key cache; growing G 16x moves decode runtime only 2%.
  • Guess-Verify-Refine Top-k in TensorRT LLM reuses the previous decode step's selection and is 2.1–2.4x faster than radix select on DeepSeek V3.2/V4. Top-k cost follows the number of keys scored, not k.
  • With a fixed budget of 2,048 keys, halving the block size nearly doubles core attention runtime. An FP16 epilogue gives 1.31x at G=64, D+1=4.

Takeaway. In a sparse-attention model, most long-context cost sits in the indexer and Top-k, so cut the number of keys scored (compression, hierarchical indexing, index sharing). Also size head groups and speculative depth to fit one Tensor Core tile.

Netflix's AI Discover runs a plan-then-execute agent harness with validated capability graphs

A production agent harness design where LLMs propose plans but code validates and executes them, plus a per-member memory store. It applies directly if you build agents.

Netflix describes the intelligence layer behind AI Discover, a theme-driven discovery tab on TV. It does not use a reason-act tool loop. A controller picks a plan: either an already-tested one or one an LLM planner drafts on the fly. Every plan is a graph of typed capabilities (retrieval, ranking, generation, packaging), and the controller validates it before anything runs. An executor runs independent steps in parallel, each with its own deadline and fallback. Generation is asynchronous: the button press returns immediately and the TV shows a "thinking" state until the server notifies it that the page is ready. Safety rules are enforced in code, not in prompts.

Under the hood

  • Plan validation checks that every step is approved, every input has a producer, the graph has no cycles, and the plan ends in exactly one page. If the planner is slow or its plan fails a check, a tested plan runs instead.
  • The planner writes typed placeholders, such as a maturity rating, instead of actual values. After validation, the controller fills them from the request by declared type, which blunts prompt injection.
  • Memory Hub is a low-latency store for each member. It holds taste summaries that the in-house MemberLLM generates offline from viewing history, plus explicit feedback such as "don't recommend". Each plan fetches only the fields it needs.

Takeaway. Have the LLM output a typed plan with placeholders instead of making tool calls directly. Then validate the plan graph in code and keep a tested plan ready as the fallback. Log each step's outcome so you can replay requests when you change prompts or models.

Google open-sources ABFS: Android checkout in 8 seconds, full build in 2 minutes

A content-addressed filesystem plus a two-phase build cache that stays correct even when dependencies are undeclared, built so many agents can work in parallel on one machine.

The Android build team has open-sourced ABFS (Another Build File Service). It has three parts: CASFS, a Linux kernel filesystem module; user-space daemons; and a horizontally scalable gRPC content-addressable storage (CAS) server, which stores data keyed by its hash. AOSP for Android 17 is 1,084 repos, 1.62M files, 161 GB of source and 155 GB of build output. On a 64-vCPU GCE VM, with the server in the same cloud network and timings averaged over 3 runs, checkout fell from ~36 min to under 8 s and a full build from ~80 min to just over 2 min. CASFS stores Git SHA hashes in extended attributes. Names and sizes show up immediately, and the file bytes are fetched through the Cacheman LRU daemon on first read.

The cache replaces Ninja's timestamp checks. In phase 1, Ninja-go hashes the command, the environment and the declared input hashes to look up candidate results from CI or other developers. In phase 2, it checks the candidate's recorded read patch against current file contents. The read patch lists every file the step actually read, captured by tapping the filesystem. If the patch matches, the recorded writes are applied. If not, the step reruns under tapping, so hidden dependencies cannot produce stale outputs.

Under the hood

  • The Cuttlefish build has 192,249 Ninja actions. Even after an edit to system/libbase, 97% of the graph is identical to the CI build.
  • Git-pushers continuously load new Git objects from Gerrit into the CAS server, which indexes source, workspace snapshots and build-step results.
  • Workspaces persist: modified files, git state and repo state sync eagerly to the server, so a mount can resume on another host.
  • Demo: 5 release branches mounted side by side; 4 agents backport, build and test a fix in parallel on one VM. A Bazel proof-of-concept exists.

Takeaway. Validating a cache hit against the files a step actually read, not only its declared inputs, makes sharing results safe even when the dependency graph is incomplete. Lazy loading by content hash also makes parallel agent workspaces almost free to create.

Prime Intellect open-sources Prime Agent, a harness that edits its own memory and prompts

A working design for agent memory you can study: lessons kept between sessions as small, versioned updates you can roll back, with recursive subagents called as code.

Prime Intellect's MIT-licensed coding and research agent is built on two ideas. The first is the Recursive Language Model (RLM): context lives in variables inside a persistent Python REPL, and subagents are function calls (rlm.spawn(...)). The second is the Continual Harness, where supplemental prompts, memories, skill descriptions and subagent specs persist as state. /refine reviews the current trajectory and makes small, evidence-backed edits to that state, with snapshots for rollback. It never touches the immutable base system prompt. The README has no benchmarks. Those would be in the arXiv paper (2608.23552).

Under the hood

  • Agents run on a daemon and survive terminal disconnects. REPL state, schedules and subagents keep running, and you can reattach later. Running agents can message and steer each other directly.
  • /autonomous runs within turn, token and time budgets and can run user-defined quality gates. The README notes that hitting a limit does not mean the task succeeded.
  • The worker and kernel processes are not a security sandbox. Model-generated Python runs with your user permissions.

Takeaway. If you are building agent memory, copy the update model: small, evidence-backed edits to supplemental state, with snapshots and a core prompt that never changes. That keeps self-improvement auditable and reversible.

graphify builds a code knowledge graph for agents with no embeddings

A retrieval design you can compare against vector RAG: tree-sitter parsing, graph traversal, and every edge labelled by how it was derived.

graphify (Apache-2.0, Python, YC S26) parses about 40 languages locally with tree-sitter, an AST (syntax tree) parser, so no LLM is involved. It resolves calls/imports/inherits edges across files and writes graph.json, which agents query with query, path and explain instead of grepping. Docs, PDFs and images go through an optional LLM pass. On the vendor's own harness it reaches 0.497 recall@10 on LOCOMO, against 0.149 for supermemory and 0.048 for mem0. QA accuracy is lower, 45.3% against supermemory's 49.7%. Several test sets are tiny (n=50, n=6).

Under the hood

  • Each edge is tagged EXTRACTED (written explicitly in the source) or INFERRED (resolved by graphify). A path's confidence is the confidence of its weakest hop.
  • Leiden clustering (falls back to Louvain) splits the graph into subsystems and names them without an LLM. 'God nodes' are the most-connected concepts. Ambiguous names return exit code 3 with the candidates listed.
  • Claude Code hooks push the agent toward the graph before it reads or greps files. Strict mode denies a Read or Grep on indexed files unless the agent queried the graph in the last 30 minutes.

Takeaway. For code retrieval, a deterministic AST graph whose edges record where they came from can beat embeddings on recall, at zero LLM cost to build it. Gating raw file reads behind a graph query is an agent-harness technique you can reuse.

Caveman 4.0 compresses agent tool output and keeps every original on disk

The output-shortening voice barely matters. What's worth copying is compressing tool output on the input side while keeping the full original recoverable.

Caveman 4.0 (Apache-2.0) is a local proxy plus a skill that works with Claude Code, Codex, Gemini CLI and about 30 other agents. The terse "voice" it is known for cuts only 3% more output than a plain Answer concisely. prompt (median, n=10). The more useful part works on input. Logs, CSV, YAML, JSON and test output are compressed before the model reads them, and the originals stay on disk so the agent can pull them back. The test was 6 synthetic tasks, each hiding one record in 61–72 KB of noise. Whole sessions used 33.2% fewer input tokens and all 18 answers were still right. HTML has no compressor yet, and those sessions came out 9.9% worse.

Under the hood

Importance-sampling correction for stale rollouts in asynchronous RL

Asynchronous RL keeps the GPUs busy by letting generators sample trajectories while the learner trains. The catch is that a trajectory may have been sampled by a policy several updates old (policy lag k). The policy-gradient estimate assumes samples come from the current policy π_θ, so stale samples bias the update. The usual fix is to weight each sampled token by the ratio r = π_θ(a|s) / μ(a|s), where μ is the behaviour policy that actually produced it.

Step by step: (1) When sampling, record log μ(a_t|s_t) for every token. Recomputing it later is unreliable, because inference engines and trainers produce slightly different numbers even with the same weights. (2) At train time, compute log π_θ for the same tokens and set r_t = exp(log π_θ − log μ). (3) Plug r into a REINFORCE-style loss: r · (R − b) · ∇log π_θ, where b is a baseline. (4) Keep the variance in check. PPO clips each token's ratio, V-trace (IMPALA) truncates it, and some methods drop a whole trajectory when its sequence-level ratio drifts too far.

Example: a token sampled at μ = 0.20 now has π = 0.30, so r = 1.5. With PPO's ε = 0.2 that is clipped to 1.2. Over a 500-token trajectory, an average log-ratio of 0.002 per token gives a sequence ratio of e^1 ≈ 2.7, which is fine. An average of 0.01 gives e^5 ≈ 148, so reject that trajectory. The trade-offs: clipping adds bias, and rejecting trajectories throws away samples, more of them as lag grows. Averaging the loss per trajectory stops long rollouts from dominating the update. Use this correction whenever generation and learning are decoupled.

Further reading: Espeholt et al., 'IMPALA: Scalable Distributed Deep-RL with Importance Weighted Actor-Learner Architectures' (2018); Schulman et al., 'Proximal Policy Optimization Algorithms' (2017)

Agent memory recalls mix source revisions unless the whole read is protected

For a memory engine that reads from several stores, this paper measures how often an update between reads returns contradictory evidence, and what each fix costs.

Haoting Qiu, Qibai Chen

Two independent researchers show that when an agent-memory recall reads from several connections or stores, an update landing between those reads can pair a fact with source text from a different revision. They tested Cognee 1.6.2 (SQLite, LanceDB, Ladybug) at about 20 recalls/s. With no protection, 199 of 12,010 recalls conflicted when writes were spaced out and 284 when writes came in bursts. Simply running the recall a second time did not fix it. Two fixes returned complete, consistent evidence for all 24,020 recalls: a read/write lock held until every lazily loaded result was read (Gate), and a generation-counter check (Epoch). Under bursts, Epoch cut update p95 by 109 ms and added 290 ms to recall p95.

Under the hood

  • Epoch works like a Linux seqlock (a sequence counter that detects reads overlapping a write): the writer moves to an odd WRITING generation, and only a successful write publishes an even READY one. A reader keeps its result only if the same even generation holds before and after, with at most 8 retries inside the deadline.
  • Hindsight fix: one read-only Repeatable Read PostgreSQL snapshot is exported and imported by every connection in the recall. It removed all 10 controlled mismatches, and recall p95 rose from 19 ms to 29 ms.
  • A failed incremental update can leave new derived content while the canonical source record is still old. Both protected policies mark the store DIRTY and refuse reads. In all 80 fault runs, the first default retry recovered through Cognee's built-in full-rebuild fallback.

Takeaway. The protected region has to run from a recall's first read until every lazy result is read, across all stores, not just one database transaction. After a failed write, refuse reads until a successful recovery instead of serving whatever state is half-published.

Under the hood

Stint stops reasoning requests from being repeatedly evicted from GPU memory

Long agent and reasoning outputs fill the GPU's KV cache (stored attention state). Stint ensures that a request it evicts gets to produce new tokens when it comes back, and it limits how long that request waits.

Ziji Shi, Xinyi Wan, Chaoyi Ruan, Guangxing Huang, Min Lin, Jialin Li

Researchers at NUS and Sea AI Lab built Stint on vLLM to fix KV thrashing: a reasoning request is evicted, restored, then evicted again after a few tokens. Stint saves fixed-size KV snapshots to a contiguous CPU pool and copies them in bulk using fused K/V kernels and double buffering. It brings back the oldest waiting request (≥5 s) and guarantees it 64 new tokens. On 399 IMO-AnswerBench problems (Qwen3-32B, H200s), p99 time per output token falls 50.7% and throughput rises 12% versus recomputation. The longest pause drops from 11–14 minutes to under 50 s.

Under the hood

  • Choosing what to evict: a small predictor reads the model's hidden states during decoding to estimate remaining length. Estimates refresh every 64 steps, and Stint evicts the request with the longest remaining output.
  • CPU pool allocator: best-fit with at most 8 contiguous ranges per snapshot; if that fails, the request is recomputed. An 800 GiB usable pool needs 1,024 GiB of pinned memory.
  • Costs: 2.7x more preemptions, median TPOT 38.2→40.9 ms, p99 inter-token latency 47.9→78.0 ms, no gain on short-output workloads. Throughput beats LMCache by 14.2% and HiCache by 48.5%.

Takeaway. Add an anti-starvation rule to any preemptive scheduler: let a request's stall timer keep running until it makes new progress, because restoring its state does not count. Then protect the returning request for a minimum turn. Snapshots that no longer grow can use exact-size, contiguous storage.
